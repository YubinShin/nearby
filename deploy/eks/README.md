# EKS 실험 클러스터

`cluster.yaml` 이 어떤 결정 위에 서 있는지 적어둔다. 매니페스트에는 주석을 두지 않는다.

> **이 클러스터는 실험용이다.** 재고 있는 운영 클러스터가 아니다.
> 답을 얻으면 지운다 — **`down.sh` 를 반드시 돌릴 것.**
> 컨트롤 플레인은 노드를 0으로 줄여도 시간당 요금이 계속 나간다.

관련: [ADR 0011](../../docs/adr/0011-module-split-and-index-contract.md) ·
[ADR 0013](../../docs/adr/0013-indexer-runtime-spring-batch.md) · 실측 전문은 `git show 83bc469`

---

## 이 클러스터가 답하려는 질문 하나

ADR 0011 의 표에 ❌ 로 남은 칸이 있었다.

> "색인이 질의 지연을 밀어올리는 것 — 같은 머신이면 그대로 경쟁한다."

**kind 는 단일 노드라 이 질문에 답할 수 없다.** 그래서 노드를 둘로 나눈 클러스터를 띄우고,
색인기와 질의기를 강제로 다른 노드에 놓고 지연을 다시 잰다.

같은 클러스터에서 **두 번** 잰다 — 분리(`overlays/eks`)와 합침(`overlays/eks-colocated`).
파드 사양은 전부 같고 배치만 다르므로, 두 패스의 차이가 곧 노드 분리의 순효과다.

---

## 노드그룹 두 개

### `ng-query` — 질의 경로 전체 (m7i.xlarge · 4 vCPU / 16 GiB)

search-api + Elasticsearch + Qdrant. **여기가 지연을 재는 노드다.**

ES·Qdrant 를 질의기와 같이 두는 게 의도다. "질의 경로"란 앱만이 아니라 엔진까지다.
이렇게 두면 실험이 두 갈래로 갈리는데, 그게 목적이다.

| 재색인 종류 | 비용이 어디에 | 예상 |
|---|---|---|
| 벡터 | 96.1%가 임베딩 = **순수 앱 CPU** → 다른 노드로 빠진다 | 지연 회복 |
| 키워드 | ES `_bulk` → **같은 ES 파드를 때린다** | 회복 안 됨 |

이 비대칭이 확인되면 "앱 분리는 앱 CPU 경쟁만 푼다"는 결론이 데이터로 남는다.
(메모리 요청 합 ~2.8Gi · 제한 합 ~5Gi · ES 힙 1g)

### `ng-index` — 색인 전용 (c7i.2xlarge · 8 vCPU / 16 GiB)

CPU 를 몰아준다. 임베딩 추론이 색인 시간의 96.1% 라 **인스턴스 타입이 곧 재색인 소요 시간**이다.
여기선 메모리가 아니라 CPU 가 손잡이다. 8 vCPU 중 7 을 파드에 주고 1 을 kubelet·CNI·EBS CSI
데몬셋에 남긴다. 합침 패스에서는 이 노드가 전부를 받는다 — CPU 요청 합 6.7 + 데몬셋 ~0.35 <
할당 가능 ~7.9.

## 두 노드그룹이 **같은 AZ** 여야 하는 이유

대조군(패스 B) 때문이다. 패스를 바꾸면 ES·Qdrant·PostGIS 가 노드를 옮기는데,
**EBS 볼륨은 AZ 에 묶여 있어 다른 AZ 의 노드에는 붙지 않는다.** storageclass 의
`WaitForFirstConsumer` 가 첫 소비자의 AZ 에 볼륨을 만들어 두므로, AZ 가 갈리면 패스 B 에서
PVC 가 영구 Pending 이 된다. 덤으로 AZ 간 네트워크 지연이 변수에서 빠진다
(색인기 → PostGIS 가 노드를 건너간다).

**어느 AZ 인지는 중요하지 않다 — 둘이 같기만 하면 된다.**

---

## 최상위 `availabilityZones` 를 못박는 이유 — 실제로 밟았다

안 적으면 eksctl 이 AZ 3개를 자기가 고른다. 그 선택과 노드그룹의 `availabilityZones` 가
어긋나면 **컨트롤 플레인을 다 만든 뒤에** 노드그룹 단계에서 죽는다.

```
could not find public subnets for zones ["ap-northeast-2a"]
(allSubnets=… "ap-northeast-2b" … "ap-northeast-2c" … "ap-northeast-2d" …)
```

2026-07-26 에 겪었다. eksctl 이 2b·2c·2d 를 골랐는데 노드그룹은 2a 로 못박혀 있었다.
**11분짜리 컨트롤 플레인이 만들어진 뒤에** 실패해서, 살리려면 노드그룹만 따로 만들어야 했다.

`--dry-run` 은 이걸 못 잡는다 — 요청한 값만 보여주고 **AZ 선택은 실제 생성 시점에 일어난다.**

요구사항은 "두 노드그룹이 같은 AZ" 였지 2a 가 아니었으므로, VPC 가 가진 2b 로 옮기고
재발 방지로 AZ 목록 자체를 파일에 못박았다. 3개를 적는 이유는 EKS 컨트롤 플레인이
최소 2개 AZ 의 서브넷을 요구하기 때문이고, 노드는 그중 하나에만 놓는다.

---

## NAT 게이트웨이를 끄는 이유 — `privateNetworking: false` 만으로는 부족하다

`vpc.nat.gateway: Disable` 에서 끊어야 NAT 가 안 생긴다. 노드그룹의 `privateNetworking: false`
는 **노드를 퍼블릭 서브넷에 놓을 뿐**이고, eksctl 은 프라이빗 서브넷을 어차피 만들면서 거기에
NAT 게이트웨이를 붙인다(기본값 `Single`). `--dry-run` 으로 확인한 사실이다.
**이 둘은 한 쌍이다** — 노드그룹만 false 로 두면 노드는 퍼블릭인데 NAT 는 그대로 생겨 요금만 낸다.

끄는 게 안전한 이유: 두 노드그룹이 모두 퍼블릭 서브넷이라 IGW 로 나간다(ECR·Docker Hub 이미지
풀, EKS 컨트롤 플레인 통신 모두 NAT 가 필요 없다). 만들어진 프라이빗 서브넷에는 아무것도
배치하지 않으므로 인터넷 경로가 없어도 무해하다.

아끼는 건 요금(시간당 + GB당)만이 아니다 — NAT 는 생성·삭제가 느려서 실험의 **왕복 시간**을
갉아먹는다. 몇 시간짜리 실험에서 그게 더 아깝다.

---

## `aws-ebs-csi-driver` 애드온과 `withOIDC` — 없으면 클러스터가 통째로 무용지물

최신 EKS 에는 in-tree EBS 프로비저너가 없다. 이 드라이버 없이는 StatefulSet 세 개
(ES·Qdrant·PostGIS)의 PVC 가 **절대 바인딩되지 않는다.** 증상이 "파드가 Pending" 뿐이라
원인을 찾기 어렵다.

드라이버는 IRSA(서비스 어카운트 → IAM 역할)를 쓰므로 `iam.withOIDC: true` 가 짝이다.
이게 빠지면 애드온이 볼륨을 못 만들고 PVC 3개가 Pending 에서 영구 대기한다.

## 아키텍처를 amd64 로 맞춘 이유

로컬(M4)에서 구운 이미지 3개는 arm64 인데 `nearby-postgis` 만 amd64 다
(`postgis/postgis:16-3.4` 가 amd64 전용).

셋을 amd64 로 다시 굽는 쪽을 골랐다. `build-images.sh` 가 `PLATFORM` 을 이미 지원해서 명령
하나로 끝나고, 반대로 가면 **데이터가 구워진 유일한 이미지**(PostGIS 시드 64,239행)의 베이스를
갈아야 한다. 위험한 쪽을 안 건드린다. 수명 몇 시간짜리 실험에서 Graviton 절약분은 무의미하다.

---

## `version` 을 비워두는 이유

eksctl 이 그 시점에 지원되는 기본 버전을 고르게 둔다. 버전을 못박으면 몇 달 뒤 "지원 종료" 로
생성이 실패해서, 실험을 재현하려는 사람이 클러스터 버전부터 고쳐야 한다.
이 파일의 목적은 버전 고정이 아니다.

## 환경별 재색인 실측 — **코어 수로 보간하지 말 것**

같은 64,239건 기준. 아키텍처가 셋 다 다르다.

| 환경 | 코어 | 소요 | 처리량 | 코어당 |
|---|---|---|---|---|
| kind (arm64 · Docker Desktop VM) | 2 | 1,963초 | 32.7건/초 | 16.4 |
| 로컬 (arm64 네이티브 · M4) | 10 | 512초 | 125.5건/초 | 12.6 |
| **EKS c7i** (x86-64 · Sapphire Rapids) | 7 | **275초** | 233.2건/초 | **33.3** |

원래 이 노드를 "코어 수 3번째 측정점"으로 쓸 계획이었고 ~700초를 예상했다. 실측은 275초 —
**7코어가 10코어보다 1.86배 빠르다.** 코어를 늘리면 보통 코어당 처리량이 내려가는데
(16.4 → 12.6) 여기만 33.3 으로 튄다. 병렬 효율로는 설명이 안 되고, 남는 설명은 명령어
집합이다 — c7i 는 AMX / AVX-512 VNNI 를 갖고 있고 임베딩 비용은 대부분 행렬곱이다.

그래서 위 세 줄은 "코어 수 대 시간" 곡선이 아니라 **환경별 실측 세 개**로만 읽어야 한다.
이 실험이 대조군에는 "한 번에 하나만 바꾼다"를 엄격히 적용했으면서 이 예측에는 적용하지
않았던 셈이다 — ADR 0011 의 옛 대조군 표와 같은 종류의 실수다.

## 테인트를 안 건 이유

`ng-index` 에 테인트를 걸면 coredns 같은 시스템 파드까지 막아 측정이 더 깨끗해진다.
안 걸었다 — 얻는 정밀도(coredns 는 CPU 를 거의 안 쓴다)보다 잃는 게 크다. 톨러레이션을 하나
빠뜨리면 파드가 **조용히 Pending** 이 되고, 그 디버깅이 실험보다 오래 걸린다.
배치 보장은 `nodeSelector`(`overlays/eks`) 로 충분하다.
