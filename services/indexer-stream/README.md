# indexer-stream — 이벤트 증분 색인기 (아직 비어 있음)

**이 모듈에는 코드가 없습니다. 일부러 없습니다.**

## 왜 이름이 `-stream` 인가

`indexer-batch` 와 갈리는 축은 **일이 어떻게 도착하느냐**입니다.

| | `indexer-batch` | `indexer-stream` |
|---|---|---|
| 일이 도착하는 방식 | 사람이/스케줄러가 부른다 (`POST /admin/reindex`) | 이벤트가 흘러 들어온다 (Kafka) |
| 언제 도는가 | 전체 재색인, 주기적 따라잡기 | 원천이 바뀌는 그 순간 |

후보로 놓고 떨어뜨린 이름들:

- **`-incremental`** — `indexer-batch` 가 **이미 증분입니다**(`CheckpointStore` 기반 watermark).
  증분이냐 아니냐는 두 모듈을 가르는 축이 아닙니다.
- **`-realtime`** — ADR 0001 이 (A) 실시간을 명시적으로 기각하고 (C) 이벤트 트리거 증분을
  골랐습니다. 모듈 이름이 결정과 어긋나면 안 됩니다.
- **`-dynamic`** — batch 의 대비어로 통용되는 말이 아니라 설명이 필요합니다.
  `batch ↔ stream` 은 설명 없이 읽힙니다.

## 언제 채워지나

**Kafka(또는 그에 준하는 이벤트 버스)가 들어올 때.** 그게 ADR 0001 이 고른 "이벤트 트리거
증분 색인"의 실현입니다. 지금은 원천 변경을 알려주는 장치가 없어서, `indexer-batch` 가
체크포인트를 들고 주기적으로 따라잡는 방식으로 대신하고 있습니다.

채워질 때 함께 일어날 일:

- **`indexer-core` 추출** — 그때 비로소 색인기가 둘이 되고, 둘이 공유하는 것(ES bulk 적용,
  체크포인트, 멱등 규칙)이 눈에 보입니다. 지금 미리 만들면 무엇을 공유할지 **코드 없이 추측**하는
  꼴이라, 두 번 틀립니다. 최종 모습은 `search-core` / `indexer-core` / `-batch` / `-stream`.
- **소비 멱등성** — 같은 이벤트가 두 번 와도 결과가 같아야 합니다 (ADR 0001). `place_id` 기준
  upsert/delete 라 이미 성질은 갖췄고, 재처리 경계만 정하면 됩니다.
- **버전 스탬프 준수** — `IndexMeta` 를 `indexer-batch` 와 똑같이 심어야 합니다. 두 색인기가
  서로 다른 스탬프를 찍으면 질의기의 기동 시 대조가 무의미해집니다.

## 그럼 왜 지금 빈 껍데기를 두나

YAGNI 대로라면 파일 자체가 없어야 맞습니다. 그걸 알면서 남기는 이유는 **이음매의 위치를
문서가 아니라 저장소 구조로 남기기 위해서**입니다. `indexer-batch` 라는 이름은 짝이 있을 때만
의미가 있는 이름이고, 그 짝이 어디에 어떤 이름으로 올지 여기 적어 두면 다음 사람(또는 6개월
뒤의 나)이 `indexer-batch` 를 "그냥 색인기"로 오해하지 않습니다.

대신 **동작하는 척하는 코드는 넣지 않습니다.** 뜨기만 하고 아무것도 안 하는 앱은 뼈대가 아니라
거짓말입니다. 그래서 Spring Boot 플러그인도 아직 붙이지 않았습니다 — 이 모듈은 지금 앱이 아닙니다.
