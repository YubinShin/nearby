# ADR 0006 — 질의 API 런타임으로 리액티브(WebFlux + 코루틴)를 선택

- **상태:** Accepted
- **날짜:** 2026-07-20
- **관련:** ADR 0003 (하이브리드 검색 · 앱단 RRF 결합), **ADR 0013 (이 결정의 적용 범위를 *질의 경로*로 좁힘 — 색인기는 Spring Batch + 블로킹으로 갔다)**

## 배경

검색 요청 하나는 ES·Qdrant 등 **여러 곳에 동시에 질의하고 합치는** 작업입니다. 대부분의 시간이
엔진의 응답을 기다리는 데 쓰이는 I/O 중심 작업입니다. 이 서버의 런타임 방식을 정해야 합니다.

- **(A) 리액티브 (WebFlux + Kotlin 코루틴)** — 응답을 기다리는 동안 스레드를 점유하지 않고 반납합니다. 적은 자원으로 많은 요청을 처리합니다.
- **(B) 블로킹 (MVC + 가상 스레드)** — 위에서 아래로 순서대로 실행되는 일반적인 방식. 대신 JDK 21의 가상 스레드로 동시성을 크게 높입니다.

과거에는 "대규모 I/O = 리액티브"가 통념이었으나, 가상 스레드의 등장으로 (B)도 적은 자원으로 높은
동시성을 낼 수 있게 됐습니다. 따라서 이 선택은 자명하지 않으며, 근거를 남깁니다.

## 결정

**(A) WebFlux + Kotlin 코루틴을 택합니다.**

## 근거

- **이 API의 본질이 '동시에 질의하고 합치기'입니다.** 코루틴이면 `async { } ... await()`로 여러 엔진을
  병렬 호출하는 코드를 순차 코드처럼 읽기 쉽게 쓸 수 있습니다. 결합 로직(RRF)이 명확하게 드러납니다.
- **스레드를 점유하지 않습니다.** 응답을 기다리는 동안 스레드를 반납하므로, 적은 자원으로 많은 동시 요청을 처리합니다.
- **코루틴이 리액티브의 최대 단점을 제거합니다.** 순수 리액티브 코드는 가독성이 나쁘기로 악명 높지만,
  `suspend` 함수로 쓰면 블로킹 코드처럼 위에서 아래로 읽히면서 실행은 논블로킹입니다.
  리액티브의 확장성과 일반 코드의 가독성을 동시에 얻습니다.

## (B)가 유효한 조건

가상 스레드는 일반 블로킹 코드를 유지하면서도 동시성 한계를 크게 풉니다. 다음 조건이라면 (B)가 더 단순하고 안전합니다.

- 대부분이 단순 CRUD이고, 요청 하나가 여러 곳에 팬아웃할 일이 적을 때
- 반드시 써야 하는 드라이버가 블로킹 전용뿐일 때
- 팀이 리액티브에 익숙하지 않아, 잘못 짜서 생기는 사고(블로킹 누수)의 위험이 이득보다 클 때

이 프로젝트는 팬아웃이 본질이고, 사용하는 저장소(ES·Qdrant·Redis 예정)가 모두 논블로킹
클라이언트를 제공하므로 (A)가 맞습니다.

ES 자바 클라이언트는 동기·비동기 양쪽 다 소켓 수준에서는 논블로킹입니다. 동기 클라이언트의
`Rest5Client.performRequest` 는 내부적으로 비동기 호출을 걸고 `Future.get()` 으로 기다립니다.
둘의 차이는 소켓이 아니라 호출한 스레드가 응답을 기다리며 묶이느냐입니다.

## 결과

- **상시 규칙 하나:** 불가피한 블로킹 호출은 `withContext(Dispatchers.IO) { ... }`로 격리해서
  이벤트 루프를 막지 않습니다. 이 경계를 코드 리뷰 체크리스트에 넣습니다.
  질의 경로에는 이제 해당하는 곳이 없습니다. 남은 정당한 사용처는 기동 시 한 번 도는
  `IndexContractGuard` 이며, 이쪽은 core 의 동기 클라이언트를 씁니다(core 는 ADR 0011·0013 에
  따라 동기로 남습니다).
- 데이터 접근은 리액티브(논블로킹) 드라이버를 우선합니다.
- 리액티브에서는 로그 추적 정보(트레이싱)가 끊기기 쉬우므로, 코루틴 컨텍스트에 맞게 전파를 설정합니다.
- 이 결정은 API 서비스 범위에 한정됩니다. 이후 특정 모듈이 단순 블로킹으로 판명되면 그 부분만 (B)로 분리할 수 있습니다.

## 측정 — 동기 클라이언트 + `Dispatchers.IO` 대 비동기 클라이언트

2026-08-03. 지연을 고정한 스텁 ES 에 같은 `Rest5ClientTransport`(같은 커넥션 풀·같은
`JsonpMapper`)로 두 클라이언트를 번갈아 물려 측정했습니다.

- 처리량과 지연은 두 방식이 같습니다.
- 처리량 병목은 클라이언트 방식이 아니라 커넥션 풀입니다.
- 갈리는 곳은 스레드 점유와 취소·타임아웃 두 가지입니다.

### 처리량·지연 (동시 64, 스텁 지연 20ms, 히트 50건)

| 방식 | 처리량 | p50 | p99 |
|---|---|---|---|
| 동기 + `Dispatchers.IO` | 421~423 req/s | 150.0~151.7ms | 163.2~165.9ms |
| 비동기 | 419~421 req/s | 150.9~151.1ms | 165.5~169.3ms |

동시 256 까지 올려도 두 방식 모두 ~421 req/s 로 같습니다. `Dispatchers.IO` 의 64 스레드
상한은 병목이 아닙니다.

### 커넥션 풀 크기별 처리량 (동시 64)

| maxConnPerRoute | 동기 | 비동기 |
|---|---|---|
| 10 (기본값) | 423 req/s, p99 163.7ms | 420 req/s, p99 166.4ms |
| 25 | 1061 req/s, p99 70.6ms | 1058 req/s, p99 71.0ms |
| 50 | 2081 req/s, p99 40.6ms | 2028 req/s, p99 42.5ms |

`Rest5ClientBuilder.DEFAULT_MAX_CONN_PER_ROUTE` 가 10 이고 스프링 부트가 이 값을 덮지
않습니다. 스텁이 관측한 최대 동시 요청 수는 어느 설정에서나 풀 크기와 같습니다.
동기와 비동기의 차이는 어느 줄에서도 2% 안쪽입니다.

### 스레드 점유

| 항목 | 동기 | 비동기 |
|---|---|---|
| `DefaultDispatcher-worker` 최대 | 70개 | 0개 |
| JSON 역직렬화 스레드 | `Dispatchers.IO` | HC5 I/O 리액터 |

### 취소·타임아웃 (3초 스텁에 `withTimeout(100ms)`)

| 방식 | 반환까지 |
|---|---|
| 동기 + `Dispatchers.IO` | 3016ms |
| 비동기 | 110ms |

코루틴 취소는 협조적이라 `suspend` 지점에서만 관측합니다. `withContext(Dispatchers.IO)`
블록 안은 블로킹 자바 코드라 취소 지점이 없고, `Future.get()` 에 묶인 스레드와 커넥션은
ES 가 응답할 때까지 잡혀 있습니다. 비동기 클라이언트는 취소가 in-flight HTTP 요청까지
전파됩니다.

### 결정 사항

| 결정 | 근거 |
|---|---|
| 질의 경로를 비동기 클라이언트로 전환 | 동기 경로는 타임아웃·취소가 in-flight 요청에 닿지 않아 느린 ES 앞에서 부하를 덜어내지 못함 |
| 성능 개선을 전환 근거로 쓰지 않음 | 처리량·지연이 두 방식 동일 |
| `maxConnPerRoute` 기본값 10 유지 | 스텁 기준 수치라 실제 ES 자원 한계를 반영하지 못함. 실제 ES 측정 후 결정 |
| `runInterruptible` 미채택 | 타임아웃은 듣지만 나간 HTTP 요청과 커넥션이 회수되지 않음 |
