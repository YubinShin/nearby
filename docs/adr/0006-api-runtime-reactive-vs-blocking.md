# ADR 0006 — 서버를 리액티브(WebFlux+코루틴)로 짠 이유

- **상태:** Accepted
- **날짜:** 2026-07-20
- **관련:** ADR 0003 (하이브리드 검색 · 앱단 RRF 결합), **ADR 0013 (이 결정의 적용 범위를 *질의 경로*로 좁힘 — 색인기는 Spring Batch + 블로킹으로 갔다)**

## 배경 (무엇을 정해야 하나)

검색 요청 하나가 ES·Qdrant 등 **여러 곳에 동시에 물어보고 합치는** 일이에요. 대부분의 시간이
"엔진의 답을 기다리는" 데 쓰이는 I/O 중심 작업이죠. 이 서버를 어떤 방식으로 짤까요?

- **(A) 리액티브 (WebFlux + Kotlin 코루틴)** — 답을 기다리는 동안 스레드를 붙잡지 않고 놓아줘요. 적은 자원으로 많은 요청을 처리해요.
- **(B) 블로킹 (MVC + 가상 스레드)** — 평범하게 위에서 아래로 순서대로 짜요. 대신 JDK 21의 가상 스레드로 동시에 아주 많이 돌려요.

예전엔 "대규모 I/O = 무조건 리액티브"였는데, 가상 스레드가 나오면서 (B)도 적은 자원으로 높은
동시성을 낼 수 있게 됐어요. 그래서 이 선택은 자명하지 않고, 근거를 남겨요.

## 결정

**(A) WebFlux + Kotlin 코루틴을 택한다.**

## 왜 (근거)

- **이 API의 본질이 '동시에 물어보고 합치기'예요.** 코루틴이면 `async { } ... await()`로 여러 엔진을
  나란히 부르는 코드를 순차 코드처럼 읽기 쉽게 쓸 수 있어요. 합치는 로직(RRF)이 깔끔하게 드러나요.
- **스레드를 안 붙잡아요.** 답을 기다리는 동안 스레드를 놓아주니, 적은 자원으로 많은 동시 요청을 처리해요.
- **코루틴이 리액티브의 최대 단점을 없애줘요.** 순수 리액티브 코드는 읽기 어렵기로 악명 높은데,
  `suspend` 함수로 쓰면 블로킹 코드처럼 위→아래로 읽히면서 실행은 논블로킹이에요.
  "리액티브의 확장성 + 평범한 코드의 가독성"을 동시에 가져가는 거예요.
- **경험·환경과 결이 맞아요.** 실무에서 리액티브 검색 서빙을 다뤄봤고, 코루틴을 적극 쓰는 환경과도 잘 맞아서 학습 비용이 낮아요.

## 언제였다면 (B)를 골랐을까

가상 스레드는 평범한 블로킹 코드를 유지하면서도 동시성 한계를 크게 풀어줘요. 그래서 다음이라면 (B)가 더 단순하고 안전해요.

- 대부분이 단순 CRUD이고, 요청 하나가 여러 곳에 팬아웃할 일이 적을 때
- 꼭 써야 하는 드라이버가 블로킹 전용뿐일 때
- 팀이 리액티브에 익숙하지 않아, 잘못 짜서 생기는 사고(블로킹 누수)의 위험이 이득보다 클 때

이 프로젝트는 팬아웃이 본질이고, 쓰는 저장소(ES·Qdrant·Redis)가 모두 논블로킹 클라이언트를
제공하며, 코루틴으로 학습 비용을 낮출 수 있어서 (A)가 더 맞아요.

## 결과 (이렇게 하면 뒤따르는 일)

- **상시 규칙 하나:** 어쩔 수 없는 블로킹 호출은 `withContext(Dispatchers.IO) { ... }`로 격리해서
  이벤트 루프를 막지 않게 해요. 이 경계를 코드 리뷰 체크리스트에 넣어요.
- 데이터 접근은 리액티브(논블로킹) 드라이버를 우선해요.
- 리액티브에선 로그 추적 정보(트레이싱)가 끊기기 쉬워서, 코루틴 컨텍스트에 맞게 전파를 설정해요.
- 이 결정은 API 서비스 범위에 한정돼요. 나중에 특정 모듈이 단순 블로킹으로 판명되면 그 부분만 (B)로 분리할 수 있어요.
