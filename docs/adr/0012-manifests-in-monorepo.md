# ADR 0012 — 배포 매니페스트를 소스와 같은 저장소에 둔다 (모노레포)

- **상태:** Accepted
- **날짜:** 2026-07-25
- **관련:** ADR 0011 (모듈 분리 — *무엇을 배포하나*), ADR 0002 (용도별 클러스터 분리 — *어디에 배포하나*)

## 배경 (무엇을 정해야 하나)

`deploy/k8s/` 에 kind·EKS 매니페스트를 만들면서, 이걸 **앱 소스와 같은 저장소**에 둘지
**별도 config 저장소**로 뺄지를 정해야 했다. 이건 취향 문제가 아니라 트레이드오프가 있는 결정이고,
"왜 이렇게 뒀냐" 는 질문이 반드시 나온다.

실무 GitOps 에서는 대개 **config 저장소를 분리**한다. 이유가 셋 있다.

1. **CI 루프 방지.** 앱 CI 가 이미지를 빌드한 뒤 매니페스트의 이미지 태그를 bump 하는데,
   그 매니페스트 커밋이 **같은 저장소의 앱 CI 를 다시 트리거**하면 무한 루프가 돈다.
   저장소가 다르면 애초에 안 걸린다.
2. **히스토리 분리.** "코드가 바뀐 이력" 과 "배포가 바뀐 이력" 이 섞이지 않는다.
   롤백도 배포만 되돌린다 — 코드 히스토리를 건드리지 않고.
3. **ArgoCD 단일 소스 + 권한 분리.** Argo 는 config 저장소 하나만 바라본다. 개발자는 앱,
   운영은 배포로 권한이 갈린다.

이 방식은 이미 겪어 봤다 — 이전 프로젝트(`이전 프로젝트`)는 앱과 별개인 config 저장소에서
ArgoCD app-of-apps + kustomize base/overlays 로 운영했다.

## 결정 — 이 저장소는 **모노레포로 둔다**

포트폴리오의 목적은 *운영 자동화*가 아니라 **설계를 하나의 이야기로 읽히게 하는 것**이다.
리뷰어가 한 번 클론해서 **소스 → 이미지 → 매니페스트**를 끊김 없이 따라갈 수 있어야 한다.
저장소를 둘로 나누면 그 흐름이 끊기고, 포폴에서 얻는 것(자동화)은 없다 — ArgoCD 도, 태그
bump CI 도 여기서는 안 돌기 때문이다. 즉 **분리의 세 이유가 전부 이 저장소엔 적용되지 않는다.**

그래서 `deploy/k8s/` 를 소스와 같은 트리에 둔다. 대신 내부는 실무 config 저장소와 **같은 구조**
(kustomize `base/` + `overlays/{kind,eks}`)로 맞춰, 나중에 그대로 떼어낼 수 있게 한다.

## 분리로 넘어가는 트리거 (YAGNI 경계)

지금 안 나누는 것이지 "안 나눈다" 가 아니다. 아래 중 하나라도 참이면 config 저장소로 뗀다.

- 이미지 빌드 CI 와 배포 동기화(ArgoCD 등)를 **실제로 연결**할 때 → 태그 bump 루프가 현실이 된다.
- 배포를 만지는 사람과 코드를 만지는 사람의 **권한을 나눠야** 할 때.
- 매니페스트가 **여러 앱/여러 클러스터**로 늘어 app-of-apps 가 필요해질 때.

이 트리거는 ADR 0011 이 `indexer-core` 추출을 미룬 논리와 같다 — **이음매는 지금 구조로 보여
두되(base/overlays), 자동화가 실재하기 전에는 저장소를 쪼개지 않는다.**

## 결과

- `deploy/k8s/` 가 소스와 한 저장소에 있고, 내부는 config 저장소로 바로 승격 가능한 kustomize 구조다.
- 면접에서 "매니페스트를 소스랑 같이 뒀네?" 는 **약점이 아니라 트레이드오프를 아는 근거**가 된다:
  포폴이라 모노레포, 실무 GitOps 면 분리 — 그 이유(루프·히스토리·권한)와 실제 경험을 함께 댈 수 있다.
