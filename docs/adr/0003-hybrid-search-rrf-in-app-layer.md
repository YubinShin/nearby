# ADR 0003 — 키워드·벡터 결과를 앱에서 합치는 방법 (RRF)

- **상태:** Accepted · **구현 완료 (6단계, 2026-07-23)**
- **날짜:** 2026-07-20
- **관련:** ADR 0007 (벡터 엔진 선택)

## 배경 (무엇을 정해야 하나)

검색은 두 엔진을 동시에 써요.

- **키워드 검색(ES, BM25)** — 글자가 얼마나 맞나로 점수를 매겨요.
- **벡터 검색(Qdrant)** — 뜻이 얼마나 비슷한가로 점수를 매겨요.

각자 "장소 목록 + 점수"를 돌려주는데, 문제는 **두 점수의 단위가 완전히 달라요.** BM25 점수는
몇 점, 몇십 점까지도 나오고, 벡터 유사도는 0~1 사이예요. 이 둘을 그냥 더하면 숫자가 큰 쪽
(보통 BM25)이 결과를 독식해요. **그럼 어떻게 공평하게 합칠까?**

## 결정

**애플리케이션 레이어에서 RRF(Reciprocal Rank Fusion)로 직접 합친다.**

RRF는 점수가 아니라 **순위**만 써요. 각 결과의 순위로 `1 / (k + 순위)` 점수를 매겨서 더해요.
점수 단위가 달라도 순위는 공평하니까, 한쪽이 독식하지 않아요.

```kotlin
fun rrf(rankings: List<List<String>>, k: Int = 60): List<Pair<String, Double>> {
    val scores = HashMap<String, Double>()
    for (ranking in rankings) {
        ranking.forEachIndexed { i, id -> scores.merge(id, 1.0 / (k + i + 1), Double::plus) }
    }
    return scores.entries.sortedByDescending { it.value }.map { it.key to it.value }
}
```

## 왜 (근거)

- **점수 스케일 문제를 우회해요.** 순위만 쓰니 BM25와 벡터 점수를 억지로 같은 잣대로 맞출 필요가 없어요.
- **엔진 내장 기능 대신 앱단인 이유** — 검색 엔진에도 RRF 기능이 있지만 상위 라이선스(유료) 제약이
  있어요. 그리고 우리 결과는 애초에 **서로 다른 시스템(ES + Qdrant)** 에서 와요. 그래서 앱단에서
  직접 합치는 게 라이선스 제약도 피하고, 두 엔진을 자유롭게 조합할 수 있어요.

## 언제였다면 다른 선택을 했을까

**단일 엔진(ES만)** 을 쓰고 라이선스가 허용된다면, 엔진 내장 결합 기능을 쓰는 게 더 단순해요.
이 프로젝트는 별도 벡터 엔진(Qdrant)까지 조합하는 하이브리드라, 앱단 결합이 자연스러워요.

## 결과 (이렇게 하면 뒤따르는 일)

- 각 엔진은 "순위 목록"만 돌려주면 돼요. 결합은 앱이 책임져요.
- `k` 값(기본 60)으로 순위의 영향력을 조절할 수 있어요. 튜닝 대상이에요.
- 결합 로직은 순수 함수라 **단위 테스트하기 쉬워요** — 다양한 순위 조합을 검증해둬요.

## 구현하며 정한 것 (6단계)

ADR 을 쓸 때는 "RRF 로 합친다"까지만 정해져 있었어요. 실제로 붙여 보니 **결합 공식보다
그 주변에서 정할 게 더 많았어요.**

### ① 각 채널에서 얼마나 깊게 뜰까 — `candidates = 50`

최종적으로 10건을 보여줄 거라고 채널마다 10건씩만 뜨면 안 돼요. **한 채널이 11등에 둔 정답은
다른 채널이 1등을 줘도 결합에 들어오지도 못해요.** 결합의 이득("한쪽이 놓친 걸 다른 쪽이 건진다")이
통째로 사라지는 지점이라, 단위 테스트로 못박아 뒀어요(`RrfTest.깊은 후보를 가져와야…`).

대가: 하이브리드가 부르는 키워드 질의는 50건을 뜨느라 단독 질의(10건)보다 느려요 — 실측 13.6ms vs 9.2ms.

### ② 한쪽이 죽으면 어떻게 할까 — 반쪽으로라도 답한다

채널이 둘이면 고장날 곳도 둘이에요. **하이브리드가 각 채널보다 *덜* 안정적이면 합칠 이유가 없어요.**
그래서 채널 실패를 삼키고 나머지로 답하되, `degraded`·`channels[].failed` 로 드러내요.
조용히 반쪽 결과를 주는 게 제일 나빠요.

### ③ 벡터만 찾은 문서를 어떻게 보여줄까 — ES 에서 채운다

벡터 payload 에는 주소가 없어요(용량 절약). 그대로 내보내면 **어느 엔진이 찾았느냐에 따라 응답
필드가 들쭉날쭉해져요.** 합쳐서 하나로 준다고 해놓고 출처가 비쳐 보이는 셈이라, 부족한 것만
ES mget 한 번으로 채워요(실측 2.1ms). 이 조회가 실패해도 검색은 성공시켜요 —
주소 없는 결과가 결과 없음보다 나아요.

### ④ 동점을 어떻게 깰까 — 점수 → 최고등수 → id

정해두지 않으면 **페이지마다 순서가 흔들려** 같은 문서가 두 번 보이거나 아예 사라져요.
실측으로 6페이지 60건에 중복 0건을 확인했어요.

## 실측 (2026-07-23, 강남구 64,239건)

### 되찾은 질의 — 실제로 칠 법한 질의 20개

| 채널 | 0건 질의 수 |
|---|---|
| 키워드 (`/v1/search`) | **10 / 20** |
| 벡터 (`/v1/vsearch`) | 1 / 20 |
| **하이브리드 (`/v1/hsearch`)** | **1 / 20** |

키워드가 못 찾던 `회 먹을 데`·`머리 자르는 곳`·`혼밥하기 좋은 집`·`매운 거 먹고 싶다` 류가
전부 살아났어요. (`야근하고 갈 곳` 하나만 어느 채널로도 0건)

### 지연 (예열 후 50회, Prometheus 카운터 차분)

| 채널 / 단계 | 평균 |
|---|---|
| 키워드 단독 | 9.2ms |
| 벡터 단독 | 4.9ms |
| **하이브리드 전체** | **16.3ms** |
| └ keyword 단계 (후보 50건) | 13.6ms |
| └ vector 단계 (후보 50건) | 5.0ms |
| └ hydrate (ES mget) | 2.1ms |
| └ fuse (RRF 계산) | **0.21ms** |

- **결합 자체는 공짜예요** — 0.21ms, 전체의 1.3%. 비용은 전부 "두 번 부르는 것"과
  "깊게 뜨는 것"에서 나와요.
- **팬아웃이 먹혔어요** — 13.6 + 5.0 = 18.6ms 가 아니라 느린 쪽(13.6)에 수렴하고,
  거기에 hydrate·fuse 가 붙어 16.3ms.

### 장애 주입 (컨테이너 중단)

| 상황 | HTTP | degraded | 결과 |
|---|---|---|---|
| 정상 | 200 | false | total 95 |
| Qdrant 중단 | 200 | **true** | 키워드만으로 total 50 |
| ES 중단 | 200 | **true** | 벡터만으로 total 50 (주소는 `null`) |
| 각각 복구 | 200 | false | total 95 로 자동 복귀 |

## 아직 답이 없는 것

**"합쳐서 더 좋아졌나"를 증명하지 못했어요.** 0건이 10개에서 1개로 준 건 확실한 이득이지만,
키워드가 이미 잘하던 질의에서는 순위가 크게 바뀌어요 — `역삼동 카페`는 키워드 top10 중
3개만 하이브리드 top10 에 남았어요.

이게 개선인지 개악인지 **판정할 정답 데이터가 없어요** (아키텍처 크리틱 #11). `k`·채널 가중치도
같은 이유로 기본값(60, 1:1)에서 움직이지 못했어요. 질의–클릭 로그가 쌓여 nDCG 를 계산할 수
있어야 비로소 튜닝 대상이 돼요. **손잡이는 설정으로 빼뒀지만, 근거 없이 돌리지 않았어요.**
