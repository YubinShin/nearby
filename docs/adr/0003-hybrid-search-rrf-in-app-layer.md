# ADR 0003 — 키워드·벡터 결과를 앱 레이어에서 RRF 로 결합

- **상태:** Accepted · **구현 완료 (6단계, 2026-07-23)**
- **날짜:** 2026-07-20
- **관련:** ADR 0007 (벡터 엔진 선택)

## 배경

Nearby의 검색은 키워드만으로는 놓치는 의미 질의를 살리기 위해 두 엔진을 동시에 사용합니다.

- **키워드 검색(ES, BM25)** — 역문서 빈도(IDF)와 단어 빈도(TF) 기반 스코어링 (0~Unbounded)
- **벡터 검색(Qdrant)** — 벡터 유사도 기반 스코어링 (0~1)

각 엔진이 질의에 따른 "장소 목록 + 점수"를 반환합니다.
두 결과를 별도 처리 없이 더하면 숫자가 큰 쪽(보통 BM25)이 결과를 독식합니다.

각 엔진의 결과를 공평하게 결합하는 방법이 필요합니다.

## 결정

**애플리케이션 레이어에서 RRF(Reciprocal Rank Fusion)로 직접 합칩니다.**

RRF는 점수 단위를 버리고 **순위**만 사용하여 한쪽의 독식을 막는 방법입니다.
각 결과의 순위로 `1 / (k + 순위)` 점수를 매겨 결합합니다.

```kotlin
fun rrf(rankings: List<List<String>>, k: Int = 60): List<Pair<String, Double>> {
    val scores = HashMap<String, Double>()
    for (ranking in rankings) {
        ranking.forEachIndexed { i, id -> scores.merge(id, 1.0 / (k + i + 1), Double::plus) }
    }
    return scores.entries.sortedByDescending { it.value }.map { it.key to it.value }
}
```

## 근거

- **점수 스케일 문제를 우회한다** — BM25(0~무한)와 벡터 유사도(0~1)는 단위가 달라 직접
  비교가 불가하므로, 점수는 버리고 순위만 사용합니다.
- **엔진 내장 기능 대신 애플리케이션 층위** — Elasticsearch에도 RRF 기능이 있으나 상위
  라이선스(유료) 제약이 존재합니다. 또한 Nearby의 검색 결과는 애초에 **서로 다른 시스템(ES +
  Qdrant)** 에서 오므로 엔진 내장 RRF만으로는 결합이 불가합니다. 라이선스 제약을 피하고
  서로 다른 엔진 간 결과를 결합하기 위해 애플리케이션 단 RRF를 택했습니다.

## 다른 선택이 유효한 조건

**단일 엔진(ES만)** 을 쓰고 라이선스가 허용된다면 엔진 내장 결합 기능이 복잡도가 낮습니다.
이 프로젝트는 별도 벡터 엔진(Qdrant)까지 조합하는 하이브리드이므로 앱단 결합이 자연스럽습니다.

## 결과

- 각 엔진은 "순위 목록"만 반환합니다. 결합은 앱의 책임으로 분리됩니다.
- `k` 값(기본 60, 튜닝 대상)은 순위 간 점수 격차를 누르는 평활 상수로, 클수록 두 채널의 합의를 우대합니다.
- 결합 로직은 순수 함수라 **단위 테스트가 가능합니다** — 다양한 순위 조합을 검증해 둡니다.

## 구현하며 정한 것 (6단계)

결합 공식 외에 구현 시 추가로 정한 사항입니다.

### ① 각 채널에서 얼마나 깊게 뜰까 — `candidates = 50`

최종 노출이 10건이라고 채널마다 10건씩만 가져오면 안 됩니다. **한 채널이 11등에 둔 정답은
다른 채널이 1등을 줘도 결합에 들어오지 못합니다.** 결합의 이득("한쪽이 놓친 것을 다른 쪽이 건진다")이
통째로 사라지는 지점이라, 단위 테스트로 못박아 두었습니다(`RrfTest.깊은 후보를 가져와야…`).

대가: 하이브리드가 부르는 키워드 질의는 50건을 뜨느라 단독 질의(10건)보다 느립니다 — 실측 13.6ms vs 9.2ms.

### ② 한쪽이 죽으면 어떻게 할까 — 반쪽으로라도 답한다

채널이 둘이면 고장날 곳도 둘입니다. **하이브리드가 각 채널보다 *덜* 안정적이면 합칠 이유가 없습니다.**
그래서 채널 실패를 삼키고 나머지로 답하되, `degraded`·`channels[].failed`로 드러냅니다.
조용히 반쪽 결과를 주는 것이 최악입니다.

### ③ 벡터만 찾은 문서를 어떻게 보여줄까 — ES에서 채운다

벡터 payload에는 주소가 없습니다(용량 절약). 그대로 내보내면 **어느 엔진이 찾았느냐에 따라 응답
필드가 들쭉날쭉해집니다.** 합쳐서 하나로 준다고 해놓고 출처가 비쳐 보이는 셈이라, 부족한 것만
ES mget 한 번으로 채웁니다(실측 2.1ms). 이 조회가 실패해도 검색은 성공시킵니다 —
주소 없는 결과가 결과 없음보다 낫습니다.

### ④ 동점을 어떻게 깰까 — 점수 → 최고등수 → id

정해두지 않으면 **페이지마다 순서가 흔들려** 같은 문서가 두 번 보이거나 아예 사라집니다.
실측으로 6페이지 60건에 중복 0건을 확인했습니다.

### ⑤ 거리로 다시 세울까 — 세우지 않는다

`/v1/hsearch` 와 `/v1/vsearch` 는 `sort` 를 받지 않습니다. 결합 결과를 거리순으로 재정렬하면
RRF 등수가 통째로 버려지고, 벡터 단독 경로에서는 의미 유사도로 뽑은 순서가 버려집니다.
좌표를 받으면 정렬과 무관하게 `distanceM` 은 채웁니다 — 서버가 이미 아는 값입니다.

거리 기반 재랭킹은 7단계 작업입니다 (ADR 0005).

## 실측 (2026-07-23, 강남구 64,239건)

### 되찾은 질의 — 실제로 칠 법한 질의 20개

| 채널 | 0건 질의 수 |
|---|---|
| 키워드 (`/v1/search`) | **10 / 20** |
| 벡터 (`/v1/vsearch`) | 1 / 20 |
| **하이브리드 (`/v1/hsearch`)** | **1 / 20** |

키워드가 못 찾던 `회 먹을 데`·`머리 자르는 곳`·`혼밥하기 좋은 집`·`매운 거 먹고 싶다` 류가
전부 살아났습니다. (`야근하고 갈 곳` 하나만 어느 채널로도 0건)

### 지연 (예열 후 50회, Prometheus 카운터 차분)

> **초기 측정치(2026-07-23).** 최신 수치는 [ADR 0011](0011-module-split-and-index-contract.md)과
> [README](../../README.md)를 참고할 것 — 같은 실행 안에서 하이브리드 중앙값과 함께 재측정했다.

| 채널 / 단계 | 평균 |
|---|---|
| 키워드 단독 | 9.2ms |
| 벡터 단독 | 4.9ms |
| **하이브리드 전체** | **16.3ms** |
| └ keyword 단계 (후보 50건) | 13.6ms |
| └ vector 단계 (후보 50건) | 5.0ms |
| └ hydrate (ES mget) | 2.1ms |
| └ fuse (RRF 계산) | **0.21ms** |

- **결합 자체는 공짜다** — 0.21ms, 전체의 1.3%. 비용은 전부 "두 번 부르는 것"과
  "깊게 뜨는 것"에서 나옵니다.
- **팬아웃이 유효했다** — 13.6 + 5.0 = 18.6ms가 아니라 느린 쪽(13.6)에 수렴하고,
  거기에 hydrate·fuse가 붙어 16.3ms.

### 장애 주입 (컨테이너 중단)

| 상황 | HTTP | degraded | 결과 |
|---|---|---|---|
| 정상 | 200 | false | total 95 |
| Qdrant 중단 | 200 | **true** | 키워드만으로 total 50 |
| ES 중단 | 200 | **true** | 벡터만으로 total 50 (주소는 `null`) |
| 각각 복구 | 200 | false | total 95 로 자동 복귀 |

## 아직 답이 없는 것

**"합쳐서 더 좋아졌나"를 증명하지 못했습니다.** 0건이 7개에서 0개로 준 것은 확실한 이득이지만,
키워드가 이미 잘하던 질의에서는 순위가 크게 바뀝니다 — `역삼동 카페`는 키워드 top10 중
3개만 하이브리드 top10에 남았습니다.

이것이 개선인지 개악인지 **판정할 정답 데이터가 없습니다** (아키텍처 리뷰 #11). `k`·채널 가중치도
같은 이유로 기본값(60, 1:1)에서 움직이지 않았습니다. 질의–클릭 로그가 쌓여 nDCG를 계산할 수
있어야 비로소 튜닝 대상이 됩니다. **손잡이는 설정으로 빼두었지만, 근거 없이 돌리지 않았습니다.**
