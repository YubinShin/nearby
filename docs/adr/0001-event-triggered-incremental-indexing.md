# ADR 0001 — 데이터를 언제 색인할까: 실시간 말고 '바뀔 때만'

- **상태:** Accepted
- **날짜:** 2026-07-20

## 배경 (무엇을 정해야 하나)

장소의 진짜 정보는 원천 창고(PostGIS)에 있어요. 그런데 사용자가 검색하려면 이 데이터가
검색 엔진(ES·Qdrant)에도 들어가 있어야 해요. 이렇게 검색 엔진에 넣는 과정을 **색인**이라고 해요.

질문은 이거예요 — **이 색인을 언제, 어떻게 할까?** 세 가지 방법이 있어요.

- **(A) 실시간** — 데이터가 바뀌는 즉시 바로 색인.
- **(B) 주기적 폴링** — 몇 분마다 "바뀐 거 있나?" 하고 전체를 확인해서 색인.
- **(C) 이벤트 트리거 증분** — 데이터가 새로 생기거나 바뀌는 '사건(이벤트)'이 있을 때, 그 바뀐 부분만 색인.

## 결정

**(C) 이벤트 트리거 증분 색인을 택한다.**

## 왜 (근거)

장소 데이터는 성격이 있어요 — **자주 바뀌지 않아요.** 가게 이름·주소·카테고리는 하루에도
수백 번씩 바뀌는 값이 아니에요. 이 성격에 맞춰 방법을 골라야 해요.

- **(A) 실시간은 과해요.** 초 단위 즉시성이 필요 없는 데이터에 실시간 파이프라인을 붙이면
  비용과 복잡도만 커져요.
- **(B) 주기 폴링은 낭비예요.** 대부분의 확인은 "바뀐 거 없음"으로 끝나요. 아무 변화도 없는데
  계속 전체를 훑는 건 자원을 버리는 거예요.
- **(C) 증분은 딱 맞아요.** 바뀌는 사건이 있을 때만, 바뀐 것만 반영해요. 낭비 없이 최신 상태를
  유지할 수 있어요.

한 가지 덧붙이면 — 실무에서는 **실시간** 색인을 다뤄봤어요. 여기서 굳이 증분을 고른 건
"몰라서"가 아니라 **이 도메인엔 증분이 맞아서**예요. 둘 다 이해하고 상황에 맞게 골랐다는 게 핵심이에요.

## 언제였다면 다른 선택을 했을까

재고·가격처럼 **초 단위로 바뀌고 즉시 반영이 중요한 데이터**라면 (A) 실시간을 골랐을 거예요.
이 프로젝트의 장소 데이터는 그렇지 않아요.

## 결과 (이렇게 하면 뒤따르는 일)

- 변경을 감지해 '이벤트'로 알려주는 장치가 필요해요(변경 감지 → 색인 트리거).
- 같은 이벤트가 두 번 와도 결과가 같도록 **멱등(idempotent)** 하게 설계해요. 색인 실패 시 재처리도 안전하게.
- 이 흐름은 '천천히 차선'이에요. 콘텐츠(장소 정보)는 느리게 바뀌니 이 차선으로,
  사용자 행동처럼 순간순간 바뀌는 건 별도의 '빠른 차선(Redis)'으로 나눠서 다뤄요.
