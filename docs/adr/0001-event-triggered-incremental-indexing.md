# ADR 0001 — 이벤트 트리거 증분 색인을 선택

- **상태:** Accepted
- **날짜:** 2026-07-20

## 배경

장소의 원본 데이터는 원천 저장소(PostGIS)에 있습니다. 사용자가 검색하려면 이 데이터가
검색 엔진(ES·Qdrant)에도 들어가 있어야 합니다. 검색 엔진에 넣는 이 과정을 **색인**이라 합니다.

정할 것은 **이 색인을 언제, 어떻게 수행할 것인가**입니다. 방법은 세 가지입니다.

- **(A) 실시간** — 데이터가 바뀌는 즉시 색인.
- **(B) 주기적 폴링** — 몇 분마다 변경 여부를 전체 확인해서 색인.
- **(C) 이벤트 트리거 증분** — 데이터가 생성·변경되는 '사건(이벤트)'이 있을 때, 바뀐 부분만 색인.

## 결정

**(C) 이벤트 트리거 증분 색인을 택합니다.**

## 근거

장소 데이터의 성격이 출발점입니다 — **자주 바뀌지 않습니다.** 가게 이름·주소·카테고리는 하루에도
수백 번씩 바뀌는 값이 아닙니다. 이 성격에 맞춰 방법을 골라야 합니다.

- **(A) 실시간은 과합니다.** 초 단위 즉시성이 필요 없는 데이터에 실시간 파이프라인을 붙이면
  비용과 복잡도만 커집니다.
- **(B) 주기 폴링은 낭비입니다.** 대부분의 확인은 "변경 없음"으로 끝납니다. 변화가 없는데
  계속 전체를 훑는 것은 자원 낭비입니다.
- **(C) 증분이 맞습니다.** 변경 사건이 있을 때만, 바뀐 것만 반영합니다. 낭비 없이 최신 상태를
  유지할 수 있습니다.

## 다른 선택이 유효한 조건

재고·가격처럼 **초 단위로 바뀌고 즉시 반영이 중요한 데이터**라면 (A) 실시간을 골랐을 것입니다.
이 프로젝트의 장소 데이터는 그렇지 않습니다.

## 결과

- 변경을 감지해 '이벤트'로 알려주는 장치가 필요합니다(변경 감지 → 색인 트리거).
- 같은 이벤트가 두 번 와도 결과가 같도록 **멱등(idempotent)** 하게 설계합니다. 색인 실패 시 재처리도 안전해야 합니다.
- 이 방식은 느리게 바뀌는 콘텐츠(장소 정보)에 적용합니다. 사용자 행동처럼 빠르게 바뀌는 데이터는
  별도 저장소(Redis)로 다룹니다(ADR 0004).
