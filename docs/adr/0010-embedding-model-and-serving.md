# ADR 0010 — 임베딩 모델 선택과 추론을 돌릴 자리

- **상태:** Accepted
- **날짜:** 2026-07-23
- **관련:** ADR 0007 (벡터 엔진 Qdrant), ADR 0003 (앱단 RRF 결합), ADR 0006 (WebFlux/코루틴), ADR 0008 (형태소 분석 — *같은 함정의 다른 얼굴*)

## 배경

5단계는 "뜻으로 찾기"입니다. ADR 0007에서 **벡터를 어디에 담을지**(Qdrant)는 정했지만, 정작
**벡터를 누가 만드는지**는 안 정했습니다. 두 가지를 정해야 합니다.

1. **어떤 모델**로 문장을 벡터로 바꿀 것인가.
2. 그 추론을 **어디서** 돌릴 것인가 — 앱 안인가, 별도 추론 서버인가, 외부 API인가.

## 결정 1 — `intfloat/multilingual-e5-small` (384차원, ONNX)

| 후보 | 차원 | 크기 | 왜 안 골랐나 / 골랐나 |
|---|---|---|---|
| **multilingual-e5-small** | 384 | 470MB | ✅ 다국어(한국어 포함) · 노트북 CPU로 6만 건 배치가 현실적 · **ONNX 공식 배포**라 파이썬 없이 JVM에서 바로 추론 |
| bge-m3 | 1024 | 2.2GB | 품질은 위지만 차원·모델이 2~5배. 저장·추론 비용이 로컬 데모 범위를 넘고, 차원이 커지면 Qdrant 메모리도 함께 커진다 |
| ko-sroberta 계열 | 768 | ~1.1GB | 한국어 특화라 매력적이지만 **ONNX 배포가 없어** 변환 파이프라인(파이썬·torch)이 전제가 된다. "재현 가능한 로컬 스택"이라는 이 프로젝트의 전제와 충돌 |
| OpenAI/Voyage 등 API | — | — | 네트워크·비용·키 관리가 붙고, 무엇보다 **오프라인 재현이 불가능**해진다. 색인 6만 건이 곧 API 청구서 |

**한국어만 놓고 보면 e5-small이 최고 품질은 아닙니다.** 다국어 모델이라 한국어 전용
모델보다 밀리는 지점이 있습니다. 그래도 고른 이유는 "품질 최대화"가 아니라 **"파이썬 없이 JVM에서
재현 가능하게 돌아가는 것 중 가장 나은 것"** 이 이 단계의 제약이기 때문입니다. 품질을 올려야 할
때 바꿀 자리는 `EmbeddingModel` 한 곳이고, 차원이 바뀌면 컬렉션을 다시 만들면 됩니다
(그래서 컬렉션 차원을 상수로 박지 않고 **모델에서 읽어** 씁니다).

### e5 계열의 접두어 규칙 — 조용히 품질을 깎는 함정

이 모델은 학습할 때 문장 앞에 `query: ` / `passage: ` 를 붙였습니다. 추론에서도 붙여야 합니다.
안 붙여도 **에러가 안 납니다.** 벡터는 멀쩡히 나오고 검색도 되는데 품질만 떨어집니다.

그래서 호출부가 실수할 수 없게 API를 아예 갈랐습니다 — `embedQuery()` / `embedPassages()`.
"실수할 수 있는 API를 만들지 않는다"가 이런 종류의 오류를 막는 유일한 방법입니다.

## 결정 2 — 추론을 **앱 안에서** 돌린다 (DJL + ONNX Runtime)

별도 추론 서버(TEI·파이썬 FastAPI)를 띄우지 않고, JVM 프로세스 안에서 ONNX 모델을 직접 돌립니다.

### 왜

- **색인과 질의가 같은 모델·같은 전처리를 쓰도록 코드로 강제됩니다.** 이게 가장 큰 이유입니다.
  문서 벡터와 질의 벡터가 다른 모델에서 나오면 두 벡터는 **다른 공간**에 놓여 유사도가
  의미를 잃습니다. 그런데 이 사고는 조용히 일어납니다 — 추론 서버만 먼저 배포하면 끝입니다.

  > **ADR 0008에서 이미 같은 함정을 밟았습니다.** 색인과 검색이 다른 사전을 보면 같은 글자가
  > 다르게 쪼개져 매칭이 조용히 깨집니다(아키텍처 리뷰 #14). 형태소 사전에서 배운 걸 임베딩에서
  > 되풀이하지 않으려고, 아예 **한 클래스에 묶어** 물리적으로 갈라질 수 없게 했습니다.

- **운영 단위가 하나 줍니다.** 로컬 스택은 이미 컨테이너 4개입니다. 5번째를 추가하는 값이
  이 규모에선 없습니다.
- **왕복이 없습니다.** 질의 임베딩이 프로세스 안 함수 호출이라 네트워크 홉이 0입니다.

### 포기한 것

- **질의 노드가 무거워집니다.** 모델 로딩에 기동 시 5.7초, 상주 메모리 약 0.5GB(JVM 힙
  바깥의 네이티브 메모리)를 씁니다. 질의 노드를 얇게 굴리고 싶으면 부담입니다.
  → 그래서 `psp.vector.enabled=false` 스위치를 뒀습니다. 키워드만 서빙하는 노드는 모델을 아예 안 읽습니다.
- **CPU를 검색과 나눠 씁니다.** 임베딩 추론은 CPU를 태우는 일이라, 같은 프로세스의 질의 처리와
  코어를 두고 경쟁합니다. 그래서 추론 동시 진입을 세마포어로 제한하고(`pool-size`),
  IO 디스패처가 아니라 `Dispatchers.Default`에서 돌립니다.
- **모델 교체가 배포입니다.** 추론 서버라면 모델만 바꿔 띄우면 되는데, 지금은 앱 배포가 필요합니다.

### 언제 떼어내야 하나 (판단 기준)

이 결정은 되돌릴 수 있습니다. 다음 중 하나라도 걸리면 추론을 별도 서비스로 분리합니다.

1. **GPU가 필요할 때** — 문서 수가 수백만이 되면 CPU 배치 임베딩이 몇 시간이 됩니다.
2. **모델 A/B가 필요할 때** — 두 모델을 동시에 서빙하며 비교하려면 앱 배포와 분리돼야 합니다.
3. **질의 노드의 메모리·기동 시간이 병목일 때** — 오토스케일이 잦으면 기동 5.7초가 비싸집니다.
4. **다른 언어 스택이 임베딩을 필요로 할 때** — 추천 배치(파이썬)가 같은 모델을 써야 한다면,
   그땐 공유 서비스가 맞습니다. 단, **그 순간 "같은 모델을 쓴다"를 보장하는 책임이 코드에서 운영으로
   넘어갑니다** — 모델 버전을 벡터에 함께 기록하는 장치가 반드시 따라와야 합니다.

## Base Image

모델 470MB를 색인기와 질의기 두 이미지에 각각 넣으면 노드가 940MB를 내려받습니다. 두 앱이 공유 베이스 이미지를 `FROM` 하면 레이어가 같아 한 번만 내려받고, 두 번째 이미지는 jar 레이어만 추가로 받습니다.

볼륨(PVC)이 아니라 이미지에 굽습니다. 모델은 불변이고, 바뀌면 그건 다른 모델이라 벡터를 전부 다시 만들어야 합니다(ADR 0011의 버전 도장이 이걸 강제합니다). 이미지에 넣으면 모델 버전이 이미지 태그로 남아 배포 이력에서 확인됩니다.

베이스는 JRE가 아니라 JDK입니다. DJL/ONNX Runtime이 네이티브 라이브러리를 풀어 쓰는데 일부 JRE 슬림 이미지에는 `libstdc++`가 없습니다. 약 100MB 차이보다 기동이 깨지지 않는 쪽을 택했습니다.

파일은 `deploy/model-base/Dockerfile`입니다. 이미지의 `ENV PSP_MODEL_DIR`은 `core.yml`의 `psp.embedding.model-dir` 기본값을 덮고, `EmbeddingModel`이 그 값으로 모델 디렉터리를 찾습니다.

## Qdrant 쪽 설계

- **거리:** Cosine. 임베딩을 L2 정규화해 저장하므로 코사인 = 내적입니다.
- **HNSW:** `m=16`, `ef_construct=100`(색인), `hnsw_ef=128`(질의). 질의 시 `ef`는 요청마다
  조절할 수 있는 손잡이로 남겨뒀습니다 — **정확도(recall)와 지연을 바꿔치기하는 유일한 다이얼**입니다.
- **payload 인덱스:** `sigungu`·`dong`·`category_large`(keyword), `location`(geo).
  필터를 **엔진 안에서** 걸기 위한 것입니다. 앱에서 사후 필터링하면 "강남구" 하나만 붙어도
  상위 N이 대부분 탈락해 결과가 텅 빕니다.
- **무중단 교체:** `place_vec_v{n}` 을 새로 채운 뒤 alias를 원자적으로 옮깁니다 — ES와 **같은 패턴**
  (ADR 0002). 벡터 엔진이 달라도 인덱스 생명주기 규약은 하나로 유지됩니다.
- **점 id:** Qdrant의 id는 부호 없는 정수이거나 UUID여야 합니다. 우리 `place_id`는 문자열이라
  못 씁니다. `UUID.nameUUIDFromBytes(place_id)`로 **결정적으로** 변환하고 원본은 payload에 담습니다.
  결정적이어야 upsert/delete가 멱등해집니다(ADR 0001).

### 색인 파이프라인을 키워드와 분리한 이유

`/admin/vector/reindex` 는 `/admin/reindex` 와 **별도로** 실행됩니다. 체크포인트도 별도 키입니다.

- 임베딩 추론은 ES bulk보다 **두 자릿수 느립니다**(실측: 아래). 한 파이프라인에 묶으면 느린 쪽이
  빠른 쪽의 주기를 결정해버립니다.
- 모델을 바꾸면 벡터만 전부 다시 만들어야 합니다. 그때 키워드 인덱스까지 재색인할 이유가 없습니다.
- 체크포인트를 공유하면 빠른 쪽이 watermark를 먼저 밀어 **느린 쪽이 델타를 건너뜁니다.**

## 벡터 검색에는 "0건"이 없다 — 그래서 문턱이 필요하다

키워드 검색은 안 맞으면 0건입니다. 벡터 검색은 **항상 `limit`개를 반환합니다.** 뜻이 아무리 멀어도
가장 가까운 것들을 줍니다. 그대로 두면 `ㅁㄴㅇㄹ` 같은 아무 말에도 그럴싸한 목록이 나옵니다.

그래서 `min-score` 아래는 잘라냅니다. 값은 감이 아니라 **점수 분포를 재서** 정했습니다(아래 실측).

## 실측

측정 환경: MacBook M4 16GB, 강남구 상가정보 64,239건, Qdrant 1.12.4 컨테이너, 앱은 호스트 JVM.

### 색인

| 항목 | 값 |
|---|---|
| 문서 수 | 64,239 |
| 전체 소요 | **8분 53초** (약 121건/초) |
| 그중 임베딩 추론 | **8분 31초 = 95.8%** |
| 그중 Qdrant 적재 | 22초 |
| 비교: 키워드 색인(ES bulk, 같은 데이터) | **14초** |

**병목은 벡터 엔진이 아니라 임베딩 추론입니다**(95.8%). Qdrant 만 놓고 보면 22초로, ES bulk 의
14초와 같은 자릿수입니다. 그래서 "벡터 색인이 느리다"의 해결책은 엔진 튜닝이 아니라
**추론을 어디서 어떻게 돌리느냐**(배치 크기·GPU·전용 서버)입니다.

**임베딩 색인은 키워드 색인보다 38배 느립니다.** 이 한 줄이 파이프라인을 분리한 이유 전부입니다.
같은 트리거에 묶었다면 증분 색인 주기가 느린 쪽에 맞춰졌을 것입니다.
(증분은 반대로 아주 쌉니다 — 1건 수정 반영에 **125ms**.)

#### 무중단 교체 검증

alias 를 v2↔v3 로 **20회 왕복 스왑**하는 동안 검색을 계속 던졌습니다:
**230회 요청, 실패 0회, 빈 결과 0회.** Qdrant 의 alias 액션 목록이 원자적이라
"가리키는 곳이 없는 순간"이 실제로 생기지 않는다는 걸 확인했습니다 (ES 와 같은 성질).

증분 색인도 네 가지를 확인했습니다: 이름 수정 → payload 반영, 소프트 삭제 → 점 제거,
복구 → 재삽입(총 64,239 유지), 재실행 → `matched=0`(멱등).

### 질의 지연 (강남구 64,239점, 50회 반복 중앙값)

| 경로 | 종단 | 내역 |
|---|---|---|
| 벡터 (질의 캐시 히트) | **4.8ms** (p95 7.2) | ANN 3.6ms |
| 벡터 (캐시 미스) | **9.3ms** (p95 10.1) | 임베딩 3.5ms + ANN 4.3ms |
| 키워드 (BM25) | 8.0ms (p95 20.8) | — |

두 가지가 예상과 달랐습니다.

1. **벡터 검색이 키워드보다 느리지 않습니다.** 6만 건 규모에선 HNSW 탐색이 4ms 안쪽이고,
   BM25 쪽이 오히려 꼬리가 깁니다(p95 20.8ms — 형태소 분석 + 여러 필드 매칭).
   "벡터는 무겁다"는 통념은 **규모에 따라 달라지는 이야기**였습니다.
2. **임베딩이 3.5ms밖에 안 듭니다.** 짧은 질의(≤64토큰)라 CPU로도 충분했습니다.
   질의 캐시가 아끼는 건 약 4.5ms — 있으면 좋지만 이게 결정적이진 않습니다.
   (색인 때 6만 건을 태우는 비용과는 완전히 다른 이야기입니다. 배치와 온라인의 비대칭.)

> 수치는 JIT 워밍업 후 측정한 값입니다 (첫 호출 851ms).

### 점수 분포와 문턱 (top-1 코사인)

| 질의 종류 | 최소 | 중앙값 | 최대 |
|---|---|---|---|
| 뜻이 통하는 질의 20개 | 0.844 | 0.864 | 0.883 |
| 엉터리·데이터에 없는 질의 12개 | 0.794 | 0.825 | **0.870** |

**두 분포는 겹칩니다.** 이게 이 표의 핵심입니다. `화산 분화구 투어`(0.870)가 `머리 자르는 곳`(0.847)보다
점수가 높습니다. 정규화된 임베딩의 코사인은 0.8 언저리에 몰려서, **절대 점수만으로 "관련 있음/없음"을
가르는 건 원리적으로 안 됩니다.**

| 문턱 | 진짜 질의 통과 | 엉터리 차단 | 진짜 질의가 받는 결과 수(중앙값/최소) |
|---|---|---|---|
| 0.78 (첫 추측) | 20/20 | **0/12** | 20 / 20 |
| 0.82 | 20/20 | 5/12 | 20 / 20 |
| **0.84 (채택)** | **20/20** | **10/12** | 20 / 5 |
| 0.86 | 12/20 | 11/12 | 1 / 0 (8개 질의가 0건) |

0.84가 "진짜 질의는 하나도 안 잃으면서 엉터리 질의의 대부분을 막는" 지점입니다. 그래도 2개는 통과합니다.

질의 세트는 `scripts/eval/queries_threshold.txt`, 측정은 `scripts/eval/measure_threshold.py` 입니다.
2026-08-01 재측정에서 32개 질의 모두 같은 값이 나왔습니다.

> **한계를 분명히 해둡니다.** 문턱은 임시방편입니다. 근본 해결은 **하이브리드**입니다 —
> "이 질의에 진짜 맞는 게 있느냐"는 판단은 글자가 겹치는지 보는 키워드 채널이 훨씬 잘합니다.
> 6단계 RRF는 기능 추가가 아니라 **이 결함의 해결책**입니다 (ADR 0003).

### 두 채널의 성격 차이 (같은 질의, 다른 답)

| 질의 | 키워드(BM25) | 벡터 |
|---|---|---|
| `회 먹을 데` | **0건** | 먹어도[횟집] · 마시아[일식 회/초밥] |
| `브런치 먹을 곳` | **0건** | 브런치빈강남[경양식] · 르브런쉭[백반/한정식] |
| `머리 자르는 곳` | **0건** | 머리할때이쁘잖아[미용실] · 머리산책[미용실] |
| `혼밥하기 좋은 집` | **0건** | 혼밥대왕[백반/한정식] · 집밥가득드림 |
| `세탁소` | (일치) | 한국세탁소[세탁소] 0.883 |
| `스타벅스` | 0건 (**상호명에 '스타벅스'가 없다** — 매장은 있는데 지점명만 등록돼 있다. data-model.md) | 0건 ← 문턱 0.84가 막음 (최고점 0.834) |
| `차 고치는 곳` | 0건 | 차병원사거리포차 · 타워차이주 ← **글자 `차`에 낚임** |

- **벡터가 이기는 곳:** 사용자의 *말*(먹을 데·자르는 곳)과 데이터의 *분류*(횟집·미용실)를 잇습니다.
  키워드는 이 질의들에 전부 0건이었습니다 — 형태소 사전을 아무리 채워도 안 되는 종류의 0건입니다.
- **벡터가 지는 곳:** ① **정확한 상호명**. `스타벅스`는 강남구 원천에 0건인데(wildcard로 확인)
  벡터는 `스타럭스`(0.834)를 내밀려 합니다. **"없다"고 말할 줄 모릅니다.** 문턱 0.84가 이 건은
  간신히 막지만, `차 고치는 곳`(0.842)은 못 막습니다 — 0.008 차이입니다. ② **글자에 낚입니다.** `차 고치는 곳`이
  자동차 정비소가 아니라 `차병원사거리포차`로 갔습니다. 다국어 소형 모델의 한계입니다.
  (`자동차 정비`라고 치면 정확히 자동차 정비소가 나옵니다 — 질의 표현에 민감합니다.)

**두 채널은 서로의 실패를 메웁니다.** 이 표가 6단계 하이브리드의 근거 자료입니다.

## 결과

- 벡터 채널이 키워드 채널과 **같은 응답 계약**(`SearchResponse`)을 지키므로, 6단계 RRF 결합은
  순위 목록 두 개를 합치는 순수 함수 하나로 끝납니다 (ADR 0003).
- 모델을 바꾸면 **벡터 전체 재색인**이 필요합니다. 차원이 바뀌면 컬렉션도 새로 만들어야 합니다
  (alias 스왑이 이걸 무중단으로 만들어줍니다).
- 새 리뷰 항목: **벡터에 모델 버전이 기록되지 않습니다.** 지금은 "모델 바꾸면 재색인"이라는 규율로만
  막고 있습니다 — 사전·인덱스 버전 정합(#14)과 정확히 같은 문제입니다.

## 문턱값 후속 (6단계에서 드러난 결함, 2026-07-23)

`min-score: 0.84` 를 정할 때 **필터 없는 전체 코퍼스**의 점수 분포만 봤습니다. 6단계에서 하이브리드에
반경 필터를 얹자 그 전제가 깨졌습니다.

### 증상

`q=카페` + 강남역 반경 300m → **0건.** 반경 안에 장소가 2,015건 있는데도.

| 반경 | 반경 안 장소 수 | top-1 코사인 | 결과 |
|---|---|---|---|
| 없음 (6만 건 전체) | 64,239 | 0.87 | 정상 |
| 1000m | – | **0.846** | 5건 (간신히 통과) |
| 500m | – | < 0.84 | **0건** |
| 300m | **2,015** | < 0.84 | **0건** |

### 원인

**후보 집합이 좁아지면 "그 안에서 가장 뜻이 가까운 것"의 절대 점수도 함께 내려갑니다.**
문턱은 6만 건 기준으로 그어 놓았는데 후보만 2천 건으로 줄었으니, 기준선이 후보 분포 전체보다
위로 떠 버렸습니다. 필터가 강할수록 결과를 더 많이 지웁니다 — **가장 필요할 때 가장 크게 망가집니다.**

### 결정

**엔진 필터가 하나라도 걸린 질의에는 절대 문턱을 적용하지 않습니다.**

문턱의 임무는 "이 질의에 맞는 게 코퍼스에 **아예 없다**"를 잡는 것입니다. 사용자가 필터로 범위를
좁혔다면 *어디서 찾을지*는 이미 사용자가 정한 것이고, 남는 질문은 "그 안에서 뭐가 제일
가깝나"뿐입니다. 필터 조합은 무한하므로 조합마다 문턱을 다시 재는 것도 불가능합니다.
**못 그을 바에는 안 긋는 쪽이 정직합니다.**

규칙 하나로 두 경우가 모두 맞습니다.

| 질의 | 필터 | 문턱 | 결과 |
|---|---|---|---|
| `스타벅스` | 없음 | 적용 | 0건 ✅ (원천에 실제로 없음) |
| `카페` + 반경 300m | 있음 | 미적용 | 최근접 결과 ✅ |

### 남은 이슈

이 규칙은 **필터가 실제로 범위를 좁혔는지 묻지 않습니다.** 지금 데이터는 전부 강남구라
`sigungu=강남구` 는 아무것도 걸러내지 않는데, 그것만으로도 문턱이 꺼져 `스타벅스` 가
`스타럭스포타커피`(0.834)를 반환합니다. → 아키텍처 리뷰 #18.
(2026-08-01 에 닫았습니다 — 아래 "문턱값 후속 2".)

### 덤으로 고친 것 — `total` 이 `size` 를 되읊던 문제

벡터 채널은 엔진에 딱 `from + size` 만큼만 요구했습니다. 그래서 `total` 이 "몇 건이 문턱을
넘었나"가 아니라 **"몇 건 달라고 했나"** 를 그대로 되돌려줬습니다 (`size=1 → total=1`,
`size=10 → total=10`). 최소 50건은 뜨도록 바꿨습니다.

## 브랜드 복원 후 재임베딩 (2026-07-23)

상호명에서 빠져 있던 브랜드를 복원한 뒤(`place_brand`, data-model.md), 임베딩 문장 맨 앞에
브랜드를 넣고 6만 건을 다시 임베딩했습니다.

```
전:  "신사역. 커피점/카페 카페. 강남구 신사동"
후:  "스타벅스 신사역. 커피점/카페 카페. 강남구 신사동"
```

| | |
|---|---|
| 소요 | 511초 (8분 31초) |
| 그중 임베딩 추론 | 489초 (**95.6%**) |
| 무중단 | `place_vec_v2` → `v3` alias 스왑, 검색 중단 없음 |

### 얻은 것

| 질의 | 키워드 | 벡터 | 하이브리드 |
|---|---|---|---|
| `스타벅스` | 86 | **0 → 26** | 62 |
| `강남 스타벅스` | 14 | 50 | 50 |
| `스타벅스 역삼` | 22 | 50 | 51 |

- **벡터 채널이 `스타벅스` 를 찾기 시작했습니다.** 문턱 0.84를 26건이 넘겼습니다.
- **하이브리드 상위 10건이 전부 두 채널 합의**(`ranks` 에 keyword·vector 둘 다)로 바뀌었습니다.
  키워드만 고쳤을 때는 벡터가 `스타커피`·`스타카페` 같은 잡음을 올렸습니다.

### 대가 — 86건의 이동이 다른 질의에도 번진다

임베딩 문장이 바뀐 문서는 **모든 질의에서** 위치가 바뀝니다. 실제로 `역삼동 카페` 벡터 top-3 이
이렇게 달라졌습니다.

| | top-3 |
|---|---|
| 전 | 역삼대로 · 역삼커피로스터스 · 역삼럭키 |
| 후 | 역삼커피로스터스 · 역삼이마트 · 커피인류 역삼점 |

빠진 `역삼대로`·`역삼럭키` 는 스타벅스 매장입니다. 문장에 `스타벅스` 가 붙으면서 일반적인
'카페' 질의에서 멀어진 것입니다. **이게 개선인지 개악인지는 판정할 수 없습니다** — 정답 데이터가
없습니다(아키텍처 리뷰 #11). 다만 **바뀌었다는 사실과 방향은 기록해 둡니다.**

관계없는 질의 다섯 개(`회 먹을 데`·`머리 자르는 곳`·`혼밥하기 좋은 집`·`브런치 먹을 곳`·
`역삼동 카페`)의 건수와 상위 결과는 그대로였고, 엉터리 질의(`ㅁㄴㅇㄹ` 0건, `차 고치는 곳` 1건)도
변화가 없었습니다.

## 문턱값 후속 2 — 필터 선택도 (2026-08-01)

리뷰 #18을 반영했습니다. 앞 절의 "남은 이슈"가 대상입니다.

### 결정

**후보가 한 건도 빠지지 않은 필터에만 문턱값을 유지합니다.** 한 건이라도 빠지면 기존대로 적용하지 않습니다.

같은 질의에 필터만 바꿔 확인했습니다.

| 질의 | 필터 | 빠진 후보 | 문턱 | 결과 |
|---|---|---:|---|---:|
| `스타벅스` | 없음 | — | 적용 | 26건 |
| `스타벅스` | `sigungu=강남구` | 0건 | 적용 | 26건 |
| `스타벅스` | 반경 2000m | 39,477건 | 미적용 | 50건 |

26건은 문턱을 넘은 건수(최저 0.840), 50건은 후보 풀 전체입니다. 수선 전에는 둘째 줄도 50건이었습니다.

빠진 후보가 없으면 후보 집합이 필터 없을 때와 같습니다. 집합이 같으니 점수 분포도 같고, 그래서 측정 없이 안전을 말할 수 있습니다. 장담할 수 있는 경우는 이것뿐입니다.

### 기각한 대안 — 선택도 기준

"남은 비율이 일정 기준을 넘으면 문턱값을 유지한다"도 검토했지만 재보니 성립하지 않았습니다.
강남역 기준, `scripts/eval/queries_threshold.txt` 의 REAL 질의 20개, 문턱값 0.84로 쟀습니다.

| 필터 | 남은 가게 | 남은 비율 | 최저 점수 | 문턱 적용 시 0건이 될 질의 |
|---|---:|---:|---:|---:|
| 없음 | 64,239 | 1.000 | 0.844 | 0/20 |
| 반경 2000m | 24,762 | 0.385 | 0.844 | 0/20 |
| 카테고리 `과학·기술` | 18,653 | 0.290 | 0.816 | **13/20** |
| 동 `역삼1동` | 13,420 | 0.209 | 0.843 | 0/20 |
| 카테고리 `음식` | 12,578 | 0.196 | 0.813 | 7/20 |
| 반경 1000m | 10,488 | 0.163 | 0.841 | 0/20 |
| 카테고리 `소매` | 9,995 | 0.156 | 0.822 | 7/20 |
| 카테고리 `교육` | 6,218 | 0.097 | 0.812 | **16/20** |
| 반경 500m | 3,804 | 0.059 | 0.833 | 2/20 |
| 반경 150m | 472 | 0.007 | 0.815 | 10/20 |

남은 비율과 품질 저하가 비례하지 않습니다. `과학·기술` 은 후보를 29% 남기고도 REAL 질의 13개를
0건으로 만들고, 반경 1000m 는 16%만 남기고도 하나도 잃지 않습니다. 어디에 선을 그어도 카테고리
필터에서 깨집니다.

후보를 줄이는 방식이 다르기 때문입니다. 지리 필터는 업종을 고르게 남긴 채 공간만 좁히므로 의미가
맞는 후보가 집합 안에 남습니다. 카테고리 필터는 의미 축 하나를 통째로 들어냅니다 — `교육` 만 남은
상태에서 `세탁소` 를 찾으면 가장 가까운 결과가 학원입니다. 점수 분포를 정하는 것은 얼마나 줄였는지가
아니라 **어떤 의미 축을 잘랐는지**이고, 비율로는 그것이 보이지 않습니다.

### 구현

개수는 세지 않고 후보가 하나라도 빠졌는지만 확인합니다. Qdrant `points/scroll` 에 필터의
여집합(`must_not`)을 걸고 `limit: 1` 로 조회해, 한 건이라도 나오면 줄어든 것으로 판단합니다.

| 방법 | 실측 |
|---|---|
| 전체 개수 + 필터 개수 (2회 조회) | 10.7 + 14.5ms |
| 여집합 개수 조회 (1회) | 12.0ms |
| **여집합 1건 조회 (채택)** | **1.2ms** |

### 한계

후보를 전혀 줄이지 않는 필터만 걸러냅니다. 의미 축을 자르는 필터에서는 문턱값이 꺼진 채로 나가므로,
`교육` 카테고리에 엉터리 질의를 넣으면 여전히 결과가 나옵니다. 문턱값으로 풀 수 있는 문제가 아니라는
앞 절의 결론은 그대로입니다.
