# ADR 0010 — 임베딩 모델 선택과 추론 위치

- **상태:** Accepted
- **날짜:** 2026-07-23
- **관련:** ADR 0007 (벡터 엔진 Qdrant), ADR 0003 (앱단 RRF 결합), ADR 0006 (WebFlux/코루틴), ADR 0008 (형태소 분석 — 같은 문제의 다른 형태)

## Context

5단계는 "뜻으로 찾기"입니다. ADR 0007에서 벡터를 어디에 담을지(Qdrant)는 정했지만 벡터를 무엇이 만드는지는 정하지 않았습니다. 두 가지를 정해야 합니다.

1. 어떤 모델로 문장을 벡터로 변환할 것인가.
2. 그 추론을 어디서 실행할 것인가 — 앱 안인가, 별도 추론 서버인가, 외부 API인가.

## Decision 1 — `intfloat/multilingual-e5-small` (384d, ONNX)

| 후보 | 차원 | 크기 | 판단 |
|---|---|---|---|
| **multilingual-e5-small** | 384 | 470MB | 채택. 다국어(한국어 포함) · 노트북 CPU로 6만 건 배치가 현실적 · **ONNX 공식 배포**라 파이썬 없이 JVM에서 바로 추론 |
| bge-m3 | 1024 | 2.2GB | 품질은 위지만 차원·모델이 2~5배입니다. 저장·추론 비용이 로컬 데모 범위를 넘고, 차원이 커지면 Qdrant 메모리도 함께 커집니다 |
| ko-sroberta 계열 | 768 | ~1.1GB | 한국어 특화지만 ONNX 배포가 없어 변환 파이프라인(파이썬·torch)이 전제가 됩니다. "재현 가능한 로컬 스택"이라는 이 프로젝트의 전제와 충돌합니다 |
| OpenAI/Voyage 등 API | — | — | 네트워크·비용·키 관리가 붙고, 오프라인 재현이 불가능해집니다. 색인 6만 건이 곧 API 청구서입니다 |

한국어만 놓고 보면 e5-small이 최고 품질은 아닙니다. 다국어 모델이라 한국어 전용 모델보다 품질이 낮은 영역이 있습니다. 그래도 고른 이유는 품질 최대화가 아니라 "파이썬 없이 JVM에서 재현 가능하게 동작하는 것 중 가장 나은 것"이 이 단계의 제약이기 때문입니다. 품질을 올려야 할 때 바꿀 자리는 `EmbeddingModel` 한 곳이고, 차원이 바뀌면 컬렉션을 다시 만듭니다. 그래서 컬렉션 차원을 상수로 두지 않고 모델에서 읽어 씁니다.

### Prefix contract

이 모델은 학습할 때 문장 앞에 `query: ` / `passage: `를 붙였습니다. 추론에서도 붙여야 합니다. 안 붙여도 에러가 발생하지 않습니다. 벡터는 정상적으로 생성되고 검색도 동작하는데 품질만 떨어집니다.

그래서 호출부가 실수할 수 없도록 API를 분리했습니다 — `embedQuery()` / `embedPassages()`.

## Decision 2 — In-process inference (DJL + ONNX Runtime)

별도 추론 서버(TEI·파이썬 FastAPI)를 두지 않고, JVM 프로세스 안에서 ONNX 모델을 직접 실행합니다.

### Rationale

- **모델·전처리 일치를 코드로 강제.** 이것이 가장 큰 이유입니다. 문서 벡터와 질의 벡터가 다른 모델에서 나오면 두 벡터는 다른 공간에 놓여 유사도가 의미를 잃습니다. 이 사고는 오류 없이 발생합니다 — 추론 서버만 먼저 배포하면 그대로 어긋납니다.

  > ADR 0008에서 같은 문제를 겪었습니다. 색인과 검색이 다른 사전을 보면 같은 글자가 다르게 분해되어 매칭이 오류 없이 깨집니다(아키텍처 리뷰 #14). 형태소 사전에서 확인한 문제를 임베딩에서 반복하지 않도록, 한 클래스에 묶어 물리적으로 분리될 수 없게 했습니다.

- **운영 단위 감소.** 로컬 스택은 이미 컨테이너 4개입니다. 5번째를 추가할 이득이 이 규모에는 없습니다.
- **네트워크 홉 없음.** 질의 임베딩이 프로세스 안 함수 호출이라 네트워크 홉이 0입니다.

### Trade-offs

- **질의 노드 부담.** 모델 로딩에 기동 시 5.7초, 상주 메모리 약 0.5GB(JVM 힙 바깥의 네이티브 메모리)를 씁니다. 질의 노드를 가볍게 운영하려면 부담입니다. → 그래서 `psp.vector.enabled=false` 스위치를 뒀습니다. 키워드만 서빙하는 노드는 모델을 로드하지 않습니다.
- **검색과 CPU 공유.** 임베딩 추론은 CPU를 점유하는 작업이라, 같은 프로세스의 질의 처리와 코어를 두고 경쟁합니다. 그래서 추론 동시 진입을 세마포어로 제한하고(`pool-size`), IO 디스패처가 아니라 `Dispatchers.Default`에서 실행합니다.
- **모델 교체가 배포.** 추론 서버라면 모델만 교체해 재기동하면 되는데, 지금은 앱 배포가 필요합니다.

### Revisit conditions

이 결정은 되돌릴 수 있습니다. 다음 중 하나라도 해당하면 추론을 별도 서비스로 분리합니다.

1. **GPU가 필요할 때** — 문서 수가 수백만이 되면 CPU 배치 임베딩이 몇 시간이 됩니다.
2. **모델 A/B가 필요할 때** — 두 모델을 동시에 서빙하며 비교하려면 앱 배포와 분리돼야 합니다.
3. **질의 노드의 메모리·기동 시간이 병목일 때** — 오토스케일이 잦으면 기동 5.7초가 비싸집니다.
4. **다른 언어 스택이 임베딩을 필요로 할 때** — 추천 배치(파이썬)가 같은 모델을 써야 한다면, 그땐 공유 서비스가 맞습니다. 단, 그 순간 "같은 모델을 쓴다"를 보장하는 책임이 코드에서 운영으로 넘어갑니다. 모델 버전을 벡터에 함께 기록하는 장치가 반드시 따라와야 합니다.

## Base Image

모델 470MB를 색인기와 질의기 두 이미지에 각각 넣으면 노드가 940MB를 내려받습니다. 두 앱이 공유 베이스 이미지를 `FROM` 하면 레이어가 같아 한 번만 내려받고, 두 번째 이미지는 jar 레이어만 추가로 받습니다.

볼륨(PVC)이 아니라 이미지에 포함합니다. 모델은 불변이고, 바뀌면 그건 다른 모델이라 벡터를 전부 다시 만들어야 합니다(ADR 0011의 버전 도장이 이걸 강제합니다). 이미지에 넣으면 모델 버전이 이미지 태그로 남아 배포 이력에서 확인됩니다.

베이스는 JRE가 아니라 JDK입니다. DJL/ONNX Runtime이 네이티브 라이브러리를 풀어 쓰는데 일부 JRE 슬림 이미지에는 `libstdc++`가 없습니다. 약 100MB 차이보다 기동이 실패하지 않는 쪽을 택했습니다.

파일은 `deploy/model-base/Dockerfile`입니다. 이미지의 `ENV PSP_MODEL_DIR`은 `core.yml`의 `psp.embedding.model-dir` 기본값을 덮고, `EmbeddingModel`이 그 값으로 모델 디렉터리를 찾습니다.

## Qdrant configuration

- **거리:** Cosine. 임베딩을 L2 정규화해 저장하므로 코사인 = 내적입니다.
- **HNSW:** `m=16`, `ef_construct=100`(색인), `hnsw_ef=128`(질의). 질의 시 `ef`는 요청마다 조절하는 손잡이로 남겨뒀습니다 — 정확도(recall)와 지연을 교환하는 다이얼입니다.
- **payload 인덱스:** `sigungu`·`dong`·`category_large`(keyword), `location`(geo). 필터를 엔진 안에서 거는 것이 목적입니다. 앱에서 사후 필터링하면 "강남구" 하나만 붙어도 상위 N이 대부분 탈락해 결과가 거의 남지 않습니다.
- **무중단 교체:** `place_vec_v{n}`을 새로 채운 뒤 alias를 원자적으로 옮깁니다 — ES와 같은 패턴입니다(ADR 0002). 벡터 엔진이 달라도 인덱스 생명주기 규약은 하나로 유지합니다.
- **점 id:** Qdrant의 id는 부호 없는 정수이거나 UUID여야 합니다. `place_id`는 문자열이라 사용할 수 없습니다. `UUID.nameUUIDFromBytes(place_id)`로 결정적으로 변환하고 원본은 payload에 담습니다. 결정적이어야 upsert/delete가 멱등합니다(ADR 0001).

### Pipeline separation

`/admin/vector/reindex`는 `/admin/reindex`와 별도로 실행됩니다. 체크포인트도 별도 키입니다.

- 임베딩 추론은 ES bulk보다 두 자릿수 느립니다(실측: 아래). 한 파이프라인에 묶으면 느린 쪽이 빠른 쪽의 주기를 결정합니다.
- 모델을 바꾸면 벡터만 전부 다시 만들어야 합니다. 그때 키워드 인덱스까지 재색인할 이유가 없습니다.
- 체크포인트를 공유하면 빠른 쪽이 watermark를 먼저 갱신해 느린 쪽이 델타를 누락합니다.

## Score threshold

키워드 검색은 일치하지 않으면 0건입니다. 벡터 검색은 항상 `limit`개를 반환합니다. 뜻이 아무리 멀어도 가장 가까운 결과를 반환합니다. 그대로 두면 `ㅁㄴㅇㄹ` 같은 임의 문자열에도 결과 목록이 반환됩니다.

그래서 `min-score` 아래는 잘라냅니다. 값은 점수 분포를 측정해 정했습니다(아래 실측).

## Benchmarks

측정 환경: MacBook M4 16GB, 강남구 상가정보 64,239건, Qdrant 1.12.4 컨테이너, 앱은 호스트 JVM.

### Indexing

| 항목 | 값 |
|---|---|
| 문서 수 | 64,239 |
| 전체 소요 | **8분 53초** (약 121건/초) |
| 그중 임베딩 추론 | **8분 31초 = 95.8%** |
| 그중 Qdrant 적재 | 22초 |
| 비교: 키워드 색인(ES bulk, 같은 데이터) | **14초** |

병목은 벡터 엔진이 아니라 임베딩 추론입니다(95.8%). Qdrant만 놓고 보면 22초로, ES bulk의 14초와 같은 자릿수입니다. 그래서 "벡터 색인이 느리다"의 해결책은 엔진 튜닝이 아니라 추론을 어디서 어떻게 실행하느냐(배치 크기·GPU·전용 서버)입니다.

임베딩 색인은 키워드 색인보다 38배 느립니다. 같은 트리거에 묶었다면 증분 색인 주기가 느린 쪽에 맞춰졌을 것입니다. 증분은 비용이 훨씬 낮습니다 — 1건 수정 반영에 **125ms**입니다.

#### Alias swap

alias를 v2↔v3로 20회 왕복 스왑하는 동안 검색을 계속 요청했습니다: **230회 요청, 실패 0회, 빈 결과 0회.** Qdrant의 alias 액션 목록이 원자적이라 "가리키는 곳이 없는 순간"이 실제로 발생하지 않는다는 것을 확인했습니다(ES와 같은 성질).

증분 색인도 네 가지를 확인했습니다: 이름 수정 → payload 반영, 소프트 삭제 → 점 제거, 복구 → 재삽입(총 64,239 유지), 재실행 → `matched=0`(멱등).

### Query latency

강남구 64,239점, 50회 반복 중앙값입니다.

| 경로 | 종단 | 내역 |
|---|---|---|
| 벡터 (질의 캐시 히트) | **4.8ms** (p95 7.2) | ANN 3.6ms |
| 벡터 (캐시 미스) | **9.3ms** (p95 10.1) | 임베딩 3.5ms + ANN 4.3ms |
| 키워드 (BM25) | 8.0ms (p95 20.8) | — |

두 가지가 예상과 달랐습니다.

1. 벡터 검색이 키워드보다 느리지 않습니다. 6만 건 규모에선 HNSW 탐색이 4ms 안쪽이고, BM25 쪽이 오히려 꼬리가 깁니다(p95 20.8ms — 형태소 분석 + 여러 필드 매칭). "벡터는 무겁다"는 통념은 규모에 따라 달라집니다.
2. 임베딩이 3.5ms만 소요됩니다. 짧은 질의(≤64토큰)라 CPU로도 충분했습니다. 질의 캐시가 절약하는 시간은 약 4.5ms로, 결정적이지 않습니다.

> 수치는 JIT 워밍업 후 측정한 값입니다 (첫 호출 851ms).

### Score distribution

top-1 코사인입니다.

| 질의 종류 | 최소 | 중앙값 | 최대 |
|---|---|---|---|
| 뜻이 통하는 질의 20개 | 0.844 | 0.864 | 0.883 |
| 엉터리·데이터에 없는 질의 12개 | 0.794 | 0.825 | **0.870** |

두 분포는 겹칩니다. `화산 분화구 투어`(0.870)가 `머리 자르는 곳`(0.847)보다 점수가 높습니다. 정규화된 임베딩의 코사인은 0.8 언저리에 몰려서, 절대 점수만으로 "관련 있음/없음"을 가르는 것은 사실상 어렵습니다.

| 문턱 | 진짜 질의 통과 | 엉터리 차단 | 진짜 질의가 받는 결과 수(중앙값/최소) |
|---|---|---|---|
| 0.78 (첫 추측) | 20/20 | **0/12** | 20 / 20 |
| 0.82 | 20/20 | 5/12 | 20 / 20 |
| **0.84 (채택)** | **20/20** | **10/12** | 20 / 5 |
| 0.86 | 12/20 | 11/12 | 1 / 0 (8개 질의가 0건) |

0.84가 "진짜 질의는 하나도 잃지 않으면서 엉터리 질의의 대부분을 막는" 지점입니다. 그래도 2개는 통과합니다.

질의 세트는 `scripts/eval/queries_threshold.txt`, 측정은 `scripts/eval/measure_threshold.py`입니다. 2026-08-01 재측정에서 32개 질의 모두 같은 값이 나왔습니다.

> 여기에는 한계가 있습니다. 문턱은 임시방편입니다. 근본 해결은 하이브리드입니다 — "이 질의에 진짜 맞는 게 있느냐"는 판단은 글자가 겹치는지 보는 키워드 채널이 훨씬 잘합니다. 6단계 RRF는 기능 추가가 아니라 이 결함의 해결책입니다(ADR 0003).

| `스타벅스` | 0건 (상호명에 '스타벅스'가 없습니다 — 매장은 있는데 지점명만 등록돼 있습니다. data-model.md) | 0건 ← 문턱 0.84가 막음 (최고점 0.834) |
| `차 고치는 곳` | 0건 | 차병원사거리포차 · 타워차이주 ← 글자 `차`에만 일치 |

- **벡터가 이기는 곳:** 사용자의 말(먹을 데·자르는 곳)과 데이터의 분류(횟집·미용실)를 연결합니다. 키워드는 이 질의들에 전부 0건이었습니다 — 형태소 사전을 채워도 해결되지 않는 종류의 0건입니다.
- **벡터가 지는 곳:** ① 정확한 상호명. `스타벅스`는 강남구 원천에 0건인데(wildcard로 확인) 벡터는 `스타럭스`(0.834)를 반환합니다. "없다"고 판단하지 못합니다. 문턱 0.84가 이 건은 차단하지만, `차 고치는 곳`(0.842)은 차단하지 못합니다 — 0.008 차이입니다. ② 글자에만 일치합니다. `차 고치는 곳`이 자동차 정비소가 아니라 `차병원사거리포차`에 매칭됐습니다. 다국어 소형 모델의 한계입니다. (`자동차 정비`라고 입력하면 정확히 자동차 정비소가 나옵니다 — 질의 표현에 민감합니다.)

두 채널은 서로의 실패를 보완합니다. 이 표가 6단계 하이브리드의 근거 자료입니다.

## Consequences

- 벡터 채널이 키워드 채널과 같은 응답 계약(`SearchResponse`)을 지키므로, 6단계 RRF 결합은 순위 목록 두 개를 합치는 순수 함수 하나로 끝납니다(ADR 0003).
- 모델을 바꾸면 벡터 전체 재색인이 필요합니다. 차원이 바뀌면 컬렉션도 새로 만들어야 합니다. alias 스왑이 이 과정을 무중단으로 만듭니다.
- 모델 이름과 차원은 `IndexMeta.Stamp`에 기록해 기동·증분 시 대조합니다. 다르면 질의기가 뜨지 않고 증분 색인도 거부합니다. 규율이 아니라 장치로 막습니다.

## Threshold follow-up (2026-07-23)

6단계에서 드러난 결함입니다. `min-score: 0.84`를 정할 때 필터 없는 전체 코퍼스의 점수 분포만 봤습니다. 6단계에서 하이브리드에 반경 필터를 적용하자 그 전제가 깨졌습니다.

### Symptom

`q=카페` + 강남역 반경 300m → **0건.** 반경 안에 장소가 2,015건 있는데도 0건입니다.

| 반경 | 반경 안 장소 수 | top-1 코사인 | 결과 |
|---|---|---|---|
| 없음 (6만 건 전체) | 64,239 | 0.87 | 정상 |
| 1000m | – | **0.846** | 5건 (간신히 통과) |
| 500m | – | < 0.84 | **0건** |
| 300m | **2,015** | < 0.84 | **0건** |

### Cause

후보 집합이 좁아지면 "그 안에서 가장 뜻이 가까운 것"의 절대 점수도 함께 내려갑니다. 문턱은 6만 건 기준으로 그었는데 후보만 2천 건으로 줄었으니, 기준선이 후보 분포보다 높아졌습니다. 필터가 강할수록 결과를 더 많이 지웁니다.

### Decision

엔진 필터가 하나라도 걸린 질의에는 절대 문턱을 적용하지 않습니다.

문턱의 임무는 "이 질의에 맞는 게 코퍼스에 아예 없다"를 판정하는 것입니다. 사용자가 필터로 범위를 좁혔다면 어디서 찾을지는 이미 사용자가 정한 것이고, 남는 질문은 "그 안에서 무엇이 가장 가까운가"뿐입니다. 필터 조합은 무한하므로 조합마다 문턱을 다시 측정하는 것도 사실상 어렵습니다.

규칙 하나로 두 경우가 모두 맞습니다.

| 질의 | 필터 | 문턱 | 결과 |
|---|---|---|---|
| `스타벅스` | 없음 | 적용 | 0건 (원천에 실제로 없음) |
| `카페` + 반경 300m | 있음 | 미적용 | 최근접 결과 |

### Open issue

이 규칙은 필터가 실제로 범위를 좁혔는지 묻지 않습니다. 지금 데이터는 전부 강남구라 `sigungu=강남구`는 아무것도 걸러내지 않는데, 그것만으로도 문턱이 꺼져 `스타벅스`가 `스타럭스포타커피`(0.834)를 반환합니다. → 아키텍처 리뷰 #18. 2026-08-01에 닫았습니다 — 아래 "Threshold follow-up 2".

### Side fix — vector `total`

벡터 채널은 엔진에 `from + size`만큼만 요구했습니다. 그래서 `total`이 "몇 건이 문턱을 넘었나"가 아니라 "몇 건 요청했나"를 그대로 반환했습니다(`size=1 → total=1`, `size=10 → total=10`). 최소 50건을 조회하도록 바꿨습니다.

관계없는 질의 다섯 개(`회 먹을 데`·`머리 자르는 곳`·`혼밥하기 좋은 집`·`브런치 먹을 곳`·`역삼동 카페`)의 건수와 상위 결과는 그대로였습니다. 엉터리 질의(`ㅁㄴㅇㄹ` 0건, `차 고치는 곳` 1건)도 변화가 없었습니다.

## Threshold follow-up 2 — filter selectivity (2026-08-01)

리뷰 #18을 반영했습니다. 앞 절의 "Open issue"가 대상입니다.

### Decision

후보가 한 건도 빠지지 않은 필터에만 문턱값을 유지합니다. 한 건이라도 빠지면 기존대로 적용하지 않습니다.

같은 질의에 필터만 바꿔 확인했습니다.

| 질의 | 필터 | 빠진 후보 | 문턱 | 결과 |
|---|---|---:|---|---:|
| `스타벅스` | 없음 | — | 적용 | 26건 |
| `스타벅스` | `sigungu=강남구` | 0건 | 적용 | 26건 |
| `스타벅스` | 반경 2000m | 39,477건 | 미적용 | 50건 |

26건은 문턱을 넘은 건수(최저 0.840), 50건은 후보 풀 전체입니다. 수선 전에는 둘째 줄도 50건이었습니다.

빠진 후보가 없으면 후보 집합이 필터 없을 때와 같습니다. 집합이 같으니 점수 분포도 같고, 그래서 측정 없이 안전을 말할 수 있습니다. 장담할 수 있는 경우는 이것뿐입니다.

### Rejected alternative

"남은 비율이 일정 기준을 넘으면 문턱값을 유지한다"도 검토했지만 다시 측정하니 성립하지 않았습니다. 강남역 기준, `scripts/eval/queries_threshold.txt`의 REAL 질의 20개, 문턱값 0.84로 측정했습니다.

| 필터 | 남은 가게 | 남은 비율 | 최저 점수 | 문턱 적용 시 0건이 될 질의 |
|---|---:|---:|---:|---:|
| 없음 | 64,239 | 1.000 | 0.844 | 0/20 |
| 반경 2000m | 24,762 | 0.385 | 0.844 | 0/20 |
| 카테고리 `과학·기술` | 18,653 | 0.290 | 0.816 | **13/20** |
| 동 `역삼1동` | 13,420 | 0.209 | 0.843 | 0/20 |
| 카테고리 `음식` | 12,578 | 0.196 | 0.813 | 7/20 |
| 반경 1000m | 10,488 | 0.163 | 0.841 | 0/20 |
| 카테고리 `소매` | 9,995 | 0.156 | 0.822 | 7/20 |
| 카테고리 `교육` | 6,218 | 0.097 | 0.812 | **16/20** |
| 반경 500m | 3,804 | 0.059 | 0.833 | 2/20 |
| 반경 150m | 472 | 0.007 | 0.815 | 10/20 |

남은 비율과 품질 저하가 비례하지 않습니다. `과학·기술`은 후보를 29% 남기고도 REAL 질의 13개를 0건으로 만듭니다. 반경 1000m는 16%만 남기고도 하나도 잃지 않습니다. 어디에 선을 그어도 카테고리 필터에서 깨집니다.

후보를 줄이는 방식이 다르기 때문입니다. 지리 필터는 업종을 고르게 남긴 채 공간만 좁히므로 의미가 맞는 후보가 집합 안에 남습니다. 카테고리 필터는 의미 축 하나를 통째로 제거합니다 — `교육`만 남은 상태에서 `세탁소`를 찾으면 가장 가까운 결과가 학원입니다. 점수 분포를 정하는 것은 얼마나 줄였는지가 아니라 어떤 의미 축을 잘랐는지이고, 비율로는 그것이 보이지 않습니다.

### Detection method

개수는 세지 않고 후보가 하나라도 빠졌는지만 확인합니다. Qdrant `points/scroll`에 필터의 여집합(`must_not`)을 걸고 `limit: 1`로 조회해, 한 건이라도 나오면 줄어든 것으로 판단합니다.

| 방법 | 실측 |
|---|---|
| 전체 개수 + 필터 개수 (2회 조회) | 10.7 + 14.5ms |
| 여집합 개수 조회 (1회) | 12.0ms |
| **여집합 1건 조회 (채택)** | **1.2ms** |

### Limitations

후보를 전혀 줄이지 않는 필터만 걸러냅니다. 의미 축을 자르는 필터에서는 문턱값이 꺼진 채로 나가므로, `교육` 카테고리에 엉터리 질의를 넣으면 여전히 결과가 나옵니다. 문턱값으로 풀 수 있는 문제가 아니라는 앞 절의 결론은 그대로입니다.

## Query admission control (2026-08-13)

### Context

「Trade-offs」에서 추론 동시 진입을 `pool-size`로 제한했습니다. 제한 자체는 `PlaceVectorSearchService`의 `Dispatchers.Default.limitedParallelism(poolSize)`과 `EmbeddingModel`의 `ArrayBlockingQueue<Predictor>` 두 겹으로 있었습니다.

그 게이트 앞의 대기열에는 상한이 없었습니다. `limitedParallelism`의 대기열은 무한입니다. 질의가 몰리면 동시 2로 처리하면서 나머지가 제한 없이 쌓입니다.

결과는 셋입니다. 지연이 상한 없이 늘어납니다. 거절이 없어 받아들일 수 없는 부하에도 계속 받습니다. 대기 중인 요청에 타임아웃이 없습니다.

### Decision

`EmbedGate`가 질의 임베딩 앞에서 대기 인원과 대기 시간에 각각 상한을 겁니다.

| 설정 | 값 | 역할 |
|---|---|---|
| `psp.embedding.gate.max-queue` | 8 | 대기 인원 상한. 초과분은 즉시 거절 |
| `psp.embedding.gate.wait-timeout` | 250ms | 대기 시간 상한. 안전장치 |

퍼밋을 즉시 받는 요청은 대기 카운터를 거치지 않습니다(`tryAcquire`). 그래서 `max-queue`가 실제 대기 인원과 일치합니다.

초과분의 처리는 경로마다 다릅니다.

| 경로 | 응답 | 근거 |
|---|---|---|
| `/v1/vsearch` | 429 + `Retry-After` | 벡터 단독 채널이라 폴백할 대상이 없습니다 |
| `/v1/hsearch` | 키워드 단독 + `degraded=true` | `HybridSearchService.runChannel`의 기존 강등 경로를 그대로 씁니다 |

두 경로 중 하나를 고를 필요가 없었습니다. 하이브리드에는 채널 실패를 강등으로 흡수하는 경로가 이미 있었고, 거절을 그 경로에 얹었습니다.

질의 벡터 캐시는 게이트 앞에 있습니다. 캐시 히트는 게이트를 타지 않습니다.

### Benchmarks

측정 환경: MacBook Air M4 16GB, 강남구 63,448건, `pool-size: 2`, 앱은 호스트 JVM. 원본은 `scripts/bench/query-gate-2026-08-13.json`입니다.

#### Measurement method

부하 생성기를 **개방 루프**로 만들었습니다(`scripts/bench/open_loop_query.py`). 응답을 기다리지 않고 고정 도착률로 주입합니다.

고정 스레드 풀(폐쇄 루프)로는 이 결정을 측정할 수 없습니다. 진행 중인 요청이 스레드 수를 넘지 못하므로 대기열 깊이도 거기서 멈춥니다. 상한이 없어도 지연이 `스레드 수 ÷ 처리율`에 수렴해 유한합니다. 상한이 막는 상황 자체가 만들어지지 않습니다.

질의는 매 요청 새로 만듭니다. 같은 질의를 돌려 쓰면 질의 벡터 캐시가 히트해 게이트를 타지 않습니다. 대신 질의에 숫자를 붙이므로 토큰이 늘어 절대 지연이 조금 높습니다.

#### Bounded vs unbounded

도착률 400/s(용량의 약 1.6배), 15초 주입, 2회 반복입니다.

| 설정 | 처리 | 거절 | p50 | p99 | 서버 대기열 최대 | 주입 후 배수 |
|---|---:|---:|---:|---:|---:|---:|
| 상한 없음 | 6,000 | 0% | 6,852ms | 10,966ms | 2,788 | 11.1초 |
| 상한 없음 (반복) | 6,000 | 0% | 6,460ms | 11,169ms | 2,730 | 11.3초 |
| 게이트 | 3,459 | 42.4% | 178ms | 297ms | 33 | 0.13초 |
| 게이트 (반복) | 3,131 | 47.8% | 200ms | 427ms | 33 | 0.20초 |

p99가 11.0초에서 0.36초로 내려갑니다. 대가는 거절 42~48%입니다.

상한이 없을 때 거절률은 0%입니다. 그런데 15초 주입이 끝난 뒤 11초를 더 처리합니다. 그 구간의 응답은 이미 떠난 사용자에게 갑니다. 거절이 0이라는 수치가 건강을 뜻하지 않습니다.

#### Rejection cost

`max-queue`와 `wait-timeout`을 격자로 재면 규칙 하나가 나옵니다.

| max-queue | wait-timeout | 처리 | 거절 | p99 | queue_full | timeout |
|---:|---:|---:|---:|---:|---:|---:|
| 32 | 250ms | 2,765 | 53.9% | 378.8ms | 3,202 | 33 |
| 32 | 100ms | **170** | 97.2% | 165.3ms | 1,365 | **4,465** |
| 32 | 500ms | 3,345 | 44.2% | 440.7ms | 2,655 | 0 |
| 8 | 250ms | 3,290 | 45.2% | 238.5ms | 2,710 | 0 |
| 128 | 250ms | **458** | 92.4% | 351.4ms | 10 | **5,532** |
| 32 | 250ms | 3,383 | 43.6% | 383.6ms | 2,614 | 3 |

타임아웃 거절이 늘면 처리량이 붕괴합니다. 두 거절의 비용이 다르기 때문입니다. `queue_full`은 즉시 거절이라 자원을 쓰지 않습니다. `timeout`은 대기열 자리를 `wait-timeout`만큼 차지한 뒤 거절됩니다. 그 자리에 들어올 수 있었던 요청이 못 들어옵니다.

대기 시간은 대략 `대기열 길이 ÷ pool-size × 서비스 시간`입니다. `max-queue: 128`이 최악인 이유가 이것입니다. 대기열이 깊어 진입에는 성공하지만 대기가 250ms를 넘어 결국 전부 타임아웃합니다.

대기 시간을 묶는 손잡이는 타임아웃이 아니라 **대기열 길이**입니다. 타임아웃은 조절기가 아니라 안전장치입니다.

첫 줄과 마지막 줄이 같은 설정입니다. p95·p99가 1% 차이입니다. 처리 건수는 22%, 거절률은 10.3%p 차이입니다. 지연 백분위는 신뢰할 수 있고 처리량·거절률은 ±10%p 잡음이 있습니다.

#### Queue length

`wait-timeout: 250ms` 고정, 도착률 두 지점입니다. `max-queue: 8`을 첫 블록과 마지막 블록에 배치했습니다.

| max-queue | 250/s p50 | 250/s p99 | 250/s 거절 | 400/s p50 | 400/s p99 | 400/s 거절 |
|---:|---:|---:|---:|---:|---:|---:|
| 4 | 48.9ms | 114.0ms | 21.0% | 58.1ms | 205.9ms | 39.1% |
| **8** | **65.2 / 65.6ms** | **132.0 / 164.5ms** | **15.4 / 12.7%** | **80.8 / 78.4ms** | **196.3 / 184.4ms** | **45.7 / 43.4%** |
| 16 | 107.0ms | 248.2ms | 13.7% | 117.6ms | 293.5ms | 37.1% |
| 32 | 185.1ms | 321.1ms | 15.9% | 185.2ms | 356.1ms | 42.6% |

지연은 대기열 길이에 거의 비례합니다. 처리량은 대기열과 무관합니다 — 250/s에서 2,962~3,272건, 400/s에서 3,256~3,775건이고 순서가 대기열 크기를 따르지 않습니다. 전 구간에서 거절은 모두 `queue_full`이고 `timeout`은 0입니다.

8이 32보다 p50을 절반 이하로, p99를 45~59% 낮춥니다. 처리량과 거절률은 잡음 안에서 같습니다. 두 도착률에서 방향이 같습니다.

`max-queue: 8`에서는 타임아웃이 걸리지 않으므로 250ms는 서비스가 느려질 때를 위한 여유로 남습니다.

### Rejected alternatives

| 후보 | 기각 이유 |
|---|---|
| `max-queue: 4` | 250/s에서 거절률이 21.0%로 8보다 5~8%p 높습니다(잡음 2.7%p). 그 대가인 p99는 114 vs 132~165ms로 작고, 400/s에서는 8보다 나쁩니다 |
| `wait-timeout: 100ms` | 대기열 32를 감당하지 못해 6,000건 중 170건만 처리했습니다 |
| `wait-timeout: 500ms` | 지금 조건에서 250ms와 구분되지 않습니다. 둘 다 타임아웃 0입니다 |
| `indexer-batch`에 백프레셔 | Spring Batch는 chunk 단위 pull이라 이미 스스로 속도가 제한됩니다 |
| Reactor `onBackpressure*` | 질의 경로는 top-N 유한 응답이라 스트림 백프레셔가 붙을 자리가 없습니다 |

### Limitations

- 벡터 채널 단일 측정입니다. 하이브리드 경로의 강등 비율은 재지 않았습니다.
- `pool-size: 2`에서 나온 값입니다. 코어 수나 `pool-size`가 바뀌면 다시 측정해야 합니다.
- 부하 창이 15초입니다. 더 긴 창에서 열이나 GC가 만드는 변화는 보지 않았습니다.
- 클라이언트가 `Retry-After`를 지키는지에 따라 거절률이 크게 달라집니다. 같은 서버 설정에서 즉시 재시도는 41.3~78.7%, `Retry-After` 존중은 6.7~9.5%였습니다. 거절률은 서버 부하만의 함수가 아닙니다.

### Measurement environment

측정 중 16GB 중 여유가 70MB까지 떨어져 스왑이 3.3GB 쌓인 구간이 있었습니다. 그 상태에서 임베딩이 3.5ms 대신 22.7ms, 모델 로딩이 2.2초 대신 7.5초였고, 같은 설정의 재실행이 2.6배씩 갈렸습니다. 위 수치는 전부 IntelliJ를 종료해 여유 1.75GB를 확보한 뒤 다시 잰 값입니다.

이 저장소의 부하 측정은 메모리 여유를 먼저 확인하고 시작해야 합니다.

## Embedding batch size (2026-08-11)

「Indexing」에서 색인 시간의 95.8%가 임베딩 추론이고 해결 방향으로 배치 크기를 지목했습니다. `psp.embedding.batch-size: 64`에는 근거가 없었습니다.

### Result

16 / 32 / 64 / 128 / 256으로 전체 재색인을 9회 실행했습니다. 이 환경의 측정으로는 배치 크기를 고르지 못합니다. 실행 순서가 만드는 차이가 배치 크기가 만드는 차이보다 큽니다.

| 비교 | 값 | 차이 |
|---|---|---|
| 같은 위치 1번째 | 배치 64 → 511.8초, 배치 256 → 501.7초 | 2.0% |
| 같은 위치 2번째 | 배치 16 → 582.2초, 배치 64 → 551.9초 | 5.2% |
| 같은 배치 256 | 위치 5에서 730.8초, 위치 1에서 501.7초 | 45.6% |
| 같은 배치 64 | 511.8 / 601.8 / 551.9초 | 17.6% |

배치가 4배 달라도 시간은 2~5% 차이입니다. 같은 배치가 실행 위치에 따라 45.6% 갈립니다. 위치 2번째 줄은 방향까지 반대로, 작은 배치가 더 느렸습니다.

순서대로 한 번씩만 돌리면 크기 순으로 단조 증가하는 표가 나옵니다. 크기 순서와 실행 순서가 같기 때문입니다. 역순 실행이 이 해석을 기각했습니다.

상주 메모리도 배치 크기와 무관합니다. 32가 1,457MB로 가장 크고 256이 1,202MB입니다.

### Decision

`psp.embedding.batch-size: 64`를 유지합니다. 바꿀 근거가 없습니다.

값을 정하려면 크기당 3회 이상, 순서 무작위, 실행 간 동일한 냉각 간격이 필요합니다. 5개 × 3회로 약 2시간 30분입니다.

원본은 `scripts/bench/embed-batch-2026-08-11.json`, 스크립트는 `scripts/bench/embed_batch_sweep.py`입니다.

### Note on comparing indexing times

ADR의 511초는 유휴 후 첫 실행에서 잰 값입니다. 같은 조건에서 511.8초로 재현됩니다. 앞으로 색인 시간을 비교할 때 이 조건을 맞춰야 합니다.

문서 수도 다릅니다. 위 「Indexing」은 64,239건, 2026-08-11 측정은 63,448건입니다. 중복 억제 791행 차이입니다.
