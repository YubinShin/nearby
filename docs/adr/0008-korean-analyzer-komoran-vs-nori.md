# ADR 0008 — 한국어 형태소 분석기: nori vs KOMORAN, 그리고 왜 플러그인으로 직접 통합하나

- **상태:** Accepted
- **날짜:** 2026-07-22
- **관련:** ADR 0002 (용도별 인덱스 분리)

## 배경 (무엇을 정해야 하나)

한국어 검색은 띄어쓰기만으로 단어를 자를 수 없어요. "강남맛집"을 그대로 색인하면 "맛집"으로
검색했을 때 안 걸려요. 그래서 문장을 **형태소(뜻을 가진 최소 단위)로 쪼개서** 색인해야 해요.
이걸 하는 게 **형태소 분석기(analyzer)** 예요.

선택지는 둘이에요.

- **(A) nori** — Elasticsearch에 **내장**된 한국어 분석기. mecab-ko-dic 사전 기반. 설치가 필요 없고 Lucene 네이티브예요.
- **(B) KOMORAN** — 순수 Java로 만든 외부 형태소 분석기. ES에 쓰려면 **커스텀 analysis 플러그인으로 감싸서** 설치해야 해요.

## 결정

**(B) KOMORAN을 택하고, ES 8.x용 커스텀 analysis 플러그인을 직접 만들어 통합한다.**

## 왜 (근거) — 실측으로 검증함

먼저 **정직하게** 짚어야 할 게 있어요. **순정 상태로는 KOMORAN이 nori보다 특별히 더 정확하지
않아요.** 둘 다 lattice + Viterbi 계열이고, 학습 안 된 신조어·외래어에서는 **둘 다 깨져요.**
로컬에서 KOMORAN(STABLE 모델)을 실제로 돌려본 결과가 이걸 보여줘요.

| 입력 | 순정 KOMORAN | 사용자 사전 한 줄 추가 후 |
|---|---|---|
| 런던베이글뮤지엄 | `런던/베이글/뮤지엄` (3조각) | **`런던베이글뮤지엄`** (고유명사 1개) |
| 성수동 **브런치** 카페 | `브/런/치` (완전 오분석) | **`브런치/NNG`** |
| **혼밥**하기 좋은 곳 | `혼/밥` | **`혼밥/NNG`** |
| **존맛탱** 파스타집 강남**맛집** | `존/맛/탱`, `강남/맛/집` | **`존맛탱`**, `강남/**맛집**` |

핵심은 오른쪽 열이에요. `place.dict`에 `브런치	NNG` **한 줄**을 넣고 `setUserDic()` 한 번
호출하니 오분석이 **즉시** 교정됐어요. 재학습도, 재빌드도, 노드 재시작도 없이 **텍스트 파일
편집만으로**요. 이게 검색 품질에 직결돼요 — 순정이면 "브런치" 질의가 색인된 `브/런/치` 토큰과
안 맞아서 **검색 누락**이 나는데, 사전 한 줄로 사라져요.

그래서 KOMORAN을 고른 진짜 이유는 "더 정확해서"가 아니라 **도메인 사전을 얼마나 쉽고 즉시
얹느냐의 자유도** 예요. 장소·음식·브랜드처럼 신조어가 끊임없이 생기는 도메인에서는 이 자유도가
정밀도를 결정해요. 구체적으로 nori 대비 이런 지점이 우위예요.

- **사용자 사전이 순수 텍스트 파일이고 즉시 반영돼요.** nori도 userdict가 있지만 복합명사
  분해(decompound) 모드와 얽혀 튜닝이 까다롭고, 반영에 재색인 성향이 강해요.
- **FW(기분석) 사전으로 결과를 강제 고정할 수 있어요.** "이 표현은 무조건 이렇게 분석하라"를
  못 박는 기능인데, nori엔 이 개념이 약해요. 도메인 오분석을 확실히 잡을 때 결정적이에요.
- **모델 자체를 도메인 코퍼스로 재학습할 수 있어요.** nori는 사전 기반이라 이 선택지가 없어요.

여기에 **조직 자산 이식성**이 더해져요. 전 직장에서는 시니어들이 KOMORAN 위에 사전·규칙
레이어를 얹은 사내 분석기(사내 분석기)를 만들어 운용했고, 그 방식을 실제로 다뤄봤어요. 즉 이
선택은 "새로 배우는 것"이 아니라 **경험한 구조를 공개 버전으로 재현**하는 거예요.

## ES 실환경 실측 (구현 후 검증)

플러그인을 ES 9.4.2에 실제로 설치하고 nori와 나란히 `_analyze` 해봤어요 (둘 다 순정, 사전 없이).

| 입력 | komoran | nori | 메모 |
|---|---|---|---|
| 성수동 브런치 | `성수동`(통짜 NNP) · `브/런/치` | `성수`+`동` · `브런치` | 엇갈림 |
| 역삼역 근처 | `역삼역`(통짜 NNP) | `역삼`+`역`(분리) | komoran 지명 강함 |
| 노티드 · 혼밥 | `노티/드`, `혼/밥` | `노티/드`, `혼/밥` | 둘 다 미등록 |

읽는 법:

- **순정은 서로 다른 걸 틀려요.** komoran은 외래어(브런치)를 박살내고, nori는 지명(성수동·역삼역)을
  쪼개요. **어느 쪽도 순정으로 완벽하지 않아요** — "순정은 도긴도긴"이라는 위 논지가 ES 실측으로
  재확인됐어요.
- **komoran은 지명 고유명사를 통짜로 인식하는 경향**이 있어요(`성수동`·`역삼역`이 NNP 하나).
  장소 검색 도메인엔 유리한 특성이에요.
- komoran의 외래어 약점은 **사전 한 줄로 메워져요**(위 로컬 실측). 결국 차이는 사전 튜닝 자유도로 수렴.
- **실용 장점:** komoran은 품사를 토큰 `type`에 그대로 노출해 `_analyze`만으로 필터링이 투명하게
  보여요. nori는 `type`이 전부 `word`라 뭐가 걸러졌는지 안 보여요. 튜닝·디버깅엔 komoran이 편해요.

## 검색 경로에서 다시 확인한 것 (4단계 실측)

실제 검색 API 를 붙여 강남구 64,239건에 질의해보니, 위 "순정의 한계"가 **검색 품질로 그대로
드러났어요.** 색인 시점엔 안 보이고 질의해봐야 보이는 것들이에요.

| 입력 | komoran 토큰 | 검색에 미치는 영향 |
|---|---|---|
| `이자카야` | `이자` + `카야` | 질의·문서가 **같은 방식으로** 쪼개져서 매칭 자체는 됨. 다만 `이자`(이자율 등)와 섞여 정밀도 손해 |
| `삼성1동` (행정동 값) | `삼성` + `1` | `삼성동` 질의가 **행정동 필드로는 안 걸림** — 지번주소(`…강남구 삼성동 159`)가 대신 받아줘서 결과적으로 검색은 됨 |
| `논현동` | `논현동` (통짜) | 정상 |

읽는 법:

- **매칭이 깨지는 조건은 "오분석"이 아니라 "질의와 문서의 분석 불일치"예요.** `이자카야`처럼 양쪽이
  똑같이 쪼개지면 검색은 됩니다. 위험한 건 `삼성동` vs `삼성1동`처럼 **문맥에 따라 다르게 쪼개지는**
  경우예요.
- 지금 이 데이터셋에서는 **지번주소가 안전망 역할**을 해요(행정동이 못 받는 걸 주소가 받음).
  주소 필드가 없는 도메인이었다면 그대로 검색 누락이었어요.
- 결론은 ADR 의 원래 논지와 같아요 — **사용자 사전이 답이고, 그게 KOMORAN 을 고른 이유**예요.
  다만 현재 재포팅한 플러그인에는 **사용자 사전 로딩 경로가 아직 없어요**(`KomoranTokenizerFactory`가
  모델만 로드). 아래 '예정'의 사전 파이프라인과 함께 플러그인에 `user_dic` 설정을 추가해야 해요.

## 정직한 트레이드오프 (택하면 떠안는 것)

- **ES 통합·운영 비용을 우리가 진다.** nori는 공짜로 얻는 걸, KOMORAN은 플러그인을 직접 만들고
  ES 버전이 오를 때마다 유지보수해야 해요.
- **shineware 공식 플러그인은 ES 7.x 대상이라 그대로 못 써요.** ES 8.x는 analysis API가 바뀌어서
  (`AbstractTokenizerFactory` 시그니처, Plugin SPI) **재포팅이 필요해요.** — 이건 부담인 동시에,
  "ES 오픈소스 내부를 이해하고 직접 개선한다"는 목표엔 오히려 잘 맞아요.
- **공식 플러그인은 Tokenizer만 있고 POS 필터가 없어요.** 조사·어미(`은/는/이/가`)까지 다
  색인돼요. **POS-stop TokenFilter를 직접 추가**해서 nori의 `nori_part_of_speech`에 해당하는
  기능을 만들어야 해요.
- **진짜 숙제는 "사전을 어디서 확보하나"예요.** 위 데모의 `place.dict`는 손으로 적은 6줄일
  뿐이에요. 실제로는 사전이 살아있게 채워지는 파이프라인이 있어야 해요 (아래 결과 참고).

## 언제였다면 (A) nori를 골랐을까

- **운영 단순함이 최우선**이고, 플러그인을 직접 유지보수할 여력이 없을 때. nori는 ES가 공식
  유지보수하니 버전 업그레이드가 안전해요.
- **범용 텍스트**가 주 대상이고 도메인 신조어 비중이 낮을 때. 이땐 사전 튜닝 자유도의 이점이 작아요.
- 복합명사 **재현율**을 `decompound_mode`로 빠르게 조절하는 게 더 중요할 때.

이 프로젝트는 장소·음식·브랜드라는 **신조어 집약 도메인**이고, "ES 내부를 직접 다뤄본다"는 것
자체가 목표라서 (B)가 더 맞아요.

## 결과 — 구현 상태

**완료 (1단계):**

- **ES 9.4.2 / lucene 10.4.0 용 KOMORAN analysis 플러그인을 별도 Gradle 모듈(`es-analysis-komoran`)로
  재포팅함.** 공식 7.x 구현 대비 ES 9.x는 analysis API가 크게 단순화돼(`AbstractTokenizerFactory(String)`
  1-인자, 4-인자 `AnalysisProvider`) 그대로는 못 쓰고 재작성함. 구성:
  `KomoranTokenizer` / `KomoranTokenizerFactory` / `KomoranPosStopTokenFilter(+Factory)` /
  `KomoranAnalysisPlugin`. 공식 7.x의 `readLine()` 첫 줄만 읽는 버그도 전체 읽기로 수정.
- **`komoran_pos_stop` TokenFilter 추가** (nori_part_of_speech 대응). lucene core `TokenFilter`를
  직접 상속해 analysis-common 의존을 피함. `stoptags` 기본값은 **공격적(콘텐츠 품사만 남김)** 으로
  실측 후 확정 — 조사·어미·접사·부호·감탄사에 더해 지정사(VCP·VCN)·보조용언(VX)·수식언(MM·MAG·MAJ)·
  의존명사(NNB)까지 제거.
- **플러그인 설치 커스텀 ES 이미지**(`deploy/elasticsearch/Dockerfile`) + 원클릭 기동(`deploy/up.sh`).
  ES 9.4.2 실기동에서 플러그인 로드·형태소 분석·POS 필터 동작 검증 완료.
- **운영 노트:** ① ES 9.x는 컨테이너가 `elasticsearch` 유저로 실행돼 root 소유 `/tmp` 파일을 못
  지움 → Dockerfile `rm` 제거. ② 설치 시 ES 9.x entitlements 경고("policy file with no additional
  entitlements") — 현재 무해하나 KOMORAN이 추가 권한을 요구하면 policy 선언이 필요할 수 있음.

**예정:**

- **사전 확보 파이프라인**을 설계해요. 사전은 세 곳에서 파생돼요:
  1. **원천 데이터(PostGIS)** — 상호명·카테고리·지역명을 사전으로 자동 추출.
  2. **검색 로그의 미매칭 질의** — 결과 0건 질의 = 신조어 후보.
  3. **공공데이터 브랜드/프랜차이즈명**.
- 사전은 색인·검색 **양쪽에서 같은 버전**을 써야 해요(불일치하면 매칭이 깨져요). 사전 갱신 시
  재색인 전략을 ADR 0002의 alias 무중단 교체와 함께 다뤄요.
- 플러그인을 설치한 **커스텀 ES 이미지**를 만들어 docker compose와 K8s에서 동일하게 써요.
