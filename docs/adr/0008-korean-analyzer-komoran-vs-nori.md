# ADR 0008 — 한국어 형태소 분석기: nori vs KOMORAN, 그리고 왜 플러그인으로 직접 통합하나

- **상태:** Accepted
- **날짜:** 2026-07-22
- **관련:** ADR 0002 (용도별 인덱스 분리)

## 배경 (무엇을 정해야 하나)

한국어 검색은 띄어쓰기만으로 단어를 자를 수 없어요. "강남맛집"을 그대로 색인하면 "맛집"으로
검색했을 때 안 걸려요. 그래서 문장을 **형태소(뜻을 가진 최소 단위)로 쪼개서** 색인해야 해요.
이걸 하는 게 **형태소 분석기(analyzer)** 예요.

선택지는 둘이에요.

- **(A) nori** — Elasticsearch에 **내장**된 한국어 분석기. mecab-ko-dic 사전 기반. 설치가 필요 없고 Lucene 네이티브예요.
- **(B) KOMORAN** — 순수 Java로 만든 외부 형태소 분석기. ES에 쓰려면 **커스텀 analysis 플러그인으로 감싸서** 설치해야 해요.

## 결정

**(B) KOMORAN을 택하고, ES 8.x용 커스텀 analysis 플러그인을 직접 만들어 통합한다.**

## 왜 (근거) — 실측으로 검증함

먼저 **정직하게** 짚어야 할 게 있어요. **순정 상태로는 KOMORAN이 nori보다 특별히 더 정확하지
않아요.** 둘 다 lattice + Viterbi 계열이고, 학습 안 된 신조어·외래어에서는 **둘 다 깨져요.**
로컬에서 KOMORAN(STABLE 모델)을 실제로 돌려본 결과가 이걸 보여줘요.

| 입력 | 순정 KOMORAN | 사용자 사전 한 줄 추가 후 |
|---|---|---|
| 런던베이글뮤지엄 | `런던/베이글/뮤지엄` (3조각) | **`런던베이글뮤지엄`** (고유명사 1개) |
| 성수동 **브런치** 카페 | `브/런/치` (완전 오분석) | **`브런치/NNG`** |
| **혼밥**하기 좋은 곳 | `혼/밥` | **`혼밥/NNG`** |
| **존맛탱** 파스타집 강남**맛집** | `존/맛/탱`, `강남/맛/집` | **`존맛탱`**, `강남/**맛집**` |

핵심은 오른쪽 열이에요. `place.dict`에 `브런치	NNG` **한 줄**을 넣고 `setUserDic()` 한 번
호출하니 오분석이 **즉시** 교정됐어요. 재학습도, 재빌드도, 노드 재시작도 없이 **텍스트 파일
편집만으로**요. 이게 검색 품질에 직결돼요 — 순정이면 "브런치" 질의가 색인된 `브/런/치` 토큰과
안 맞아서 **검색 누락**이 나는데, 사전 한 줄로 사라져요.

그래서 KOMORAN을 고른 진짜 이유는 "더 정확해서"가 아니라 **도메인 사전을 얼마나 쉽고 즉시
얹느냐의 자유도** 예요. 장소·음식·브랜드처럼 신조어가 끊임없이 생기는 도메인에서는 이 자유도가
정밀도를 결정해요. 구체적으로 nori 대비 이런 지점이 우위예요.

- **사용자 사전이 순수 텍스트 파일이고 즉시 반영돼요.** nori도 userdict가 있지만 복합명사
  분해(decompound) 모드와 얽혀 튜닝이 까다롭고, 반영에 재색인 성향이 강해요.
- **FW(기분석) 사전으로 결과를 강제 고정할 수 있어요.** "이 표현은 무조건 이렇게 분석하라"를
  못 박는 기능인데, nori엔 이 개념이 약해요. 도메인 오분석을 확실히 잡을 때 결정적이에요.
- **모델 자체를 도메인 코퍼스로 재학습할 수 있어요.** nori는 사전 기반이라 이 선택지가 없어요.

여기에 **조직 자산 이식성**이 더해져요. 전 직장에서는 시니어들이 KOMORAN 위에 사전·규칙
레이어를 얹은 사내 분석기(사내 분석기)를 만들어 운용했고, 그 방식을 실제로 다뤄봤어요. 즉 이
선택은 "새로 배우는 것"이 아니라 **경험한 구조를 공개 버전으로 재현**하는 거예요.

## ES 실환경 실측 (구현 후 검증)

플러그인을 ES 9.4.2에 실제로 설치하고 nori와 나란히 `_analyze` 해봤어요 (둘 다 순정, 사전 없이).

| 입력 | komoran | nori | 메모 |
|---|---|---|---|
| 성수동 브런치 | `성수동`(통짜 NNP) · `브/런/치` | `성수`+`동` · `브런치` | 엇갈림 |
| 역삼역 근처 | `역삼역`(통짜 NNP) | `역삼`+`역`(분리) | komoran 지명 강함 |
| 노티드 · 혼밥 | `노티/드`, `혼/밥` | `노티/드`, `혼/밥` | 둘 다 미등록 |

읽는 법:

- **순정은 서로 다른 걸 틀려요.** komoran은 외래어(브런치)를 박살내고, nori는 지명(성수동·역삼역)을
  쪼개요. **어느 쪽도 순정으로 완벽하지 않아요** — "순정은 도긴도긴"이라는 위 논지가 ES 실측으로
  재확인됐어요.
- **komoran은 지명 고유명사를 통짜로 인식하는 경향**이 있어요(`성수동`·`역삼역`이 NNP 하나).
  장소 검색 도메인엔 유리한 특성이에요.
- komoran의 외래어 약점은 **사전 한 줄로 메워져요**(위 로컬 실측). 결국 차이는 사전 튜닝 자유도로 수렴.
- **실용 장점:** komoran은 품사를 토큰 `type`에 그대로 노출해 `_analyze`만으로 필터링이 투명하게
  보여요. nori는 `type`이 전부 `word`라 뭐가 걸러졌는지 안 보여요. 튜닝·디버깅엔 komoran이 편해요.

## 검색 경로에서 다시 확인한 것 (4단계 실측)

실제 검색 API 를 붙여 강남구 64,239건에 질의해보니, 위 "순정의 한계"가 **검색 품질로 그대로
드러났어요.** 색인 시점엔 안 보이고 질의해봐야 보이는 것들이에요.

| 입력 | komoran 토큰 | 검색에 미치는 영향 |
|---|---|---|
| `이자카야` | `이자` + `카야` | 질의·문서가 **같은 방식으로** 쪼개져서 매칭 자체는 됨. 다만 `이자`(이자율 등)와 섞여 정밀도 손해 |
| `삼성1동` (행정동 값) | `삼성` + `1` | `삼성동` 질의가 **행정동 필드로는 안 걸림** — 지번주소(`…강남구 삼성동 159`)가 대신 받아줘서 결과적으로 검색은 됨 |
| `논현동` | `논현동` (통짜) | 정상 |

읽는 법:

- **매칭이 깨지는 조건은 "오분석"이 아니라 "질의와 문서의 분석 불일치"예요.** `이자카야`처럼 양쪽이
  똑같이 쪼개지면 검색은 됩니다. 위험한 건 `삼성동` vs `삼성1동`처럼 **문맥에 따라 다르게 쪼개지는**
  경우예요.
- 지금 이 데이터셋에서는 **지번주소가 안전망 역할**을 해요(행정동이 못 받는 걸 주소가 받음).
  주소 필드가 없는 도메인이었다면 그대로 검색 누락이었어요.
- 결론은 ADR 의 원래 논지와 같아요 — **사용자 사전이 답이고, 그게 KOMORAN 을 고른 이유**예요.
  → 4단계에서 플러그인에 사전 로딩 경로를 넣고 원천 기반 사전을 만들었어요 (아래 절).

## 사전을 실제로 넣어보고 알게 된 것 (4단계)

### 무엇을 사전에 넣을 것인가 — "자주 나오는 명사"가 아니다

처음 떠올린 방법은 **원천 데이터의 명사를 사전에 넣는 것**이었어요. 실측해보니 그대로 하면
검색이 **더 나빠져요.**

- **카테고리는 넣으면 안 돼요.** 245개 중 127개가 여러 토큰으로 쪼개지지만, 보면 전부 **원하는
  결과**예요 (`돼지고기 구이/찜` → 돼지고기·구이·찜). 사전에 넣어 통짜로 만들면 부분 검색이 죽어요.
- **상호명 통짜 등록은 더 나빠요.** `역삼커피로스터스`를 고유명사로 등록하면 "커피"로 못 찾아요.
- **빈도만 보고 뽑으면 쓰레기가 들어와요.** 자주 부서지는 문자열 상위가 `앤주·랩주·텍주`였는데,
  원천에서 **`주식회사`가 `주`로 절단**된 데이터 품질 문제였어요 (`더블유에프텍주`).

그래서 기준을 바꿨어요. **사전에 넣을 것은 "형태소 분석기가 *틀리게* 아는 문자열"이다.**
모르는 단어(NA)는 통짜 토큰으로 나와 오히려 안전해요. 위험한 건 오분석이에요.

판정은 기계적으로 해요 — 토큰 offset 을 보고 **한 글자짜리 토큰이 연속되는 구간**을 찾으면
그 구간은 어휘로 인식되지 못한 거예요. 이걸 `scripts/build_komoran_dict.py` 가 자동화해요.

두 가지 규칙이 품질을 좌우했어요.

1. **어휘 경계 판정.** 부서진 구간(`브런치빈`)은 어휘 경계를 몰라서 실제 어휘(`브런치`)보다 길어요.
   그래서 구간 안의 **부분문자열을 모두** 후보로 내고, *항상 더 긴 것의 일부로만 나타나는* 조각은
   버려요. `브런`은 문서빈도가 `브런치`와 같으면(= 단독으로 나온 적이 없으면) 어휘가 아니에요.
   (신조어 추출의 분기 엔트로피를 단순화한 것)
2. **최소 단위 우선.** `논현`과 `논현점`을 둘 다 넣으면 `논현점`이 통짜가 되어 **`논현` 검색을
   오히려 막아요.** 짧은 것만 채택하면 `논현점`은 논현/점 으로 알아서 쪼개져요.

결과: 강남구 64,239건에서 **1,377개** 자동 등재. 실행 15초.

### 결정적 비교 — 사전보다 POS 필터가 더 큰 문제였다

상호명 64,239건에서 **원문 글자가 색인에서 사라지는 비율**을 재봤어요.

| 구성 | 글자 유실 | 글자 불일치 |
|---|---|---|
| ① 1단계 상태 (사전X · 공격적 stoptags) | 30.81% | 34.34% |
| ② stoptags 만 완화 | 8.36% | 16.98% |
| ③ ② + 사전 1,379개 | **5.57%** | **14.36%** |
| ④ POS 필터 없음 (이론적 하한) | 0.82% | 9.23% |

> '글자 유실'은 토큰을 이어붙인 게 원문보다 짧은 경우, '글자 불일치'는 원문의 어떤 글자가 토큰
> 어디에도 없는 경우예요. 후자가 `논현 → 놓/현` 같은 **형태 변형 오분석**까지 잡아서 더 정확해요.

**사전을 먼저 넣으려 했지만, 측정해보니 피해의 대부분은 POS 필터가 만들고 있었어요.**
1단계에서 정한 공격적 `stoptags`(접사·관형사·부사·의존명사·보조용언까지 제거)는, 오분석과 만나면
원문 글자를 통째로 삼켜요. 예: 상호명 `무도` → `무/NNG + 도/JX` → 조사로 오인된 `도`가 삭제 →
그 가게는 **어떤 질의로도 못 찾아요.**

태그별 기여도(그 태그만 빼면 유실이 얼마나 주는가): **NNB 7.20%p · XPN 3.44%p · MAG 1.94%p ·
MM 1.81%p · XSN 1.55%p** — 전부 "공격적" 정책에서 추가한 것들이었어요.

**그래서 1단계의 결정을 뒤집었어요.** 플러그인 기본 `stoptags` 를 **보수적**(조사·어미·부호·감탄사만
제거)으로 바꿨어요. 색인량은 8% 늘지만 유실 12,000여 건을 되찾아요. 공격적 정책이 필요한
인덱스는 `stoptags` 로 직접 지정하면 돼요 — **안전한 쪽을 기본값으로.**

### 사전의 두 번째·세 번째 원천 — 사람이 넣는 시드와 검색 로그

`브런치`는 이 ADR 의 대표 사례인데도 자동 추출로는 안 잡혔어요. 강남구 상호명에 4번 나오는데
그중 형태소가 깨진 건 2번이라 문서빈도 임계(3)를 못 넘었어요.

이게 **원천 기반 사전의 구조적 한계**예요 — 사전은 *데이터에 있는 것*을 커버하지, *사용자가
입력하는 것*을 커버하지 않아요. "브런치"는 사용자가 치는 말이지 상호명에 자주 박히는 말이 아니거든요.

그래서 사전을 **세 층**으로 만들었어요.

| 층 | 파일 | 채우는 방법 | 규모 |
|---|---|---|---|
| 자동 추출 | `place.dict` 의 자동 구역 | 원천 코퍼스 채굴 (재생성됨) | 1,377 |
| **시드** | `manual.dict` | 사람이 판단해 등재 | 21 |
| **검색 로그** | → `manual.dict` 로 채택 | `mine_query_log.py` 가 후보 제안 | 트래픽에 비례 |

시드 등재 기준은 자동 추출과 같은 철학이에요 — **많이 넣는 게 좋은 게 아니에요.**

- ✅ 한 글자/자모로 **산산조각** 나고 조각이 무의미한 것: `브런치`→브·런·치, `크로플`→크·로·프·ㄹ
- ❌ 조각이 **그 자체로 검색어가 되는** 합성어: `스터디카페`→스터디·카페 는 **정상**이에요.
  통짜로 만들면 "카페"로 못 찾아요. (`코인노래방`·`네일아트`·`셀프세차`도 마찬가지)
- ❌ 이미 KOMORAN 이 통짜로 아는 것(`스타벅스`·`베이커리`·`삼겹살`): 생성기가 자동으로 경고해요.

> 이 두 번째 규칙은 ADR 원문의 관점을 한 번 뒤집어요. 원문은 `런던베이글뮤지엄`을 통짜 고유명사로
> 만드는 걸 성공 사례로 들었는데, **검색** 관점에선 `런던·베이글·뮤지엄` 이 오히려 나아요
> ("베이글"로 찾을 수 있어야 하니까). 형태소 분석 정확도와 검색 재현율은 같은 목표가 아니에요.

### 검색 로그 채굴 — 0건에는 두 종류가 있다

`QueryLog` 가 질의를 한 줄 JSON 으로 남기고(`logs/query.log`, logback 으로 앱 로그와 분리),
`scripts/mine_query_log.py` 가 **0건·완화 질의**에서 후보를 뽑아요. **자동 등재는 하지 않아요** —
질의엔 오타·장난·한 번 쓰고 마는 말이 섞이니 사람이 검토하고 `manual.dict` 로 옮겨요.

여기서 중요한 구분 하나. **0건 질의는 원인이 두 가지**인데 사전은 하나만 고쳐요.

- **분석 실패로 0건** — 데이터엔 있는데 못 쪼개서 못 찾음 → **사전으로 해결돼요**
- **데이터에 없어서 0건** — 사전을 아무리 넣어도 결과는 그대로 0건이에요

그래서 후보마다 원문 존재 여부를 분석과 무관한 `wildcard` 로 확인해 `[분석실패]` / `[데이터없음]`
꼬리표를 붙여요. 이걸 구분 안 하면 "사전에 넣었는데 왜 그대로죠?" 를 반복하게 돼요.

로컬 데모에서 나온 후보(`감태`·`연트럴파크`)는 전부 `[데이터없음]` 이었어요 — 강남구 원천에 없는
말이라 **채택하지 않는 게 맞아요.** 실제 트래픽이 있어야 `[분석실패]` 쪽이 쌓여요.

한 가지 더 알게 된 것: **질의와 문서가 *똑같이* 깨지면 검색은 여전히 돼요.** 현재 분석기로도
글자가 사라지는 상호가 표본 6,000건 중 519건 있는데, 그 이름으로 검색하면 정상적으로 찾아져요
(`샤론스톤`→샤론·스토·ㄴ 이 양쪽 모두). 손해는 *못 찾는 것*이 아니라 *정밀도*예요 —
조각이 엉뚱한 문서와도 겹치거든요.

## 정직한 트레이드오프 (택하면 떠안는 것)

- **ES 통합·운영 비용을 우리가 진다.** nori는 공짜로 얻는 걸, KOMORAN은 플러그인을 직접 만들고
  ES 버전이 오를 때마다 유지보수해야 해요.
- **shineware 공식 플러그인은 ES 7.x 대상이라 그대로 못 써요.** ES 8.x는 analysis API가 바뀌어서
  (`AbstractTokenizerFactory` 시그니처, Plugin SPI) **재포팅이 필요해요.** — 이건 부담인 동시에,
  "ES 오픈소스 내부를 이해하고 직접 개선한다"는 목표엔 오히려 잘 맞아요.
- **공식 플러그인은 Tokenizer만 있고 POS 필터가 없어요.** 조사·어미(`은/는/이/가`)까지 다
  색인돼요. **POS-stop TokenFilter를 직접 추가**해서 nori의 `nori_part_of_speech`에 해당하는
  기능을 만들어야 해요.
- **진짜 숙제는 "사전을 어디서 확보하나"예요.** 위 데모의 `place.dict`는 손으로 적은 6줄일
  뿐이에요. 실제로는 사전이 살아있게 채워지는 파이프라인이 있어야 해요 (아래 결과 참고).

## 언제였다면 (A) nori를 골랐을까

- **운영 단순함이 최우선**이고, 플러그인을 직접 유지보수할 여력이 없을 때. nori는 ES가 공식
  유지보수하니 버전 업그레이드가 안전해요.
- **범용 텍스트**가 주 대상이고 도메인 신조어 비중이 낮을 때. 이땐 사전 튜닝 자유도의 이점이 작아요.
- 복합명사 **재현율**을 `decompound_mode`로 빠르게 조절하는 게 더 중요할 때.

이 프로젝트는 장소·음식·브랜드라는 **신조어 집약 도메인**이고, "ES 내부를 직접 다뤄본다"는 것
자체가 목표라서 (B)가 더 맞아요.

## 결과 — 구현 상태

**완료 (1단계):**

- **ES 9.4.2 / lucene 10.4.0 용 KOMORAN analysis 플러그인을 별도 Gradle 모듈(`es-analysis-komoran`)로
  재포팅함.** 공식 7.x 구현 대비 ES 9.x는 analysis API가 크게 단순화돼(`AbstractTokenizerFactory(String)`
  1-인자, 4-인자 `AnalysisProvider`) 그대로는 못 쓰고 재작성함. 구성:
  `KomoranTokenizer` / `KomoranTokenizerFactory` / `KomoranPosStopTokenFilter(+Factory)` /
  `KomoranAnalysisPlugin`. 공식 7.x의 `readLine()` 첫 줄만 읽는 버그도 전체 읽기로 수정.
- **`komoran_pos_stop` TokenFilter 추가** (nori_part_of_speech 대응). lucene core `TokenFilter`를
  직접 상속해 analysis-common 의존을 피함. `stoptags` 기본값은 1단계에 **공격적(콘텐츠 품사만 남김)**
  으로 정했다가, **4단계 실측으로 보수적(조사·어미·부호·감탄사)으로 되돌림** — 위 절 참고.

**완료 (4단계):**

- **사용자 사전 로딩 경로 추가.** `komoran_tokenizer` 에 `user_dictionary` · `fw_dictionary` 설정
  (ES config 디렉토리 기준 상대경로, 경로 탈출 차단). 설정했는데 파일이 없으면 **기동을 실패**시킨다 —
  사전이 조용히 무시되면 색인과 검색이 서로 다른 사전을 보게 되고, 그게 가장 잡기 어려운 장애다.
- **원천 기반 사전 생성기** `scripts/build_komoran_dict.py`. 사전은 이미지에 굽지 않고
  `deploy/elasticsearch/analysis/` 를 마운트 — 원천에서 **생성되는 산출물**이라 자주 바뀌기 때문.
- **운영 노트:** `_analyze` 에 tokenizer 를 즉석 지정하면 호출마다 KOMORAN 모델(5MB)을 새로 로딩한다
  (실측 **7 req/s**). 인덱스 설정에 두면 팩토리가 인덱스당 한 번 만들어져 캐시된다(**3,133 req/s**).
  6만 건 분석 도구를 만들 때 이 차이가 곧 실행 가능/불가능이었다.
- **플러그인 설치 커스텀 ES 이미지**(`deploy/elasticsearch/Dockerfile`) + 원클릭 기동(`deploy/up.sh`).
  ES 9.4.2 실기동에서 플러그인 로드·형태소 분석·POS 필터 동작 검증 완료.
- **운영 노트:** ① ES 9.x는 컨테이너가 `elasticsearch` 유저로 실행돼 root 소유 `/tmp` 파일을 못
  지움 → Dockerfile `rm` 제거. ② 설치 시 ES 9.x entitlements 경고("policy file with no additional
  entitlements") — 현재 무해하나 KOMORAN이 추가 권한을 요구하면 policy 선언이 필요할 수 있음.

**예정:**

- 사전은 세 곳에서 파생돼요. **1번만 구현했어요.**
  1. ✅ **원천 데이터(PostGIS)** — 오분석 구간에서 자동 추출 (`scripts/build_komoran_dict.py`).
  2. ✅ **검색 로그의 미매칭 질의** — `QueryLog` + `scripts/mine_query_log.py`.
     후보 제안까지 자동, **채택은 사람이** (위 절 참고). 실제 트래픽이 쌓여야 값어치가 나와요.
  3. 📝 **공공데이터 브랜드/프랜차이즈명** — 원천에 프랜차이즈 직영점이 누락돼 있어요
     (강남구 데이터에 '스타벅스' 상호가 0건). 별도 목록이 필요해요. 지금은 자주 쓰는 몇 개만
     `manual.dict` 에 손으로 넣어뒀어요.
- **기분석 사전(FW)은 경로만 열어두고 아직 안 써요.** 사용자 사전으로 안 잡히는 문맥 의존
  오분석에 쓸 자리인데, 지금은 그만큼의 사례가 확인되지 않았어요.
- 사전은 색인·검색 **양쪽에서 같은 버전**을 써야 해요(불일치하면 매칭이 조용히 깨져요).
  현재는 사전을 바꾸면 **전체 재색인**이 필요해요 — alias 무중단 교체(ADR 0002)로 처리하지만,

- 플러그인을 설치한 **커스텀 ES 이미지**를 만들어 docker compose와 K8s에서 동일하게 써요.
