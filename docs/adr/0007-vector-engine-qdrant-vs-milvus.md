# ADR 0007 — 벡터 엔진으로 별도 엔진 Qdrant 를 선택

- **상태:** Accepted
- **날짜:** 2026-07-20
- **관련:** ADR 0002 (용도별 분리), ADR 0003 (하이브리드 검색 · 앱단 RRF 결합)

## Context

이 서비스는 "뜻으로 찾기"를 합니다. 문장을 숫자 벡터로 바꿔 의미가 비슷한 장소를 찾는 방식입니다. 결정은 두 단계입니다.

1. **먼저:** 벡터 검색을 ES 안에서 할 것인가(내장), 별도 벡터 엔진을 둘 것인가?
2. **그다음:** 별도 엔진을 둔다면 무엇을 쓸 것인가 — Qdrant vs Milvus?

## Stage 1 decision — Dedicated engine over ES built-in

ES도 벡터 검색을 합니다. `dense_vector` 필드에 HNSW로 근사 kNN 검색을 합니다. BM25와 하이브리드도 됩니다. 양자화(int8·int4·이진 양자화)까지 붙어 빠르게 발전하고 있습니다. 이 프로젝트 규모(수만~수십만 장소)에서는 ES 내장 벡터만으로도 기능적으로 충분합니다.

그럼에도 별도 엔진(Qdrant)을 둔 것은 "ES가 못해서"가 아니라 다음을 위해서입니다.

- **아키텍처 증명** — 목표가 "별도 벡터 엔진 + ES를 조합한 하이브리드 검색"을 직접 설계해 보는 것입니다. 규모가 커졌을 때 실제로 쓰이는 구조이므로, 그 구조를 손으로 만들어 보는 것 자체가 목적입니다.
- **판단 기준의 이해** — "언제 전용 엔진으로 넘어가야 하는가"를 아는 것이 핵심입니다. 전용 엔진이 푸는 문제는 다음과 같습니다(=규모가 커지면 ES 내장이 부담스러워지는 지점).
  - **메모리·규모** — HNSW는 빠르려면 그래프가 RAM에 있어야 합니다. 벡터가 수억~수십억이 되면 JVM/Lucene 위의 ES는 메모리·비용이 부담입니다. 전용 엔진은 압축·디스크 기반으로 더 많은 벡터를 담습니다.
  - **자원 격리** — 벡터 검색은 메모리·CPU 소모가 큽니다. ES 클러스터 안에 큰 벡터 인덱스를 같이 넣으면 키워드 검색(BM25)과 자원 경쟁이 생깁니다. 분리하면 서로 영향을 주지 않습니다. (ADR 0002의 "성격 다른 워크로드는 한 곳에 섞지 않는다"와 같은 논리입니다.)
  - **필터링된 벡터 검색** — "카페면서 영업 중인 것 중 의미가 가장 비슷한 곳"처럼 필터+ANN을 동시에 잘하는 것은 어려운 문제이고, 전용 엔진이 여기에 집중 투자합니다.

## Stage 2 decision — Qdrant vs Milvus

Qdrant를 택합니다.

- **Qdrant는 경량.** Rust로 만든 단일 엔진이라 컨테이너 하나로 기동합니다. 노트북(M4 16GB)에서 ES·Redis(예정)·PostGIS와 함께 실행하기 좋고, 중소 규모와 빠른 개발에 최적입니다.
- **Milvus는 대규모 전용.** 처음부터 수십억 벡터를 분산으로 다루도록 설계되어, etcd·오브젝트 스토리지·로그 브로커(Pulsar/Kafka) 같은 부속이 함께 필요합니다. 강력하지만 무겁고 운영이 복잡합니다. 이 프로젝트 규모에는 과합니다.
- **두 엔진 모두 같은 HNSW 원리.** 한쪽으로 원리를 익히면 개념이 그대로 이식됩니다.

## Rust runtime benefits

오픈소스 Rust 프로젝트라 HNSW 인덱스·세그먼트·메모리 매핑(mmap) 같은 내부 구현을 직접 열어볼 수 있습니다. GC나 JVM 힙 튜닝 부담이 없습니다.

## Revisit conditions

- **ES 내장으로 갔을 경우** — 운영을 한 시스템으로 단순하게 유지하는 것이 최우선이고, 벡터 규모가 중간 이하라면 별도 엔진 없이 ES 내장 벡터로 가는 것이 합리적입니다.
- **Milvus로 갔을 경우** — 수십억 규모의 벡터를 여러 노드에 분산해 대규모로 서빙해야 한다면 Milvus의 compute/storage 분리 구조가 유리합니다.

## Step 5 benchmarks (2026-07-23)

"컨테이너 하나로 기동한다"는 기대와 "이 규모엔 ES 내장으로도 충분하다"는 단서 모두 실측으로 확인했습니다.

| 항목 | 실측 |
|---|---|
| 컬렉션 | `place_vec_v{n}` · 64,239점 · 384차원 · Cosine · HNSW(m=16, ef_construct=100) |
| 색인 | 8분 33초 (병목은 Qdrant가 아니라 **임베딩 추론** — ADR 0010) |
| 질의 | ANN 탐색 **3.6ms** (hnsw_ef=128, 상위 10) |
| 필터 | payload 인덱스로 엔진 안에서 처리 — 행정동 필터 결과 100% 일치, 반경 300m 요청 시 최대 거리 275m |

**얻은 것 — 예상대로:**
- **ES와 같은 alias 스왑 패턴.** `POST /collections/aliases`의 액션 목록이 원자적이라 "가리키는 곳이 없는 순간"이 없습니다. 20회 왕복 스왑 중 검색 230회 **실패 0**으로 확인했습니다. 벡터 엔진이 달라도 **인덱스 생명주기 규약**은 하나로 유지된다는 것이 이 아키텍처의 실질적 이득이었습니다.
- **필터+ANN 동시 적용.**

**부딪힌 것 — 문서에 없던 것:**
- **점 id 제약.** Qdrant의 id는 부호 없는 정수이거나 UUID입니다. 문자열 `place_id`를 그대로 사용할 수 없어 결정적 UUID 변환이 필요했습니다(멱등성 유지). ES가 임의 문자열 `_id`를 받는 것과 다릅니다.
- **REST 경로의 비대칭.** alias **조회**는 `GET /aliases`, **변경**은 `POST /collections/aliases`. 혼동해 8분짜리 적재를 한 번 폐기했습니다 (아키텍처 리뷰 #16).

**규모 판단 유지.** 6만 건에서 ANN 3.6ms는 ES 내장 `dense_vector`로도 충분히 나올 수치입니다.

## Consequences

- 개념(HNSW·필터링·하이브리드)이 이식 가능하므로, 규모가 커지면 Milvus로 전환하는 선택지를 열어둡니다.
- 벡터 검색 결과는 키워드 검색(ES)과 애플리케이션 레이어에서 RRF로 결합합니다 (ADR 0003).
