# ADR 0007 — 벡터 엔진 선택: ES 내장 vs 별도 엔진, 그리고 Qdrant vs Milvus

- **상태:** Accepted
- **날짜:** 2026-07-20
- **관련:** ADR 0002 (용도별 분리), ADR 0003 (하이브리드 검색 · 앱단 RRF 결합)

## 배경 (무엇을 정해야 하나)

이 서비스는 "뜻으로 찾기"를 해요. 문장을 숫자 묶음(벡터)으로 바꿔서 의미가 비슷한 장소를 찾는
거예요. 결정할 게 두 단계예요.

1. **먼저:** 벡터 검색을 ES 안에서 할까(내장), 아니면 별도 벡터 엔진을 둘까?
2. **그다음:** 별도 엔진을 둔다면 어떤 걸 쓸까 — Qdrant vs Milvus?

## 1단계 결정 — 왜 ES 내장이 아니라 별도 엔진인가

먼저 정직하게 짚어둘 게 있어요. **ES도 벡터 검색을 해요.** `dense_vector` 필드에 HNSW로 근사
kNN 검색을 하고, BM25와 하이브리드도 되고, 양자화(int8·int4·이진 양자화)까지 붙어서 빠르게
좋아지고 있어요. **이 프로젝트 규모(수만~수십만 장소)에선 ES 내장 벡터만으로도 기능적으로 충분해요.**

그런데도 별도 엔진(Qdrant)을 둔 건 "ES가 못해서"가 아니라 다음을 위해서예요.

- **아키텍처 증명** — 목표가 "별도 벡터 엔진 + ES를 조합한 하이브리드 검색"을 직접 설계해보는 것이에요.
  이건 규모가 커졌을 때 실제로 쓰이는 구조라, 그 구조를 손으로 만들어보는 것 자체가 목적이에요.
- **판단 기준의 이해** — "언제 전용 엔진으로 넘어가야 하는가"를 아는 게 핵심이에요. 전용 엔진이
  푸는 문제는 이런 것들이에요(=규모가 커지면 ES 내장이 부담스러워지는 지점):
  - **메모리·규모** — HNSW는 빠르려면 그래프가 RAM에 있어야 해요. 벡터가 수억~수십억이 되면
    JVM/Lucene 위의 ES는 메모리·비용이 부담돼요. 전용 엔진은 압축·디스크 기반으로 더 많은 벡터를 담아요.
  - **자원 격리** — 벡터 검색은 메모리·CPU를 많이 먹어요. ES 클러스터 안에 큰 벡터 인덱스를 같이
    넣으면 키워드 검색(BM25)과 자원을 두고 싸워요. 떼어내면 서로 안 흔들려요.
    (**ADR 0002의 "성격 다른 워크로드는 한 통에 안 섞는다"와 같은 논리예요.**)
  - **필터링된 벡터 검색** — "카페면서 영업 중인 것 중 의미가 가장 비슷한 곳"처럼 필터+ANN을
    동시에 잘하는 건 어려운 문제인데, 전용 엔진이 여기에 많이 투자해요.

> 정직한 한 줄 정리: *"이 규모엔 ES 내장으로도 충분하다. 별도 엔진은 ES가 못해서가 아니라,
> 하이브리드 아키텍처를 증명하고 '언제 전용 엔진이 필요한지'의 판단을 보여주려고 택했다."*

## 2단계 결정 — Qdrant vs Milvus

**Qdrant를 택한다.**

- **Qdrant는 가벼워요.** Rust로 만든 단일 엔진이라 컨테이너 하나면 떠요. 노트북(M4 16GB)에서
  ES·Redis·PostGIS와 함께 돌리기 좋고, 중소 규모와 빠른 개발에 최적이에요.
- **Milvus는 대규모 전용이에요.** 처음부터 수십억 벡터를 분산으로 다루도록 설계돼서,
  etcd·오브젝트 스토리지·로그 브로커(Pulsar/Kafka) 같은 부속이 줄줄이 붙어요. 강력하지만 무겁고
  운영이 복잡해요. 이 프로젝트 규모엔 과해요.
- **둘 다 HNSW라는 같은 원리로 동작해요.** 한쪽으로 원리를 익히면 개념이 그대로 이식돼요.

## Rust라는 추가 이점 (솔직한 강점)

Qdrant는 오픈소스 Rust 프로젝트예요. Rust를 읽을 수 있으면 **HNSW 인덱스·세그먼트·메모리
매핑(mmap) 같은 내부 구현을 직접 열어볼 수 있어요.** 대부분의 엔지니어는 벡터 엔진의 소스를
못 읽는데, 이건 "검색 엔진 오픈소스를 깊이 이해하고 내부 구조를 분석해본" 경험으로 직접 이어져요.
(참고: Rust 기반이라 GC나 JVM 힙 튜닝 같은 문제가 없어요. ES를 괴롭히는 그 부담이 여기선 아예 없어요.)

## 언제였다면 다른 선택을 했을까

- **ES 내장으로 갔을 경우** — 운영을 한 시스템으로 단순하게 유지하는 게 최우선이고, 벡터 규모가
  중간 이하라면 별도 엔진 없이 ES 내장 벡터로 가는 게 합리적이에요.
- **Milvus로 갔을 경우** — 수십억 규모의 벡터를 여러 노드에 분산해 대규모로 서빙해야 한다면
  Milvus의 compute/storage 분리 구조가 유리해요. 대형 프로덕션이 그런 경우예요.

## 5단계 실측 (2026-07-23 추가)

실제로 만들어보고 확인한 것들. **컨테이너 하나로 뜬다**는 기대는 그대로 맞았고,
"이 규모엔 ES 내장으로도 충분하다"는 위의 정직한 단서도 그대로 유효하다.

| 항목 | 실측 |
|---|---|
| 컬렉션 | `place_vec_v{n}` · 64,239점 · 384차원 · Cosine · HNSW(m=16, ef_construct=100) |
| 색인 | 8분 33초 (병목은 Qdrant 가 아니라 **임베딩 추론** — ADR 0010) |
| 질의 | ANN 탐색 **3.6ms** (hnsw_ef=128, 상위 10) |
| 필터 | payload 인덱스로 **엔진 안에서** 처리 — 행정동 필터 결과 100% 일치, 반경 300m 요청 시 최대 거리 275m |

**얻은 것 — 예상대로:**
- **alias 스왑이 ES와 같은 패턴으로 성립한다.** `POST /collections/aliases` 의 액션 목록이
  원자적이라 "가리키는 곳이 없는 순간"이 없다 — 20회 왕복 스왑 중 검색 230회 **실패 0**으로 확인했다. 벡터 엔진이 달라도 **인덱스 생명주기 규약은 하나**로
  유지된다는 게 이 아키텍처의 실질적 이득이었다.
- **필터+ANN이 실제로 같이 걸린다.** ADR 작성 시점에 "전용 엔진이 여기 투자한다"고 적었던
  그 기능을 그대로 썼다.

**부딪힌 것 — 문서에 없던 것:**
- **점 id 제약.** Qdrant 의 id 는 부호 없는 정수이거나 UUID 다. 문자열 `place_id` 를 그대로
  못 써서 결정적 UUID 변환이 필요했다(멱등성 유지). ES 가 임의 문자열 `_id` 를 받는 것과 다르다.
- **REST 경로의 비대칭.** alias **조회**는 `GET /aliases`, **변경**은 `POST /collections/aliases`.
  헷갈려서 8분짜리 적재를 한 번 날렸다 (크리틱 #16).

**규모 판단은 그대로다.** 6만 건에서 ANN 3.6ms 는 ES 내장 `dense_vector` 로도 충분히 나올
수치다. 이 선택의 값은 성능이 아니라 **"두 엔진을 조합하는 구조를 손으로 만들어 봤다"** 는 것이고,
그건 이 ADR이 처음부터 밝힌 이유와 같다.

## 결과

- 개념(HNSW·필터링·하이브리드)이 이식 가능하므로, 규모가 커지면 Milvus로 전환하는 선택지를 열어둬요.
  되돌릴 수 없는 결정이 아니에요.
- 벡터 검색 결과는 키워드 검색(ES)과 애플리케이션 레이어에서 RRF로 결합해요 (ADR 0003).
