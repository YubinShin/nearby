# ADR 0011 — 색인기와 질의기를 별도 아티팩트로 쪼개고, 색인 계약을 런타임에 대조한다

- **상태:** Accepted
- **날짜:** 2026-07-24
- **관련:** ADR 0002 (용도별 인덱스·클러스터 분리), ADR 0010 (임베딩 모델과 추론 위치 — *이 결정이 깨뜨리는 보호*), ADR 0001 (이벤트 트리거 증분), ADR 0008 (형태소 사전 — *같은 함정의 첫 얼굴*)
- **닫는 셀프 크리틱:** #5(부분 → 완전), #14, #15

## 배경 (무엇을 정해야 하나)

`search-api` 하나가 쓰기(색인)와 읽기(질의)를 겸했다. 4단계에서 `psp.role.indexer` /
`psp.role.query` **런타임 플래그**를 붙여 "같은 아티팩트를 두 역할로 나눠 띄우는 것"까지는
했다(#5). 하지만 나눠 띄워도 **한 아티팩트라는 사실**은 그대로다.

문제는 두 가지다.

1. **폭발 반경.** 실무에서 실시간 색인 컨슈머가 월 최대 14건 OOMKilled 났다. 그게 검색 API와
   같은 프로세스였다면 그 14번이 전부 **검색 장애**였다. 플래그로 빈을 꺼도 힙은 공유한다.
2. **자원 성격이 반대.** 색인은 CPU 버스트다 — 벡터 전체 재색인 492초 중 **471초(95.7%)가
   임베딩 추론**이다. 질의는 저지연 상시 대기다(하이브리드 중앙값 8.2ms). 한 프로세스에
   묶으면 색인이 도는 동안 질의가 코어를 빼앗긴다.

플래그에는 세 번째 문제도 있다. **잘못 켜면 열린다.** `psp.role.indexer=true` 가 실수로 켜지면
질의 노드에 `POST /admin/reindex` 가 노출된다. 사람이 실수할 여지가 남아 있다.

## 결정 1 — 모듈을 넷으로 쪼갠다

```
search-api  ──┐
              ├──▶  search-core  (라이브러리)
indexer-batch ┘
indexer-stream  (뼈대만)
```

| 모듈 | 무엇 | 패키지 |
|---|---|---|
| **search-core** (lib) | 두 앱이 어긋나면 **조용히 망가지는 것** | `dev.yubin.search.core.*` |
| **search-api** (app) | `/v1/*` 질의. `/admin` 없음, PostGIS 없음 | `dev.yubin.search.*` (그대로) |
| **indexer-batch** (app) | `/admin/*`, ES bulk, 체크포인트, PostGIS R2DBC | `dev.yubin.search.indexer.*` |
| **indexer-stream** | 비어 있음 (아래 참조) | `dev.yubin.search.indexer.stream` |

### 무엇을 core 에 넣을지 — 기준을 좁게 잡았다

"둘 다 쓰니까 core" 로 하면 core 가 금방 쓰레기통이 된다. 기준은 하나다.

> **한쪽만 바꿨을 때 프로그램이 죽지 않고 결과만 이상해지는 것** → core

| 어긋나면 | 어떻게 되나 | core? |
|---|---|---|
| 색인은 `brand`, 질의는 `brand_name` | 예외 없음. 브랜드가 안 보인다 | ✅ |
| 색인은 A모델, 질의는 B모델 | 예외 없음. 점수가 의미를 잃는다 | ✅ |
| RRF 상수 `k` | 질의기만의 문제 | ❌ |

그래서 `Brands`·`PlaceRow`·`PlaceDocuments`·`PlaceEsDocs`·`EmbeddingModel`·`PlaceVectorText`·
`QdrantStore`·`PlaceVectorPayload`·`IndexMeta` 가 core 다.

**`PlaceDocuments`(필드명을 쓰는 쪽)와 `PlaceEsDocs`(같은 필드명을 읽는 쪽)를 같은 폴더에** 뒀다.
`PlaceEsDocs` 주석에 원래부터 "색인된 스키마와 1:1" 이라고 적혀 있었다. 말로 적는 것보다
나란히 두는 편이 강한 약속이다.

`PlaceVectors` 는 쪼갰다 — `payload()` 는 Qdrant 문서 스키마라 core, `filter()`·`distanceM()` 은
질의 규칙이라 search-api. 덤으로 **core 가 `SearchRequest`(질의 개념)를 몰라도 되게** 됐다.

> 경계가 맞다는 신호: 크리틱 #21 회귀 테스트("색인 문서·임베딩 문장·payload 가 같은 브랜드를
> 쓴다")가 검사하는 세 경로가 옮기고 보니 **전부 core 안에** 있었다.

### 왜 `search-core` 이고, `indexer-core` 는 왜 지금 없나

공유 모듈 이름이 `indexer-core` 면 질의 앱이 "indexer-core" 에 의존하는 그림이 되어 리뷰어에게
잘못 읽힌다. `indexer-core` 는 **색인기가 둘이 됐을 때** 추출한다 — 그때 비로소 둘이 공유하는
것(bulk 적용·체크포인트·멱등 규칙)이 눈에 보인다. 지금 만들면 무엇을 공유할지 **코드 없이
추측**하는 꼴이라 두 번 틀린다.

### `indexer-stream` — 이름과, 비어 있는 이유

`indexer-batch` 와 갈리는 축은 **일이 어떻게 도착하느냐**다(스케줄 vs 이벤트).

- **`-incremental` 은 틀렸다.** `indexer-batch` 가 이미 `CheckpointStore` 기반 증분이다.
- **`-realtime` 은 ADR 0001 과 어긋난다.** 거기서 실시간을 기각하고 이벤트 트리거를 골랐다.
- **`batch ↔ stream`** 은 설명 없이 읽히는 축이다.

YAGNI 대로면 디렉토리 자체가 없어야 맞다. 그걸 알면서 남기는 이유는 **`indexer-batch` 라는
이름이 짝이 있을 때만 의미가 있기** 때문이다. 대신 **동작하는 척하는 코드는 넣지 않는다** —
Spring Boot 플러그인도 붙이지 않았다. 뜨기만 하고 아무것도 안 하는 앱은 뼈대가 아니라 거짓말이다.

## 결정 2 — `psp.role.*` 플래그를 전부 제거한다

모듈이 곧 역할이다. 12개 클래스의 `@ConditionalOnProperty(prefix = "psp.role")` 를 지웠다.
(무엇을 어디로 옮길지는 그 어노테이션이 이미 답을 갖고 있었다 — 분류가 아니라 **승격**이다.)

플래그와 다른 점은 **클래스가 아예 없다**는 것이다. jar 로 확인했다.

```
search-api.jar    r2dbc/postgresql 0개 · indexer/Admin 0개
indexer-batch.jar r2dbc/postgresql 9개
```

질의 앱이 원천 창고를 열 방법 **자체가 없다.**

`psp.vector.enabled` 는 남긴다. 임베딩 모델을 읽을지 말지는 여전히 런타임 선택이다(ADR 0010).

## 결정 3 — 어긋나면 안 되는 설정은 `core.yml` 한 곳에

`application.yml` 을 그냥 반으로 잘라 복사하면, 이 값들이 한쪽만 바뀌는 사고가 언젠가 난다.

```yaml
psp.index.search-alias   # 색인기가 채우고 질의기가 읽는 같은 이름
psp.vector.alias
psp.embedding.*          # 같은 모델·같은 전처리 (ADR 0010)
spring.elasticsearch.uris
```

그리고 그 사고는 **예외를 던지지 않는다.** 색인기는 `place_search_v9` 를 채우고 질의기는 `v8` 을
읽는데 로그는 깨끗하고 결과만 낡는다. 코드를 core 에 모은 것과 **같은 이유로** 설정도 한 벌만 둔다.
두 앱은 `spring.config.import: classpath:core.yml` 로 읽는다.

## 결정 4 — 런타임 버전 도장 (`IndexMeta`) — **이 분리의 필수 조건**

### 무엇을 잃었나

ADR 0010 이 노린 보호("색인과 질의가 같은 모델·같은 전처리")는 **한 프로세스였기에 코드로
강제**됐다. 쪼개면 그 보호가 사라진다. `search-core` 를 공유하는 건 **한 빌드 안에서만**
드리프트를 막고, 따로 배포된 두 아티팩트는 여전히 어긋날 수 있다(롤링 배포·배포 실패·롤백).

그 어긋남은 증상이 없다. 384차원끼리면 유사도 계산은 멀쩡히 되고 숫자도 그럴싸하다.
로그도 깨끗하고 헬스체크도 초록이다. **결과만 조용히 틀린다.**

### 설계

- **indexer-batch 가 찍는다** — alias 스왑이 **성공한 뒤에.** 순서가 중요하다. 스왑 전에 찍으면
  적재가 실패했을 때 "새 스키마로 색인됐다"는 거짓말이 남는다.
- 도장 값은 설정이 아니라 **실제로 로드된 모델**에서 읽는다(`EmbeddingModel.modelId`/`dimension`).
  설정은 "그럴 것이다"이고 로드된 모델은 "그렇다"라, 설정만 맞고 파일이 다른 경우까지 잡힌다.
- **search-api 가 기동 시 대조한다.** 다르면 **컨텍스트가 뜨지 않는다.**
- **도장이 없으면 경고만.** 분리 이전에 만든 인덱스로도 뜰 수 있어야 한다.
  **"모르는 것"과 "다른 것"을 구분한다.**

### 왜 경고가 아니라 기동 실패인가

경고면 로그 한 줄 지나가고 서비스는 계속 돈다. 품질이 나빠진 걸 누군가 알아채기까지 며칠이 걸린다.
안 뜨면 배포가 그 자리에서 실패한다. **조용히 틀리는 것보다 시끄럽게 실패하는 쪽이 낫다.**

### 도장을 왜 ES 문서에 두나 — Qdrant 는 안 됐다

원래는 Qdrant 컬렉션 메타에 붙이려 했다(#15 가 적어둔 방향이다). 확인해보니 **Qdrant 1.12 는
모르는 필드를 오류 없이 조용히 버린다.**

```
PUT /collections/probe  {"vectors":{...}, "metadata":{"x":"1"}}  →  {"result":true,"status":"ok"}
GET /collections/probe                                           →  metadata 없음
```

**하필 이 기능이 막으려는 바로 그 실패 방식이다.** 추측했다면 "도장을 찍었다"고 믿으면서 아무것도
안 찍혔을 것이다. 그래서 ES·Qdrant 양쪽 도장을 ES 문서 한 곳(`psp_index_meta`)에 모았다.

### 트레이드오프 — 모델을 다 읽은 뒤에 검사한다

기동 실패 경로에서 임베딩 모델 로딩 5.6초·0.5GB 를 버린다. 벡터 계약을 대조하려면 "설정에
뭐라고 적혀 있나"가 아니라 **실제로 로드된 모델이 무엇인가**가 필요해서다. 오탐을 줄이는 값으로
크래시루프 시 기동 시간을 지불한다.

## 결정 5 — 증분 색인은 계약이 다르면 **거부한다**

증분은 새 인덱스를 만들지 않고 **살아있는 인덱스에 덮어쓴다.** 그래서 모델이 바뀐 채 증분을
돌리면 한 컬렉션에 두 모델의 벡터가 **섞인다.**

```
1. 모델 A 로 전체 재색인   → 64,239건 전부 A
2. 모델 B 로 색인기 재배포
3. 증분 실행              → 바뀐 500건만 B
   → A 63,739 + B 500 섞임. 도장은 여전히 A
```

대응은 둘이다. **감지**(문서마다 `meta` 를 남겨 사후 확인)와 **차단**(증분 전에 도장을 대조하고
거부). **차단을 골랐다** — 섞인 걸 나중에 아는 것보다 애초에 못 섞이게 하는 편이 싸다.
비용은 GET 한 번이고, 문서당 저장 오버헤드가 0이다.

## 결정 6 — 색인 주기를 세 층으로 나눈다

도장은 **담기로 한 것**만 지킨다. 담지 않은 어긋남은 그대로 쌓인다.

- **형태소 사전 변경** — 질의 로그 채굴로 계속 자란다(ADR 0008). 증분은 바뀐 행만 건드리므로
  나머지는 옛 분석 결과로 남는다.
- **원천이 `updated_at` 을 안 올리고 값만 고친 경우** — watermark 기반 증분은 영영 못 본다.
- **tombstone** — 전체 재색인이 곧 청소다.

이건 도장으로 못 막는다. **주기적 전체 재색인이 쓸어내야** 한다.

| 무엇 | 주기 | 무엇이 정하나 |
|---|---|---|
| 증분 | 5분 | 신선도 요구 ↔ 변경량. 장소는 느리게 바뀐다(ADR 0001) |
| 전체 재색인 | 매일 04:30 | 전체 재색인 비용 ↔ 드리프트 상한선 |
| 모델·스키마 변경 | **주기가 아니라 이벤트** | 도장 대조가 증분을 거부해 강제 |

전체 재색인 비용이 실측으로 있어서 결정이 감이 아니다: **키워드 17초 + 벡터 8분 12초 = 하루의
0.6%.** 드리프트를 고민하는 것보다 매일 다시 만드는 쪽이 싸다. (서울 전체 53.7만이면 8.4배 —
약 71분. 여전히 새벽 창에 들어간다.)

스케줄러는 만들되 **기본은 꺼둔다.** 앱이 뜨자마자 원천을 훑으면 로컬 시연·실측이 방해받는다.
`application.yml` 의 cron 값이 곧 "프로덕션이면 이렇게 돈다"의 기록이다.

## 실측 (2026-07-24, 강남구 64,239건)

### 색인 — 분리 후에도 성능이 같다

| | 이번 | 분리 이전 |
|---|---|---|
| 키워드 전체 재색인 + alias 스왑 | **17초** (`v15`→`v16`) | 17초 |
| 벡터 전체 재색인 + alias 스왑 | **492초** (8분 12초), 임베딩 471초 = **95.7%** | 513초, 95.6% |

### 질의 — 재색인 전후 결과가 완전히 같다

회귀 질의 20개(`scripts/queries_regression.txt`, `scripts/measure_search.py`).

| 채널 | 0건 (재색인 전) | 0건 (재색인 후) | 중앙값 | p95 |
|---|---|---|---|---|
| 키워드 | 7 | **7** | 4.6ms | 7.0ms |
| 벡터 | 2 | **2** | 4.7ms | 5.7ms |
| 하이브리드 | 0 | **0** | 8.2ms | 11.4ms |

### 색인 중 질의 — 분리의 주장을 직접 잰다

색인이 도는 동안 세 채널을 4워커로 계속 두들겼다(`scripts/verify_zero_downtime.py`).

| 구간 | 요청 | 실패 | 빈 결과 | 하이브리드 중앙값 | p95 |
|---|---|---|---|---|---|
| 유휴 (기준선) | 12,887 | **0** | **0** | 11.5ms | 20.5ms |
| 키워드 전체 재색인 중 (17초) | 10,127 | **0** | **0** | 15.2ms | 30.8ms |
| 벡터 전체 재색인 중 (879초) | 183,475 | **0** | **0** | 23.4ms | 52.3ms |

**얻은 것:** 20만 건 넘게 던지는 동안 실패 0·빈 결과 0. alias 스왑이 원자적이라 "가리키는 곳이
없는" 순간이 생기지 않는다. 빈 결과를 따로 센 이유가 이것이다 — 실패 카운터만 보면 200 OK 에
0건이 돌아오는 사고를 놓친다.

**정직하게 남는 것 — 지연은 2배가 됐다** (11.5ms → 23.4ms, p95 는 2.6배). 프로세스는 나뉘었지만
로컬에서는 **같은 CPU 를 나눠 쓴다.** 즉 이 분리가 지금 보장하는 것은 **장애 격리**이지
**자원 격리**가 아니다.

| 무엇을 막았나 | 지금 상태 |
|---|---|
| 색인기 OOM 이 검색 프로세스를 죽이는 것 | ✅ 다른 프로세스라 전파되지 않는다 |
| 질의 노드에 `/admin` 이 열리는 것 | ✅ 클래스가 jar 에 없다 |
| 색인이 질의 지연을 밀어올리는 것 | ❌ 같은 머신이면 그대로 경쟁한다 |

세 번째는 **아티팩트 분리로 풀리는 문제가 아니다.** 두 앱을 다른 노드(또는 K8s 파드)에
배치해야 완성된다. 다만 그 배치가 **가능해진 것**이 이 ADR 의 성과다 — 한 아티팩트였을 때는
애초에 불가능했다. ADR 0002 의 멀티클러스터도 같은 선상에 있다.

### 버전 도장

```
search   {schema_version: 1}
suggest  {schema_version: 1}
vector   {schema_version: 1, embedding_model: multilingual-e5-small, embedding_dim: 384}
```

### 계약 불일치 시 기동 차단 (negative test)

`SCHEMA_VERSION` 을 2로 올리고 질의기를 띄웠다. **기동에 실패했다.**

```
Caused by: java.lang.IllegalStateException: [search] 색인된 데이터와 이 프로세스의 계약이 다릅니다.
  - 문서 스키마 버전: 색인=1, 질의=2
  이 상태로는 오류 없이 결과만 조용히 틀려집니다.
  → 색인기(indexer-batch)에서 POST /admin/reindex 로 전체 재색인한 뒤 다시 띄우세요.
```

이 테스트가 통과해야 "쪼개도 안전하다"고 말할 수 있다. 되돌린 뒤 정상 기동과
`색인 계약 확인 완료 — 스키마 v1` 을 확인했다.

## 덤 — 실측이 분리와 무관한 버그를 잡았다

회귀 측정 스크립트가 `/v1/search?q=CU` 가 **187건을 200 OK 로** 돌려주면서 결과의 이름·주소가
전부 빈 문자열인 것을 잡아냈다. `total` 과 하이라이트는 정상이었다 — 그건 ES 메타데이터라서.

원인은 **Jackson 이 두 개** 올라와 있는 것이었다.

| 누가 | 어떤 Jackson | Kotlin 모듈 |
|---|---|---|
| Spring Boot 4 (웹) | Jackson 3 (`tools.jackson`) | 있음 |
| ES 자바 클라이언트 | Jackson 2 (`com.fasterxml.jackson`) | **없음** |

Kotlin 모듈 없는 Jackson 2 는 `val` 뿐인 data class 를 만나면 합성 무인자 생성자로 만든 뒤
세터가 없어 못 채우고, **예외 없이 전부 기본값**이 된다.

영향이 조회에 그치지 않았다.

- `CheckpointStore.Checkpoint` 를 **항상 못 읽어** 증분 색인이 매번 인덱스 max 로 폴백했다.
  체크포인트는 크리틱 #1·#2 를 고치려고 만든 장치인데 그게 무력화돼 있었다.
- 하이브리드에서 키워드 후보 50건이 **전부 같은 빈 문서 하나로 접혀**, RRF 가 사실상 벡터 단독으로
  돌고 있었다.
- `IndexMeta.Stamp` 도 같은 병이라, 이 ADR 의 도장을 만들다가 밟아서 드러났다.

`main` 에 같은 테스트를 옮겨 돌려 **분리 이전에도 실패**함을 확인했다. 고침은 `search-core` 가
`JsonpMapper` 빈을 제공하는 것 — ES 를 읽는 코드가 두 앱과 core 에 흩어져 있어 한쪽만 고치면
다른 쪽이 계속 빈 값을 받는다. **이 저장소가 core 를 두는 이유와 정확히 같은 이유다.**

## 무엇을 포기했나 (정직하게)

- **빌드가 복잡해졌다.** 모듈 4개, `settings.gradle.kts` 두 겹(컴포지트 + 멀티프로젝트).
  단일 아티팩트보다 처음 여는 사람에게 불친절하다.
- **로컬 실행이 두 명령이 됐다.** 데모할 때 앱을 둘 띄워야 한다.
- **core 가 무거워졌다.** ES 클라이언트·WebClient·DJL 을 다 안다. "순수한 도메인 모듈"은 아니다.
  대신 **한 벌만 존재해야 하는 것**을 담는다는 기준은 지켰다.
- **기동 시간을 지불한다.** 계약 불일치일 때 모델 로딩 5.6초를 버리고 실패한다(위 트레이드오프).

## 결과 (이렇게 하면 뒤따르는 일)

- **멀티클러스터의 전제가 갖춰졌다** (ADR 0002 의 연장). 질의기가 독립 아티팩트라
  "어느 클러스터를 보나"가 그 앱의 설정 한 줄이 된다.
- **`SCHEMA_VERSION` 을 올리는 규율이 생겼다.** 문서 필드명이나 ES 매핑을 바꾸면 올려야 한다.
  안 올리면 옛 스키마 위에서 새 질의가 돌고, 올리면 재색인 전까지 질의기가 뜨지 않는다 — 후자가 의도다.
- **`indexer-core` 추출 시점이 정해졌다** — `indexer-stream` 에 실코드가 붙을 때.
- **#14·#15 가 닫혔다.** 사전 해시는 아직 도장에 없다(→ 남은 구멍).

## 남은 구멍

- **형태소 사전 버전이 도장에 없다.** 사전은 ES 플러그인 쪽에 있어 앱이 읽기 어렵다. 지금은
  매일 전체 재색인이 쓸어내는 것으로 대신한다(결정 6). 사전 해시를 도장에 넣는 게 #14 의 완전한 해결이다.
- **문서 단위 출처가 없다.** 차단으로 섞임을 막았지만, 이미 섞인 인덱스를 사후에 감지할 방법은 없다.
  필요해지면 문서에 `meta` 필드를 더한다.
- **자원 격리는 아직 없다.** 색인 중 질의 지연이 2배가 된다(위 실측). 프로세스는 나뉘었지만
  같은 CPU 를 쓴다. 두 앱을 다른 노드에 배치해야 닫히는 항목이고, 이 ADR 은 그 배치를
  **가능하게** 만든 데까지다.
- **`indexer-batch` 자신은 도장을 기동 시 대조하지 않는다.** 증분 시작 전에만 본다. 색인기는
  어긋나도 "전체 재색인" 이라는 정당한 복구 경로가 있어서, 기동을 막으면 복구 수단까지 막힌다.
