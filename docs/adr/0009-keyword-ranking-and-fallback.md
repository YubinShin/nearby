# ADR 0009 — 키워드 랭킹은 정밀도 우선, 0건 시 완화 폴백

- **상태:** Accepted
- **날짜:** 2026-07-23
- **관련:** ADR 0002 (용도별 인덱스 분리) · ADR 0006 (리액티브 런타임) · ADR 0008 (형태소 분석기)

## Context

"역삼 커피" 한 줄이 들어오면, 어떤 문서를 어떤 순서로 반환할 것인가. 장소 검색 질의는 대개 **지역어 + 업종어**가 섞여 있고, 이 둘은 서로 다른 필드에 흩어져 있습니다.

- `역삼` → 지번주소(`서울특별시 강남구 역삼동 …`) 또는 행정동(`역삼1동`)
- `커피` → 상호명(`커피니`) 또는 업종(`카페`)

따라서 "한 필드에서 두 단어를 다 찾는" 일반적인 검색 방식으로는 잘 매칭되지 않습니다. 결정할 것은 셋입니다.

1. 여러 필드에 흩어진 단어를 어떻게 묶어서 볼 것인가
2. 모든 단어를 요구할 것인가(정밀도), 일부만 맞아도 받을 것인가(재현율)
3. 자동완성은 무엇으로 순서를 매길 것인가

## Decision

1. **`cross_fields` + `operator=AND`** — 여러 필드를 하나의 큰 필드처럼 보고, 질의의 모든 단어가 (필드를 넘나들어서라도) 있어야 걸리게 합니다.
2. 0건이면 `minimum_should_match=70%`로 한 번 더 질의하고, 응답에 `relaxed=true`를 표시합니다.
3. 자동완성은 **BM25 × (접두 일치 가산점) × (이름 길이 역수)** 로 정렬하고, 동점은 `place_id` 오름차순으로 고정합니다.

## Rationale

### 1. cross_fields

단어가 필드를 넘나들기 때문입니다. `best_fields`(기본값)는 "가장 잘 맞는 한 필드"의 점수를 씁니다. `역삼 커피`처럼 단어가 두 필드에 나뉘어 있으면 어느 한 필드도 온전히 맞지 않아 점수가 낮습니다. `cross_fields`는 필드들을 한 덩어리로 보고 단어 단위로 매칭하므로 이 경우에 맞습니다.

전제 조건 하나: cross_fields는 분석기가 같은 필드끼리 그룹을 만듭니다. 그래서 매칭에 쓰는 필드는 전부 komoran으로 통일했습니다. 카테고리·행정동은 원래 `keyword`(분석 안 함)라 부분 단어가 걸리지 않았습니다. 그래서 `.txt` 멀티필드(komoran)를 적용해 매칭은 `.txt`, 필터는 `keyword` 원본으로 역할을 분리했습니다.

가중치는 `name^5 = brand_text^5 > branch^3 > category_small.txt^2 > dong.txt^1.5 > category_mid.txt = sigungu.txt = 주소`. 상호명이 가장 강한 신호라는 도메인 판단이고, 이 순서는 단위 테스트로 고정했습니다.

### 2. AND-first with 0-hit fallback

장소 검색에서 단어 하나만 맞은 결과는 대개 소음입니다. "역삼 커피"에 역삼동 치과가 나오면 안 됩니다. 그래서 기본은 모든 단어를 요구합니다(정밀도 우선).

문제는 이 경우 **0건**이 늘어난다는 것입니다. 검색 UX에서 빈 화면은 최악이므로, 0건일 때만 조건을 풀어 재질의합니다. 비용이 0건일 때만 발생하므로 정상 경로 지연에는 영향이 없습니다.

완화 임계값은 실측으로 정했습니다.

| 임계값 | `삼성동 이자카야` 결과 | 판단 |
|---|---|---|
| `50%` | **6,876건** | 3단어 중 1단어만 맞아도 걸려서 소음 |
| `70%` | **12건** | 3단어 중 2단어 필요 — 이자카야만 맞은 곳들 |

(이 질의가 0건이었던 것은 버그가 아니라 **데이터 사실**입니다. 강남구에 상호명이 '이자카야'인 곳은 17곳인데 삼성동에는 없습니다. 폴백이 지역 조건을 풀어 인근 이자카야를 보여준 것이 의도한 동작입니다.)

완화했다는 사실은 응답에 `relaxed=true`로 드러냅니다. 표시 없이 다른 것을 보여주면 사용자도 호출하는 서비스도 속게 되기 때문입니다.

### 3. Autocomplete

없는 신호를 지어내지 않습니다. 가장 좋은 자동완성 신호는 **인기도(클릭·주문)** 인데 현재 원천에 없습니다. 그래서 가진 것으로만 순서를 정하되, 각 신호가 실제로 기여하는지 측정했습니다.

| 신호 | 실측 결과 |
|---|---|
| 접두 일치 가산점 (`prefix` on `label.raw`) | 비접두 매칭 `e-스타치과` 57위 → **122위**로 강등. 효과 있음 |
| 이름 길이 역수 (`name_length`) | 질의별로 갈림 — `강남`은 상위권 개선(`강남`이 `강남#`보다 위로), `커피`·`스타`는 상위 10 불변, `김밥`은 무변화 |
| `place_id` tie-break | 동점 순서 고정 (아래) |

길이 역수는 기대만큼 기여하지 않았습니다. BM25의 필드 길이 정규화가 이미 짧은 이름을 올려주고 있어 신호가 상당 부분 겹칩니다. 남겨둔 이유는 상위권이 아니라 중위권 순서를 다듬는 효과가 있고 비용이 필드 하나뿐이기 때문입니다.

`스타` 질의의 상위 20건이 **서로 다른 점수 3종**뿐이었습니다. BM25의 길이 정규화가 1바이트로 양자화되어 있어 짧은 이름들이 무더기로 같은 점수를 받습니다. 동점의 순서를 ES 내부 doc id에 맡기면 세그먼트 병합·재색인·레플리카에 따라 순서가 달라집니다 — 한 글자 칠 때마다 목록이 튀는 원인입니다. `place_id`로 2차 정렬을 걸어 **결정적**으로 만들었습니다. (실측: 같은 질의 5회 반복 결과 완전 일치)

## Trade-offs

- **AND 우선은 오타에 약함.** 한 글자 틀리면 0건 → 폴백 경로로 빠집니다. `fuzziness`는 형태소 분석기와 함께 쓰면 오작동이 많아 지금은 넣지 않았습니다. 오타 교정은 별도 레이어(질의 로그 기반 스펠 체커)로 다루는 것이 맞습니다.
- **`relaxed` 폴백은 질의를 두 번 보냄.** 0건 질의가 많은 서비스라면 이것이 그대로 부하입니다. 질의 로그에서 0건 비율을 지표로 보고 판단해야 합니다.
- **`place_id` tie-break는 "안정적"이지 "좋은" 순서가 아님.** 인기도 신호가 생기면 그것으로 교체해야 합니다. 지금은 임의로 흔들리는 것보다 낫다는 수준의 결정입니다.
- **가중치 숫자(5, 3, 2, 1.5)에 근거 데이터 없음.** 도메인 직관으로 정했고, 제대로 하려면 클릭 로그로 평가셋을 만들어 nDCG로 튜닝해야 합니다. 지금은 그 로그가 없습니다.

## Query log

위 트레이드오프(오타 교정 · 0건 비율 · 가중치 근거)는 모두 질의 로그를 전제로 합니다. 모든 검색·자동완성 질의를 `logs/query.log`에 한 줄 JSON으로 기록합니다. 앱 로그와 파일을 분리한 이유는 디버깅 산출물이 아니라 데이터 자산이라 수명과 관리 주체가 다르기 때문입니다.

```jsonc
{"ts":"2026-07-23T17:30:20.265+09:00","type":"search","q":"존맛탱","total":0,"zero":true,"relaxed":true,"took_ms":1}
```

| 용도 | 내용 |
|---|---|
| 사전 확보 | 0건 질의가 미등록 어휘의 직접 증거입니다. `scripts/mine_query_log.py`가 후보를 뽑습니다 |
| 랭킹 근거 | 질의–클릭 쌍이 기록되어야 필드 가중치를 nDCG로 평가할 수 있습니다 |

질의문 외에 식별자를 기록하지 않습니다.

## Consequences

- 랭킹 규칙은 전부 **`PlaceQueries` 순수 함수** 한 곳에 모으고, 질의 JSON을 단위 테스트로 고정합니다. ES 없이 실행되는 테스트라 랭킹 변경이 의도치 않게 새는 것을 막습니다.
- 6단계 RRF 결합에서 이 키워드 검색은 **채널 하나**로 들어갑니다. 그래서 서비스는 순위·점수·`place_id`를 온전히 반환하는 것을 계약으로 삼습니다 (ADR 0003).
- 인기도 신호가 생기면 자동완성의 `name_length` 자리를 그것으로 교체합니다. `function_score` 구조는 그대로 두고 함수만 바꾸면 됩니다.
