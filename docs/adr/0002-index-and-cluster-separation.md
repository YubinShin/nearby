# ADR 0002 — 검색 인덱스를 용도별로 나눈 이유

- **상태:** Accepted
- **날짜:** 2026-07-20

## 배경 (무엇을 정해야 하나)

검색 엔진 안에서 데이터가 담기는 통을 **인덱스**라고 해요. 이 서비스에는 성격이 다른 두 가지
검색이 있어요.

- **본문 검색** — "강남 파스타"를 넣으면 관련도 높은 장소를 찾아주는 것.
- **자동완성** — "강남 파"까지만 쳐도 "강남 파스타"를 미리 띄워주는 것.

이 둘을 **한 인덱스에 같이 넣을까, 따로 나눌까?**

## 결정

**용도별로 인덱스를 나눈다** (본문 검색용 / 자동완성용). 그리고 규모가 커지면 인덱스뿐 아니라
**클러스터(엔진 묶음)까지 목적별로 분리**할 수 있는 구조로 처음부터 설계한다.

## 왜 (근거)

두 검색은 요구사항이 완전히 달라요.

- **자동완성은 타이핑 한 글자마다 호출돼요.** 그래서 초고빈도·초저지연이 필요하고, 데이터를 담는
  방식도 달라요(글자를 잘게 쪼개 미리 저장하는 edge_ngram 같은 방식).
- **본문 검색은 "얼마나 관련 있나(relevance)"가 핵심**이에요. 호출 빈도는 자동완성보다 낮지만
  한 번의 검색이 더 무거워요.

이 둘을 한 통에 섞으면, **한쪽 트래픽이 다른 쪽의 성능과 자원을 침범**해요. 자동완성 요청이
몰리면 본문 검색이 느려지는 식이죠. 나눠두면 각각 독립적으로 튜닝하고, 필요한 만큼만 키우고,
한쪽에 장애가 나도 다른 쪽으로 안 번져요(장애 격리).

## 플랫폼 관점 (이게 진짜 이유)

이건 "장소 검색 하나"만 만들 거면 굳이 안 나눠도 돼요. 하지만 목표가 **여러 서비스가 공통으로
쓰는 플랫폼**이에요. 서비스가 늘어나면 용도(쇼핑 검색, 광고 검색, 통합 검색…)도 계속 늘어나요.
그때마다 통을 새로 나누려면 고통스러워요. **처음부터 용도별로 분리하는 토폴로지**로 가면,
새 용도가 붙어도 기존 것에 영향 없이 확장할 수 있어요.

## 언제였다면 다른 선택을 했을까

서비스가 작고 검색 용도가 하나뿐이라면 **단일 인덱스**로 단순하게 가는 게 맞아요.
요구가 갈리는 순간 그 단순함이 한계가 되는데, 이 프로젝트는 처음부터 여러 용도를 전제해요.

## 결과 (이렇게 하면 뒤따르는 일)

- 인덱스마다 데이터 담는 방식(매핑)을 따로 관리해요.
- 새 버전으로 바꿀 때 서비스가 안 끊기도록 **별칭(alias)을 새 인덱스로 바꿔치기**하는 무중단 교체를 써요.
- 자원(메모리·노드)을 용도별로 격리해서, 한쪽 부하가 전체를 흔들지 않게 해요.
