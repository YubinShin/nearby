# Permit Change Review Agent

## Overview

인허가 스냅샷의 변경을 기존 장소 데이터와 대조하고, 근거를 포함한 갱신 제안 또는 판단 보류를 반환하는 CLI Agent입니다. Agent는 조회 결과에 따라 다음 도구를 선택하는 LLM을 뜻합니다. Tool-calling은 모델이 도구 이름과 인자를 요청하면 프로그램이 검증 후 실행하는 방식입니다.

데이터 준비, 주소 기반 후보 조회, Gemini Tool-calling 실행과 JSON 결과 저장을 구현했습니다. 빽다방 상호 변경 사례에서 실제 모델의 도구 호출과 제안 제출을 확인했습니다. 전용 평가셋, 규칙 기반 방식과의 비교, 검토 UI와 승인 후 반영은 구현 예정입니다. 단일 사례의 실행 성공을 판단 품질 검증으로 해석하지 않습니다. 이 문서는 후속 코드 변경 범위의 승인을 대신하지 않습니다.

목표는 실제 데이터 변경을 대상으로 도구 호출, 서로 다른 원천의 장소 연결, 근거 추적, 실패 처리와 평가를 구현하는 것입니다. 모델이 규칙 기반 처리보다 정확하거나 효율적인지는 비교 평가 전까지 판단하지 않습니다.

## Snapshot Preparation

[prepare_snapshot.py](../scripts/permit_review/prepare_snapshot.py)는 이전·신규 manifest와 자치단체 코드를 입력받아 비교 결과 JSON을 생성합니다. Python 표준 라이브러리만 사용하며 DB나 LLM API를 호출하지 않습니다.

```bash
python3 scripts/permit_review/prepare_snapshot.py \
  --previous data/raw/localdata/seoul/restaurants-snack/baseline-undated/manifest.json \
  --current data/raw/localdata/seoul/restaurants-snack/2026-10-27/manifest.json \
  --gov-code 3220000 \
  --output /tmp/permit-review-gangnam.json

python3 -m unittest discover -s scripts/permit_review -p 'test_*.py' -v
```

출력 부모 디렉터리는 미리 존재해야 합니다. 출력 파일이 이미 있으면 실패하며 덮어쓰지 않습니다. 원본 파일과 manifest는 읽기만 합니다.

| Rule        | Behavior                                                                         |
| ----------- | -------------------------------------------------------------------------------- |
| 무결성      | manifest의 SHA-256과 바이트 크기가 실제 파일과 다르면 실패                       |
| CSV 구조    | 필수 컬럼 누락, 중복 헤더, 행의 컬럼 수 불일치 시 실패                           |
| 인코딩      | CP949 디코딩 불가 바이트를 감지하고 필드명·논리 레코드 번호 기록                 |
| 정규화      | 필드 양끝 공백 제거. 날짜·좌표는 문자열 비교                                     |
| 중복        | 선택한 지역에서 같은 관리번호가 여러 행이면 모두 비교에서 제외                   |
| 비교 제외   | 어느 스냅샷에서든 중복이거나 디코딩 문제가 있으면 해당 ID를 양쪽 비교에서 제외   |
| 식별자 누락 | 빈 관리번호·디코딩 불가 관리번호는 이슈로 기록하고 비교에서 제외                 |
| 상태        | 영업·폐업을 모두 보존                                                            |
| 변경 종류   | `added`, `modified`, `absent_from_current`로 구분. 누락을 폐업으로 변환하지 않음 |
| 비교 필드   | 상호·상태 코드와 이름·상세 상태 코드·폐업일·주소·업태·좌표                       |
| 갱신 시각   | 결과에 보존하되, 시각만 바뀐 경우 업무 필드 변경으로 집계하지 않음               |
| 근거        | 스냅샷 SHA-256과 논리 레코드 번호로 원본 행 참조                                 |

`previous.issues`와 `current.issues`의 디코딩 오류는 서울 원본 전체에서 집계합니다. 중복 관리번호와 변경 통계는 `--gov-code`로 선택한 지역 기준입니다. 중복은 내용이 같은 행도 자동 병합하지 않습니다. 이러한 보수적 제외는 변경 누락 가능성이 있으므로 제외 ID와 원본 행을 별도 검토해야 합니다.

### Verification

[단위 테스트](../scripts/permit_review/test_prepare_snapshot.py)는 폐업 보존, 중복 분리, 상호 변경과 근거 참조, 행 누락, 디코딩 오류, 무결성 실패, 시각 단독 변경, 다중 행 필드, 지역 제한, 빈 식별자, 필수 컬럼과 출력 덮어쓰기 방지를 검증합니다. 2026-10-27 실행에서 12개 테스트가 통과했습니다.

서비스 검증 중 첫 빌드 시도는 Gradle 캐시 잠금 파일 접근 권한 부족으로 시작하지 못했습니다. 권한을 받아 실행한 빌드는 Elasticsearch `localhost:9200` 연결 거부로 인프라 테스트 5개가 실패했습니다. Docker 기동 후 연결 실패는 해소됐습니다. 이후 전체 빌드에서 기존 `EmbedGateTest`의 타임아웃·permit 반환 경합 테스트가 실패했습니다. 해당 테스트 클래스의 단독 실행은 통과했으며 실패의 근본 원인은 아직 확정하지 않았습니다. 관련 코드는 수정하지 않았습니다.

이후 `services/gradlew -p services build test`는 `BUILD SUCCESSFUL`로 종료됐습니다. `search-api` 테스트가 다시 실행됐으며 XML 기준 92개, 실패·오류·건너뜀 0개입니다. `ask-api`·`indexer-batch`·`search-core`는 `UP-TO-DATE`였으므로 이번 실행에서 새로 검증한 테스트 수에 합산하지 않습니다. 재실행 통과가 앞선 동시성 실패의 원인 해소를 의미하지는 않습니다.

## Place Candidate Lookup

[find_candidates.py](../scripts/permit_review/find_candidates.py)는 변경 JSON의 `change_id`와 장소 CSV를 입력받습니다. 이전·신규 인허가의 건물 주소에 일치하는 장소 후보를 모두 반환합니다. DB·검색 API·LLM을 호출하지 않는 로컬 조회 함수입니다. Agent는 `review_tools.py`의 페이지 조회 도구를 거쳐 이 결과를 사용합니다.

```bash
python3 scripts/permit_review/find_candidates.py \
  --changes /tmp/permit-review-gangnam.json \
  --change-id 715c7bc0ecd43dda62eb0975b1611a196d143b7ec0da1318873f2ebd5dc41d05 \
  --places data/gangnam_place.csv \
  --output /tmp/permit-review-hanti-candidates.json
```

`--changes`는 Snapshot Preparation 명령의 출력입니다. 예제 변경 ID는 문서에 기록한 두 스냅샷의 빽다방 상호 변경에서 생성됐습니다. 스냅샷이 바뀌면 새 변경 ID를 사용해야 합니다. 출력 파일은 덮어쓰지 않습니다.

### Matching Rules

| Rule        | Behavior                                                                                             |
| ----------- | ---------------------------------------------------------------------------------------------------- |
| 주소 정규화 | NFC 정규화와 연속 공백 축약 후 쉼표·괄호 앞 문자열을 건물 주소로 사용                                |
| 허용 형식   | `서울특별시 + 구 + 도로명 + 건물번호` 형식만 비교. 도로명은 대로·로·길로 끝나며 건물번호의 부번 허용 |
| 완전 일치   | 정규화된 건물 주소 전체 비교. `405`, `405-1`, `4050`은 서로 다른 주소                                |
| 상세주소    | 층·호수는 후보 선정에 사용하지 않음. 원문 주소는 결과에 보존                                         |
| 변경 전후   | 이전·신규 주소를 모두 조회하고 어느 쪽과 일치했는지 기록                                             |
| 상호·업종   | 후보의 정보로 반환하되 필터나 동일 장소 판정에 사용하지 않음                                         |
| 후보 순서   | `place_id` 오름차순. 적합도 순위가 아님                                                              |
| 원본 검증   | UTF-8 장소 CSV의 필수 컬럼·행 구조 검사. 빈 ID·중복 ID·디코딩 오류 시 실패                           |
| 출처        | 입력 변경 JSON과 장소 CSV의 SHA-256 기록. 장소 근거는 CSV 해시와 논리 레코드 번호로 연결             |

조회 상태는 `candidates_found`, `no_candidates`, `unsearchable`로 구분합니다. 인허가 주소가 없거나 지원하지 않는 형식이면 해당 조회 대상에 사유를 기록합니다. 비교 가능한 주소가 하나도 없으면 `unsearchable`입니다. 장소 CSV의 주소 누락·지원하지 않는 형식은 `place_address_issues`에 기록합니다.

결과의 `identity_confirmed`는 항상 `false`입니다. 후보가 하나여도 같은 장소로 확정하지 않습니다. `scope`는 `provided_place_csv`이며, `no_candidates`는 이 CSV에서 주소가 일치하는 후보를 찾지 못했다는 뜻입니다. 기존 CSV의 중복 장소 판정이나 브랜드 복원 테이블은 적용하지 않습니다.

로컬 후보 조회 함수는 모든 후보를 반환하며 `truncated`는 `false`입니다. Tool-calling에서는 별도의 도구 계층이 페이지 조회와 출력 크기 제한을 적용합니다. 원문 주소에 호수가 있어도 건물만 같으면 후보에 포함되므로, 서로 다른 호수의 매장은 후속 검토에서 구분해야 합니다. `서울`을 `서울특별시`로 바꾸거나 지원하지 않는 주소를 추정하지 않습니다.

### Verification

2026-10-27 실행에서 `data/gangnam_place.csv`의 64,239개 레코드를 조회했습니다. 빽다방 변경 ID에 대해 도곡로 405의 후보 38건을 반환했습니다. 별도로 CSV의 `road_address == "서울특별시 강남구 도곡로 405"`인 행을 추출하고, 후보 ID 집합이 같은지 확인했습니다. 해당 장소 CSV에는 주소 누락·지원하지 않는 형식으로 분리된 행이 없었습니다.

`MA010120220814335796`의 `바른에프앤비한티역점빽다방`이 후보에 포함됐습니다. 각 후보에는 이전·신규 인허가의 근거 참조가 모두 남습니다. 원본 장소 CSV의 SHA-256과 출력의 출처 해시가 일치하는지도 확인했습니다. 후보 38건은 같은 장소 38건을 의미하지 않습니다.

[후보 조회 테스트](../scripts/permit_review/test_find_candidates.py) 12개와 기존 변경 추출 테스트 12개가 통과했습니다. 복수 업종 후보, 건물 부번·번호 접두사·자치구 불일치, 주소 누락, 변경 전후 주소, 신규·누락 레코드, 상세주소 보존, 지원하지 않는 형식, 중복 장소 ID와 잘못된 변경 ID를 검증했습니다. `services/gradlew -p services build test`는 `BUILD SUCCESSFUL`로 종료됐으며, 서비스 태스크는 모두 `UP-TO-DATE`로 재사용됐습니다. 이번 후보 조회 검증에서 기존 Kotlin 테스트를 새로 실행하지는 않았습니다.

## Scope

첫 구현은 서울 원본 중 강남구의 상호 변경과 영업 상태 변경을 검토 대상으로 제안합니다. 신규 관리번호와 주소·좌표 변경은 추출 결과에 보존하되, 첫 평가 대상에 포함할지는 사례 검토 후 결정합니다.

| Responsibility                                  | Owner                               |
| ----------------------------------------------- | ----------------------------------- |
| 원본 무결성 확인, 파싱, 변경 추출               | 코드                                |
| 도구 선택, 후보 비교, 추가 근거 요청, 검토 제안 | 모델                                |
| 인자·근거 ID·대상 필드·실행 예산 검증           | 코드                                |
| 장소 동일성 및 제안의 최종 검토                 | 사람                                |
| 장소 원천·검색 색인 실제 변경                   | 첫 구현에 쓰기 도구를 제공하지 않음 |

인허가 관리번호와 장소의 `place_id`는 서로 다른 식별자입니다. 같은 주소, 유사한 이름, 가까운 좌표 중 하나만으로 자동 연결하지 않습니다. 인허가 폐업이 확인돼도 다른 원천의 장소 삭제를 자동 승인하지 않습니다. 새 파일에서 행이 사라진 경우도 폐업으로 간주하지 않습니다.

## Proposed Workflow

1. 코드가 명시적으로 지정된 이전·신규 스냅샷의 해시와 컬럼을 확인합니다.
2. 코드가 상태를 보존하며 행을 정규화하고 중복 식별자를 분리합니다.
3. 중복 선택 정책이 확정된 레코드에서 변경을 추출하고 변경 ID를 부여합니다.
4. Agent가 변경 상세와 기존 장소 후보를 도구로 조회합니다.
5. 후보가 여러 개이거나 근거가 충돌하면 추가 조회하거나 판단을 보류합니다.
6. Agent가 갱신 제안, 변경 불필요 또는 판단 보류를 제출합니다.
7. 코드가 제출 형식과 근거 참조를 검증하고 사람이 검토할 결과로 저장합니다.

원본의 사업장명·주소 등은 데이터로 취급합니다. 필드에 포함된 문구가 도구 권한이나 실행 지침을 바꾸지 못하도록 설계합니다.

## Tools

현재 도구 계약은 [review_tools.py](../scripts/permit_review/review_tools.py)의 `TOOL_DECLARATIONS`에 정의합니다. 모델에 임의 SQL, 파일 경로, 외부 URL을 실행하는 도구는 제공하지 않습니다.

| Tool                    | Input                                        | Output                                                | Validation                                          |
| ----------------------- | -------------------------------------------- | ----------------------------------------------------- | --------------------------------------------------- |
| `get_permit_change`     | `change_id`                                  | 이전·신규 값과 원본 행 참조                           | 현재 검토에 속한 변경 ID만 허용                     |
| `find_place_candidates` | `change_id`, `page`                          | 건물 주소 후보, 조회 범위, 전체 후보 수와 다음 페이지 | 페이지당 10건, 음수·범위 밖·정수가 아닌 페이지 거부 |
| `get_place_evidence`    | `change_id`, `place_id`                      | 장소 CSV 필드, 건물 주소 일치 근거, 출처              | 해당 검토에서 조회한 후보 ID만 허용                 |
| `submit_review`         | 판단, 대상 ID, 제안 필드, 근거 ID, 보류 사유 | 검증된 검토 결과 또는 오류                            | 근거와 대상의 연결, 허용 필드, 필수 정보 검사       |

변경 상세와 장소 상세 출력에는 원본 해시와 논리 레코드 번호로 구성한 근거 ID를 포함합니다. 후보 페이지에는 ID·상호·지점·업종·주소를 제공하고, 장소 근거는 `get_place_evidence`를 호출한 뒤에만 제출에 사용할 수 있습니다. 전화번호와 종사자 수 등 검토에 필요하지 않은 정보는 모델 입력에 포함하지 않습니다.

후보 검색에는 누락 가능성이 있습니다. 조회 결과가 없다는 이유만으로 장소가 존재하지 않는다고 결론 내리지 않습니다. 후보가 상한 때문에 잘렸는지도 출력에 표시합니다.

## Review Contract

검토 결과와 실행 이력에는 다음 정보를 저장합니다.

- 실행 ID, 변경 ID, 이전·신규 스냅샷 해시
- 판단: `propose_update`, `no_change`, `needs_review`
- 대상 `place_id`와 제안 필드의 기존 값·새 값
- 판단 근거 ID와 설명. 충돌한 근거·확인하지 못한 조건의 별도 구조화 필드는 구현 예정
- 종료 사유와 사람이 검토할 설명
- 모델·프롬프트·도구 스키마 버전, 호출 이력, 시간·토큰 사용량

`propose_update`와 `no_change`는 모든 후보 페이지를 조회하고 대상 장소의 상세 근거를 읽은 뒤에만 허용합니다. 첫 버전은 `changed_fields == ["name"]`인 변경에만 두 판단을 허용합니다. `propose_update`의 기존 값은 장소 CSV의 상호와, 새 값은 신규 인허가의 상호와 같아야 합니다. `no_change`는 대상 상호가 신규 인허가 상호와 이미 같고 제안 필드가 없을 때만 허용합니다. 상태·주소 변경과 불확실한 연결은 `needs_review`로 제출합니다.

`needs_review`는 갱신 필드를 포함하지 않습니다. 대상을 지정하면 해당 장소 상세 근거가 필요하며, 대상이 없으면 빈 `place_id`를 사용합니다. 모든 판단은 실제 조회한 이전·신규 인허가 근거를 포함해야 합니다. 존재하지 않거나 조회하지 않은 근거, 다른 후보의 근거로 대상 장소를 대신한 제안은 거부합니다. 수락된 결과에도 `requires_human_review: true`, `semantic_accuracy_verified: false`를 기록합니다. 형식 검증 통과는 장소 연결이나 제안 내용의 정확성을 뜻하지 않습니다.

변경 전후 인허가 스냅샷 해시는 상세 조회 결과의 근거 ID에 포함됩니다. 실행 이력의 `sources`에는 입력 변경 JSON과 장소 CSV의 해시를 별도로 기록합니다. 상세 조회 전에 실패하면 변경 JSON의 해시를 기준으로 원본을 추적해야 합니다.

## Execution Limits and Failure Handling

| Condition                     | Proposed Behavior                                     |
| ----------------------------- | ----------------------------------------------------- |
| 해시 불일치·필수 컬럼 누락    | 모델 호출 전 실행 실패                                |
| 디코딩 불가 값·중복 행 충돌   | 원본을 보존하고 해당 레코드를 별도 검토 대상으로 분리 |
| 잘못된 도구 이름·인자         | 실행하지 않고 검증 오류 반환                          |
| 같은 인자의 반복 호출         | 같은 실행 내 결과 재사용 또는 반복 종료               |
| 시간·호출·토큰 예산 소진      | 수집한 근거를 보존하고 미완료 사유 반환               |
| 조회 서비스 실패              | 실패와 후보 없음 구분, 근거 부족 시 판단 보류         |
| 사용자 취소                   | 후속 도구 실행 중단, 취소 전파와 자원 해제 검증       |
| 잘못된 근거 ID·근거 없는 대상 | 제안 확정 거부                                        |

현재 기본값은 다음과 같습니다. 시간 측정은 스냅샷·장소 CSV를 읽고 후보를 준비한 이후의 모델 실행 루프부터 시작합니다.

| Limit          | Default         | Enforcement                                       |
| -------------- | --------------: | ------------------------------------------------- |
| 모델 요청      | 8회             | 다음 요청 전에 검사                               |
| 도구 실행 시도 | 16회            | 검증 실패를 포함해 집계                           |
| 실행 시간 예산 | 90초            | 단계 전후 확인, 남은 시간을 HTTP timeout으로 전달 |
| 요청 본문      | 131,072바이트   | 도구 스키마와 누적 대화를 포함한 직렬화 크기 검사 |
| 도구 결과      | 24,576바이트    | 초과 시 오류 반환, 조회·제출 상태 변경 되돌림     |
| 모델 응답      | 1,048,576바이트 | 읽기 중 제한                                      |
| 모델 출력 토큰 | 요청당 2,048    | `maxOutputTokens`로 전달                          |
| 누적 보고 토큰 | 100,000         | 응답의 `totalTokenCount` 합산 후 후속 실행 중단   |

보고 토큰 제한은 응답 후 확인하므로 마지막 요청에서 초과할 수 있습니다. 사용량이 없으면 `usage_missing`으로 종료합니다. 실제 비용 상한이나 사전 토큰 계산을 제공하지 않습니다. HTTP timeout은 소켓 대기 제한이며 전체 실행 시간을 정확히 강제 종료하는 장치는 아닙니다. 기한을 넘긴 응답은 도구 실행에 사용하지 않지만, 진행 중인 네트워크 대기 때문에 실제 반환은 늦어질 수 있습니다.

동일 도구·인자가 반복되면 재실행하지 않고 `repeated_call`로 종료합니다. 잘못된 인자는 오류를 모델에 반환해 다른 호출로 수정할 기회를 줍니다. HTTP 실패는 자동 재시도하지 않습니다. `Ctrl-C`는 실행 중 수집한 이력을 보존하고 `cancelled`로 종료합니다. 강제 프로세스 종료에 대한 복구와 실행 중 체크포인트는 구현 예정입니다.

## Agent Execution

[run_review.py](../scripts/permit_review/run_review.py)가 실행 루프와 JSON 저장을 담당합니다. [gemini_client.py](../scripts/permit_review/gemini_client.py)는 `generateContent` REST API를 호출합니다. 모델이 반환한 content를 서명 필드와 함께 다음 요청에 보존하고, 함수 호출 ID가 있으면 도구 응답에도 같은 ID를 포함합니다. 자유 텍스트는 검토 결과로 수락하지 않으며, `submit_review`는 단독 호출이어야 합니다.

```bash
python3 scripts/permit_review/run_review.py \
  --changes /tmp/permit-review-gangnam.json \
  --change-id 715c7bc0ecd43dda62eb0975b1611a196d143b7ec0da1318873f2ebd5dc41d05 \
  --places data/gangnam_place.csv \
  --output /tmp/permit-review-live.json \
  --live --model gemini-3.5-flash-lite
```

실제 호출에는 환경변수 `GEMINI_API_KEY`가 필요합니다. 모델은 명시적으로 지정합니다. 키는 인증 헤더로만 전달하며 출력에 기록하지 않습니다. 실행 이력에는 모델 응답과 도구 인자·결과, 시간, 사용량, 원본 해시를 기록합니다. 기존 출력 파일은 덮어쓰지 않습니다. 정상 제출은 종료 코드 0, 제안 미완료는 종료 코드 2입니다.

`--live --model ...` 대신 `--fixture 응답목록.json`을 사용하면 네트워크 없이 응답을 재생합니다. 파일 형식은 Gemini 응답 객체의 JSON 배열입니다. 모델 응답에 기록된 사용량도 재생되므로 fixture 실행의 `reported_total_tokens`는 신규 API 사용량이 아닙니다.

[evaluate_reviews.py](../scripts/permit_review/evaluate_reviews.py)는 저장된 실행 결과를 채점합니다. 원본 해시가 다르면 `source_mismatch`, 결과가 없으면 `missing`, 정상 제출 전에 종료하면 `incomplete`로 구분합니다. 세 경우 모두 확정 라벨 분모에 남습니다. 미확정 라벨은 `unlabeled`로 별도 집계합니다. 동일 변경의 중복 실행이나 평가셋에 없는 실행을 입력하면 거부합니다.

자동 검사는 판단·대상·변경값·변경 ID·필수 근거 ID·사람 검토 플래그·설명 유무의 일치를 확인합니다. 통과 상태는 `structural_match`이며 의미적 정확성 판정이 아닙니다. 설명의 근거 적절성과 호수 미확인 명시 여부는 `manual_criteria`에 따라 사람이 검토합니다. 채점기는 해당 검토를 `pending`으로 표시하며 최종 의미적 합격률을 계산하지 않습니다. 근거 ID의 존재만으로 실제 업소 동일성을 증명하지 않습니다.

```bash
python3 scripts/permit_review/evaluate_reviews.py \
  --cases scripts/permit_review/eval_cases.json \
  --runs /tmp/permit-review-tj.json \
  --output /tmp/permit-review-evaluation.json
```

집계는 cohort별로 분리하며 구조 일치 건수와 확정 라벨 수를 분자·분모로 반환합니다. 완료·보류·제안·구조 불일치 제안·사람 검토 대기 건수도 반환합니다. 빽다방 개발 사례와 합성 데이터는 실제 평가셋에 포함하지 않았습니다. 현재 네 사례는 소규모 정책 평가이며 `no_change`, 복수 후보, 폐업과 모델 출력 변동의 평가를 포함하지 않습니다. 2026-10-27에 `gemini-3.5-flash-lite`로 각 사례를 한 번씩 실행했습니다.

### Baselines

동일한 변경 사례와 조회 데이터를 사용해 규칙 기반 처리와 Agent를 비교할 예정입니다. 규칙 기반 처리는 정해진 순서로 후보를 조회하고 명시된 연결 조건을 적용합니다. Agent는 결과에 따라 조회 순서와 추가 조회 여부를 선택합니다. 비교 시 후보 검색 범위와 제공 근거를 기록합니다.

모델이 만든 제안을 그대로 정답으로 사용하지 않습니다. 사람이 근거를 확인해 장소 연결, 허용 가능한 조치와 판단 불가를 라벨링합니다. 검토 전에는 정답 미확정으로 표시합니다. 프롬프트 조정용 사례와 최종 평가 사례를 분리하고, 같은 장소의 유사 사례가 양쪽에 섞이는지 확인합니다.

### Cases and Metrics

| Case                                  | Evaluation Focus                     |
| ------------------------------------- | ------------------------------------ |

평가에서는 장소 연결 정확성, 제안 정확성, 잘못된 갱신 제안 수, 보류 비율과 근거 적절성을 함께 확인합니다. 보류만으로 오류율을 낮추지 못하도록 처리 가능한 사례의 제안 비율도 기록합니다. 도구 호출 수, 불필요한 조회, 반복 호출, 지연과 토큰 사용량을 함께 측정합니다. 모든 비율에는 분자·분모와 판정 기준을 표시합니다.

고정 응답을 사용하는 오프라인 테스트는 도구 계약과 실행 제어를 검증합니다. 실제 모델 평가는 판단 품질과 출력 변동을 검증합니다. 두 결과는 구분해 보고합니다. 소규모 유료 호출은 사용자 허용 범위에서 전송 필드·모델·예상 호출 수·비용을 알린 뒤 실행합니다. 비용이 커지는 반복 평가는 별도로 합의합니다.

## Implementation Sequence

1. 중복 행과 실제 변경 사례를 조사하고 스냅샷 정규화·선택 규칙을 합의합니다.
2. 장소 연결 사례와 판단 불가 사례를 선정하고 검토 기준을 작성합니다.
3. 도구 입력·출력, 실행 제한, 저장 형식과 수정 파일 목록을 합의합니다.
4. 변경 추출과 규칙 기반 기준선을 구현하고 검증합니다.
5. Tool-calling 실행과 근거 검증을 구현하고 고정 응답으로 검증합니다.
6. 소규모 실제 모델 평가 후 결과와 한계를 기록합니다.

첫 구현의 완료 기준은 스냅샷 선택부터 변경 추출, 도구 조회, 근거를 포함한 검토 결과까지 한 흐름을 재현하는 것입니다. 원천 데이터에 대한 쓰기 없이 종료해야 합니다. 잘못된 호출과 예산 소진도 검증해야 합니다. 포트폴리오에는 실제 구현·실행·평가 범위만 기록하고, 상용 운영이나 정확성 향상을 측정 없이 주장하지 않습니다.
