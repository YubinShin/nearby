# Glossary

이 저장소를 읽는 데 필요한 말들입니다. 이 프로젝트 문서에 **실제로 나오는 말만** 모았습니다. 일반 검색 교과서 사전이 아니라, "이 저장소를 읽다가 막혔을 때 찾아보는 사전"입니다.

---

## 1. Search basics

**색인 (index / indexing)**
데이터를 **미리 찾기 좋게 정리해두는 것**, 또는 그 정리된 결과물. 책 뒤의 "찾아보기"와 같습니다. 매번 6만 개를 처음부터 뒤지지 않으려고 만듭니다. 원천(PostGIS) → 검색 엔진(ES·Qdrant)으로 옮기는 과정 전체를 "색인 파이프라인"이라 부릅니다.

**질의 (query)**
사용자가 입력한 검색어, 또는 그것을 엔진 형식으로 번역한 요청. `q=회 먹을 데`가 질의입니다. 엔진에 보내는 JSON도 질의라고 부릅니다.

**관련도 (relevance)**
"이 결과가 이 질의에 얼마나 맞나". 기본 정렬 기준(`sort=relevance`)입니다.

**랭킹 (ranking)**
결과를 어떤 순서로 줄 세울지 정하는 규칙. [ADR 0009](adr/0009-keyword-ranking-and-fallback.md)가 키워드 랭킹 규칙입니다.

**0건 (zero result)**
검색 결과가 하나도 없는 것. 0건 질의는 버리지 않고 로그에 기록합니다 — 사전에 없는 단어의 직접 증거이기 때문입니다.

**완화 재질의 (relaxed)**
엄격하게 찾아 0건이면, 조건을 풀어서 **한 번 더** 찾는 것. "모든 단어 포함"으로 0건이면 "70%만 포함"으로 다시 찾습니다. 응답에 `relaxed:true`로 알립니다.

**자동완성 (suggest)**
다 입력하기 전에 뒤를 채워주는 것. 본문 검색과 **다른 인덱스**를 씁니다. `/v1/suggest`. 규칙이 달라서 인덱스를 나눴습니다 ([ADR 0002](adr/0002-index-and-cluster-separation.md)).

**하이라이트 (highlight)**
결과에서 **어느 글자가 걸렸는지** 표시해주는 것. 형태소 분석이 제대로 적용됐는지 눈으로 확인하는 용도로 켜뒀습니다.

**페이징 (paging)**
결과를 10개씩 잘라서 반환하는 것. `from`(몇 번째부터) + `size`(몇 개). 벡터 엔진에는 `from` 개념이 없어서, 앞부터 다 받아 앱에서 잘라 씁니다.

## 2. Keyword search (Elasticsearch)

**Elasticsearch (ES)**
글자 기반 검색 엔진. 이 프로젝트의 키워드 검색을 담당합니다.

**BM25**
"이 문서가 이 검색어에 얼마나 맞나"를 점수로 매기는 **표준 공식**. 드물게 나오는 단어일수록 높은 점수를 주고, 문서가 길수록 점수를 깎습니다. 점수가 **수십 점대**로 나옵니다. 이것이 벡터 점수(0~1)와 합칠 수 없는 이유입니다.

**필드 (field)**
문서를 이루는 칸. 상호명·주소·카테고리 같은 것들.

**필드 가중치 (`name^5`)**
어떤 칸에서 걸렸는지에 따라 점수에 배수를 주는 것. `name^5` 면 상호명 매칭을 5배로 칩니다. 지금 값은 도메인 직관일 뿐 근거 데이터가 없습니다 (아키텍처 리뷰 #11).

**cross_fields**
여러 칸을 **한 칸처럼 붙여놓고** 매칭하는 방식. "역삼동 카페"의 `역삼동`은 주소 칸에, `카페`는 상호명 칸에 있어도 걸리게 합니다.

**edge_ngram**
단어를 **앞에서부터 잘라** 조각을 미리 저장하는 것. `스` → `스타` → `스타벅` → `스타벅스`. 자동완성 인덱스가 이것을 씁니다. 그래서 본문 인덱스와 따로 만듭니다.

**alias (별명)**
인덱스에 붙이는 별명. 앱은 별명만 부르고, 실제 인덱스는 뒤에서 바꿔 끼웁니다. `place_search` → `place_search_v10`.

**`_bulk`**
문서 여러 건을 **한 번의 요청으로** 넣는 ES API. 한 건씩 넣으면 네트워크 왕복이 병목입니다. 2,000건씩 묶어 보냅니다.

**샤드 / 레플리카 (shard / replica)**
인덱스를 분할한 조각 / 그 복사본. 분할하면 나눠서 빨리 찾고, 복사하면 하나 죽어도 버팁니다. 로컬 단일 노드라 실제로 나누지는 않았습니다. 확장 설계는 [ADR 0002](adr/0002-index-and-cluster-separation.md).

## 3. Korean text processing

**형태소 분석 (morphological analysis)**
한국어 문장을 **뜻을 가진 최소 단위로 분해하는 것**. `강남역맛집` → `강남역` + `맛집`. 영어는 띄어쓰기로 분해하면 되지만 한국어는 그렇지 않아서 반드시 필요합니다. [ADR 0008](adr/0008-korean-analyzer-komoran-vs-nori.md)의 주제입니다.

**분석기 (analyzer)**
"글자 → 검색 단위"로 바꾸는 처리 묶음. 색인할 때와 검색할 때 같은 것을 써야 합니다. 다르면 매칭이 오류 없이 깨집니다. 이 프로젝트에서 실제로 겪은 사고입니다.

**토큰 (token)**
분해된 결과 조각 하나.

**KOMORAN / nori**
한국어 형태소 분석기 두 종류. nori는 ES에 기본 내장, KOMORAN은 별도. KOMORAN을 골랐고, 최신 ES를 지원하지 않아 **플러그인을 직접 재포팅**했습니다.

**품사 (POS) / stoptags**
단어의 종류(명사·조사·어미…) / **버릴 품사 목록**. 조사(`~에서`)나 어미는 검색에 도움이 되지 않으므로 버립니다. stoptags는 보수적으로 유지합니다 ([ADR 0008](adr/0008-korean-analyzer-komoran-vs-nori.md)).

**사용자 사전 (user dictionary)**
분석기가 모르는 단어를 "이건 한 덩어리"라고 알려주는 목록. 원천 데이터에서 자동 생성(`build_komoran_dict.py`) + 사람이 관리하는 시드 사전, 두 갈래입니다.

## 4. Vector search

**임베딩 (embedding)**
문장을 **숫자 벡터로 바꾸는 것**. 뜻이 비슷하면 숫자도 비슷하게 나옵니다. `"회 먹을 데"` → `[0.03, -0.11, ...]` 384개 숫자.

**벡터 (vector) / 차원 (dimension)**
그 숫자 묶음 / 숫자의 개수. 우리 모델은 **384차원**입니다. 크면 표현력이 좋지만 저장·계산 비용이 늡니다.

**코사인 유사도 (cosine similarity)**
두 벡터가 얼마나 같은 방향을 보는지. **-1 ~ 1**, 클수록 비슷합니다. 벡터 검색의 점수가 이것입니다. 실제로는 0.8 근처에 몰려 나옵니다.

**L2 정규화 (normalize)**
벡터의 **길이를 1로 맞추는 것**. 방향만 남겨서 코사인 비교를 정확하게 합니다.

**ANN (근사 최근접 이웃)**
"정확히 제일 가까운 것"을 포기하고 **거의 가까운 것을 훨씬 빨리** 찾는 방법. 6만 개를 전부 비교하면 느리기 때문입니다. 6만 건에서 5ms 정도 나옵니다.

**HNSW**
ANN을 구현하는 대표적인 자료구조. 계층 그래프를 타고 내려가며 가까운 것을 찾습니다.
- `m` — 점 하나가 가질 이웃 수 (16)
- `ef_construct` — **만들 때** 얼마나 넓게 탐색할지 (100)
- `hnsw_ef` — **찾을 때** 얼마나 넓게 탐색할지 (128). 키우면 정확해지고 느려집니다.

**Qdrant**
벡터 전용 검색 엔진. 이 프로젝트의 의미 검색을 담당합니다.

**컬렉션 (collection)**
Qdrant에서 ES의 "인덱스"에 해당하는 것. `place_vec_v2` + alias `place_vec` — ES와 **똑같은 무중단 규약**을 썼습니다.

**payload**
벡터에 함께 포함되는 부가 데이터. 필터링과 화면 표시에 씁니다. 상호명·카테고리·지역·좌표만 넣고 주소는 뺐습니다 (토큰만 차지하고 의미가 없어서).

**문턱값 (min-score)**
"이만큼도 안 비슷하면 버린다"는 기준선. 벡터 검색은 **"없다"고 말할 줄 몰라서** 이 선이 없으면 아무 질의에나 답을 반환합니다. 현재 0.84입니다 ([ADR 0010](adr/0010-embedding-model-and-serving.md)).

**선택도 (selectivity)**
전체 대비 필터 적용 시 **남은** 후보의 비율. `sigungu=강남구`는 100% 남습니다 — 전부 강남구 데이터라 거를 게 없습니다. 강남역 반경 300m는 3% 남습니다. 남은 비율이 비슷해도 카테고리로 좁히면 결과가 사라지고 반경으로 좁히면 정상이었기 때문입니다 ([ADR 0010](adr/0010-embedding-model-and-serving.md) Threshold follow-up 2).

**추론 (inference)**
학습이 끝난 모델에 입력을 넣어 출력을 받는 것. **모델을 쓰는 쪽**의 일입니다. 벡터 색인 9분 중 **96.1%가 추론 시간**입니다.

**ONNX**
프레임워크에 매이지 않는 **모델 파일 형식**. 파이썬 없이도 실행할 수 있습니다. JVM 앱 안에서 모델을 실행하려고 이 형식을 골랐습니다.

**DJL (Deep Java Library)**
JVM에서 모델 추론을 실행하는 라이브러리. `TextEmbeddingTranslatorFactory`로 "문장 → 벡터"를 한 번에 처리합니다.

**pooling**
모델이 출력한 **토큰마다의 벡터**를 문장 벡터 하나로 합치는 방법. 평균(mean)을 많이 씁니다.

**`query:` / `passage:` 프리픽스**
e5 계열 모델이 **학습할 때 문장 앞에 붙였던 표식.** 쓸 때도 붙여야 합니다. 안 붙여도 에러가 발생하지 않고 품질만 나빠집니다. 그래서 함수를 둘로 분리했습니다.

**양자화 (quantization)**
모델 숫자의 정밀도를 낮춰(예: int8) 더 빠르고 가볍게 만드는 것. 품질은 조금 깎입니다. 아직 하지 않았습니다. 색인 시간을 줄일 후보로만 적어뒀습니다.

## 5. Hybrid search

**하이브리드 검색 (hybrid search)**
글자 검색과 의미 검색을 **둘 다 하고 결과를 합치는 것**. `/v1/hsearch`. 고정 세트 질의 20개에서 0건이 키워드 7 → 하이브리드 0으로 줄었습니다.

**RRF (Reciprocal Rank Fusion)**
**점수 대신 등수만으로** 여러 결과를 합치는 방법.
```
점수 = Σ  가중치 / (k + 그 채널에서의 등수)
```
BM25(수십 점)와 코사인(0~1)은 단위가 달라 더할 수 없습니다.

**`k` (RRF 완충값)**
등수 차이를 얼마나 평평하게 만들지. 기본 60. 60이면 1등(1/61)과 2등(1/62)이 거의 같아서, "양쪽이 다 찾았다"가 "한쪽 1등"을 이깁니다.

**후보 (candidates)**
합치기 전에 각 채널에서 조회하는 결과 수. 50개씩 조회합니다. 10개씩만 조회하면, 한쪽이 11등에 둔 정답은 다른 쪽이 1등을 줘도 결합에 포함되지 않습니다.

**채널 (channel)**
검색 경로 하나. 여기서는 `keyword` · `vector` · `hybrid` · `suggest`. 지표·로그를 채널별로 나눠 측정합니다. 합쳐 측정하면 어디가 느린지 모릅니다.

**degraded (반쪽 응답)**
채널 하나가 죽어도 **나머지로 답하고, 반쪽인 것을 알리는 것**. `/v1/hsearch` 응답의 `degraded` · `channels[].failed` 필드입니다.

**hydrate (채워 넣기)**
한 엔진에만 있는 정보를 다른 곳에서 **보충하는 것**. 벡터만 찾은 문서는 주소가 없어서 ES에서 한 번에 조회해 채워 반환합니다(mget).

## 6. Indexing pipeline and zero downtime

**원천 (source of truth)**
"진짜 데이터는 여기"라고 정한 한 곳. 나머지는 전부 여기서 파생됩니다. PostGIS가 원천입니다. ES·Qdrant는 **언제든 다시 만들 수 있는** 사본입니다.

**전체 재색인 (full reindex)**
처음부터 전부 새로 만드는 것. 매핑이 바뀌었을 때 씁니다.

**증분 색인 (incremental indexing)**
**바뀐 것만** 반영하는 것.

**watermark (기준선) / 체크포인트**
"여기까지는 처리했다"고 표시해두는 시각. 다음에는 그 뒤부터만 읽습니다. 키워드와 벡터가 **각자 따로** 가집니다 — 임베딩이 느려서 진도가 다르기 때문입니다.

**멱등 (idempotent)**
**여러 번 해도 결과가 같은 것.** 색인을 두 번 실행해도 문서가 두 개가 되면 안 됩니다. 문서 id를 `place_id`로 고정해서 보장합니다.

**소프트 삭제 (soft delete)**
행을 실제로 지우지 않고 `deleted_at`에 표시만 하는 것. 실제로 지우면 "지워졌다"는 사실을 증분 색인이 알 방법이 없습니다.

**무중단 스왑 (zero-downtime swap)**
새 인덱스를 다 만든 **뒤에** 별명을 한 번에 옮겨 끼우는 것. 검색이 끊기지 않습니다. 재색인 중 검색 90회·alias 20회 왕복 230회 요청에서 실패 0을 실측했습니다.

**역할 분리 (indexer / query node)**
색인기와 질의기를 **별도 아티팩트**로 나눈 것 (ADR 0011). 질의 노드에는 `/admin/*`이 없습니다. 색인 부하가 검색 지연에 새지 않게, 그리고 관리 API 노출면을 줄이기 위해서입니다.

## 7. Server and concurrency

**WebFlux / 리액티브 / 논블로킹**
요청을 기다리는 동안 **스레드를 붙잡지 않는** 방식. 적은 스레드로 많은 요청을 받습니다. 검색 서버는 대부분의 시간을 "엔진 응답 기다리기"로 보내서 잘 맞습니다 ([ADR 0006](adr/0006-api-runtime-reactive-vs-blocking.md)).

**코루틴 (coroutine) / `suspend`**
"기다리는 코드"를 **위에서 아래로 읽히게** 쓰면서도 논블로킹으로 실행되는 코틀린 기능. 콜백 지옥 없이 리액티브를 쓰려고 골랐습니다.

**팬아웃 (fan-out) / `async`**
여러 곳에 **동시에** 질의하고 모두 모아 쓰는 것. 순차로 부르면 두 지연의 **합**이지만, 팬아웃하면 **느린 쪽 하나**에 수렴합니다.

**Dispatchers.IO / Default**
기다리는 일(IO)용 스레드 풀 / **계산하는 일**(CPU)용 스레드 풀. 임베딩 추론은 계산이라 `Default`에서 실행합니다.

**세마포어 (semaphore)**
**동시에 들어갈 수 있는 인원 수**를 제한하는 장치. 추론기에 동시에 2개까지만 들어가게 합니다. 코어 수보다 많이 넣으면 서로 느려집니다.

**LRU 캐시**
자리가 차면 **가장 오래 안 쓴 것부터** 버리는 캐시. 같은 검색어의 벡터는 몇 번을 만들어도 같으므로 재계산하지 않습니다.

**R2DBC**
관계형 DB를 **논블로킹으로** 읽는 규격. JDBC의 리액티브 판. 지금은 쓰지 않습니다. 색인기가 Spring Batch 전환과 함께 JDBC로 내려왔습니다 (ADR 0013). 질의기는 여전히 리액티브입니다 (ADR 0006).

## 8. Data and geography

**PostGIS**
PostgreSQL에 **지리 기능**을 더한 확장. 좌표를 저장하고 거리·반경을 계산합니다.

**GiST 인덱스**
공간 데이터를 빨리 찾기 위한 인덱스 종류. "이 반경 안"을 빠르게 반환합니다.

**geo_point / geo_radius**
좌표 타입 / "이 점에서 몇 m 안" 필터. ES와 Qdrant 양쪽에 다 있습니다. 필터는 엔진에 넘깁니다. 앱에서 거르면 상위 N이 다 탈락해 결과가 빕니다.

**haversine (하버사인)**
지구를 구로 보고 두 좌표 사이 거리를 구하는 공식. 응답의 `distanceM`을 채울 때 씁니다.

**시군구 / 행정동**
행정 구역 단위. 강남구 / 역삼1동 같은 것. 필터 조건입니다. **`역삼동`은 없고 `역삼1동`·`역삼2동`만** 있습니다.

**`place_id`**
장소 하나를 가리키는 고유 값. 원천·ES·Qdrant를 잇는 열쇠입니다. ES 문서 id로도 그대로 써서 멱등성을 얻습니다.

**결정적 UUID**
같은 입력이면 **항상 같은 UUID**가 나오게 만드는 것. Qdrant는 id가 숫자나 UUID여야 해서, `place_id`를 UUID로 변환해 씁니다.

## 9. Observability and operations

**Micrometer / Prometheus**
앱이 지표를 기록하는 라이브러리 / 그 지표를 모아 보는 시스템. `/actuator/prometheus`로 노출합니다.

**p95 / p99 (꼬리 지연)**
"100명 중 95번째로 느린 사람"이 겪은 시간. 평균 10ms에 p99 500ms인 꼬리는 평균만으로는 보이지 않습니다.

**SLO**
"이 정도는 지키겠다"고 정해둔 목표선.

**단계 지표 (stage latency)**
한 채널 **안에서** 단계별로 분해해 측정하는 것. "벡터가 느리다"까지는 채널 지표로 알지만, 모델 문제인지 탐색 문제인지는 이것을 나눠야 압니다.

**질의 로그**
검색어와 결과 건수를 기록한 한 줄 JSON. ① 0건 질의 → 사전 후보 ② 질의–클릭 → 랭킹 근거. 앱 로그와 파일을 나눠뒀습니다.

**색인 지연 (index lag)**
원천이 바뀐 시각과 색인이 따라잡은 시각의 차이.

## 10. Quality and evaluation

**재현율 (recall)**
찾아야 할 것 중 **얼마나 찾아냈나**. 놓친 것이 적으면 높습니다. 하이브리드가 개선한 것은 이쪽입니다 (0건 7 → 0).

**정밀도 (precision)**
찾아온 것 중 **얼마나 맞나**. 엉뚱한 것이 적으면 높습니다. `차 고치는 곳` → 차병원사거리포차가 정밀도 문제입니다. 아직 고치지 못했습니다.

**nDCG**
"좋은 결과가 얼마나 위쪽에 있나"를 측정하는 표준 지표. **정답 데이터가 있어야** 계산할 수 있습니다. 정답 데이터는 `scripts/eval/golden_set.yaml`에 있습니다 — 25질의·정답 1,088건. 채점은 `score_golden_set.py`가 합니다.

**콜드스타트 (cold start)**
아무 정보도 없는 사용자·항목에 무엇을 보여줄지의 문제. 7단계 주제입니다 ([ADR 0005](adr/0005-cold-start-and-recommend-strategy.md)).

**쿠키리스 세션**
쿠키로 사람을 추적하지 않고 **한 번의 방문 흐름만** 다루는 방식. 재방문 추적으로 넘어가지 않는 것이 원칙입니다 ([ADR 0004](adr/0004-cookieless-session-model.md)).

## 11. Documentation and process

**ADR (Architecture Decision Record)**
**"왜 이렇게 정했는지"를 기록하는 짧은 문서.** 무엇을 골랐나보다 무엇을 포기했나가 더 중요합니다. [13편](adr/) 있습니다.

**아키텍처 리뷰**
스스로 찾은 결함 목록. 고친 것·못 고친 것·왜 못 고쳤는지를 같이 적습니다. [architecture-review.md](architecture-review.md)에 30건 있습니다.

**컴포지트 빌드 (composite build)**
서로 독립적인 여러 빌드를 **묶어서 한 번에 인식시키는** Gradle 방식. 저장소 루트에서 `search-api`와 ES 플러그인 빌드를 같이 열려고 썼습니다.
