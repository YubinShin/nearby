# 아키텍처 셀프 크리틱 (Step 5 기준)

색인 파이프라인과 검색 API(Step 0–5)를 스스로 뜯어보고 약점을 정리한다. "동작한다"와
"플랫폼으로 옳다"는 다르다. 각 항목에 **상태**(✅ 고침 / 📝 이월)와 근거를 붙였다.
이 문서 자체가 설계 판단의 기록이다.

## Tier 1 — 정확성 (고쳤음)

### #1 삭제가 반영되지 않는다 → ✅ 고침
증분 색인이 PostGIS에 *존재하는* 행만 읽어 upsert하면, 원천에서 삭제된 장소가 ES에 유령으로 남는다.
- **해결:** `place.deleted_at` 소프트 삭제 컬럼 + `BEFORE UPDATE` 트리거로 `updated_at` 자동 갱신.
  증분은 삭제된 행도 읽어 **ES `_bulk` delete**로 제거(멱등, 없는 문서 삭제 404는 정상 처리).
  전체 재색인은 `deleted_at is null`만 읽어 tombstone을 물리적으로 청소.
- **실측:** 소프트 삭제 1건 → 증분 → 64,239→64,238, 재색인 후에도 유지, `deleted_at=null` 복구 → 64,239.

### #2 watermark 단조성 가정이 깨진다 → ✅ 고침 (#1과 함께)
watermark를 "인덱스의 max(updated_at)"로 뽑으면, 삭제된 문서는 인덱스에서 사라져 max를 못 올린다
→ watermark가 삭제 지점을 못 넘어가 삭제 행을 매번 재처리. 또한 배치 내 색인 순서가 시간순이
아니면 실패한 옛 행을 건너뛸 수 있다.
- **해결:** watermark를 인덱스 내용과 분리해 **별도 체크포인트 문서**(`psp_index_checkpoint`)에 저장.
  전체 재색인이 시드를 심고, 증분이 처리한 델타의 최신 시각으로 전진. 삭제도 정상적으로 전진시킴.
- **실측:** 삭제 후 증분 재실행 → 0건(재처리 없음), 체크포인트가 삭제 지점을 넘어서 있음.
- **남은 한계:** 타임스탬프 기반이라 여전히 밀리초 경계·시계 역행에 이론적 취약. 운영에서는 **단조 증가
  version(bigint) 컬럼**이 가장 견고. 현재는 `date_trunc('milliseconds')`로 PG μs↔ES ms 불일치만 차단.

### #3 재색인 실패 시 고아 인덱스가 쌓인다 → ✅ 고침
`createNextVersion`으로 새 인덱스를 만든 뒤 적재가 실패하면, 스왑도 삭제도 안 된 인덱스가 디스크에 남는다.
- **해결:** `rebuildAndSwap`의 적재 구간을 try/catch로 감싸 실패 시 방금 만든 새 버전을 삭제하고 예외 전파.
  스왑 전 실패라 서빙 중인 인덱스에는 영향 없음.

## Tier 2 — 플랫폼/확장 (이월: 설계로 남기고 단계적 반영)

### #4 본문/자동완성 alias 스왑이 서로 원자적이지 않다 → 📝 이월
두 인덱스를 각각 스왑하는 사이 "search=v2, suggest=v1"인 순간이 존재. 우리 용도엔 무해하나
"두 인덱스 정합"을 주장할 순 없다. 필요 시 단일 `_aliases` 요청에 두 인덱스 액션을 함께 묶으면 원자화 가능.

### #5 색인기와 질의기가 한 앱에 있다 → ✅ 고침 (Step 4, 배포 단위 분리 가능)
`search-api`가 쓰기(색인)와 읽기(질의)를 겸했다. 둘은 스케일 특성·장애 도메인이 다르다(색인은
배치·무거움, 질의는 고빈도·저지연).
- **해결:** 패키지 경계(`index` / `query`)를 가르고, `psp.role.indexer` · `psp.role.query`
  스위치로 **같은 아티팩트를 두 역할로 나눠 띄우도록** 했다. 별도 Gradle 모듈로 쪼개지 않은 건
  설정·매핑·DTO가 중복되고 로컬 데모에서 얻는 게 적어서다 — **배포 단위 분리라는 실익만** 취했다.
- **실측:** `--psp.role.indexer=false` → `/v1/search` 200, `POST /admin/reindex` **404**,
  색인 lag 지표 미등록. `--psp.role.query=false` → `/v1/*` 전부 **404**, 증분 색인 200.
- **남은 한계:** 프로세스는 나뉘지만 **코드베이스는 하나**다. 진짜 조직 규모에선 릴리스 주기가
  엉킨다(질의 핫픽스가 색인 코드를 끌고 간다). 그때 모듈을 쪼개면 되고, 그 경계는 이미 그어져 있다.
  이것이 멀티클러스터의 전제 — 질의기가 독립하면 "어느 클러스터를 보나"는 설정 한 줄이 된다.

### #6 환경별 설정이 매핑에 박혀 있다 → 📝 이월
`place_search.json`에 `number_of_replicas: 0`, `number_of_shards: 1`이 하드코딩. 운영은 replica≥1 필요.
- **방향:** 스키마(매핑)와 환경설정(샤드/레플리카)을 분리 — 매핑은 공통, 샤드/레플리카는 환경 오버레이로.
  샤드 수 설계 근거(문서 수·노드 수·검색 동시성)도 함께 문서화 필요.

### #7 위치 정보의 진실 원천이 모호하다 → 📝 이월
`geom`(PostGIS)과 `location`(ES geo_point)이 이중으로 존재. 거리 랭킹의 기준이 어디인가?
- **방향:** PostGIS를 거리 계산의 진실 원천으로, ES `location`은 필터/부스팅 보조로 역할을 ADR에 명시.

### 멀티클러스터 분리 → 📝 설계 문서
JD의 "용도별 멀티클러스터 운영"은 로컬에서 ES 2대 + 용도별 클라이언트 빈으로 시연 가능하나,
메모리 비용 대비 개념적 이득이 적다. **앱 분리(#5)를 먼저** 하고, 멀티클러스터는 토폴로지
다이어그램 + ADR 확장으로 남긴다. 앱이 용도별 클라이언트로 라우팅하면 이미 *cluster-ready*.

## Tier 3 — 운영/품질 (Step 4 읽기 경로와 함께)

### #8 관측성이 없다 → ✅ 고침 (Step 4)
색인 lag, 질의 지연 등 지표가 전무했다. JD가 강조하는 "지표 기반 병목·장애 진단"의 근거가 없었다.
- **해결:** Micrometer + `/actuator/prometheus`. **채널별** 질의 지연(`psp_query_latency_seconds`,
  태그 `channel=keyword|suggest|vector`, `outcome`)과 **색인 lag**(`psp_index_lag_seconds`).
- **5단계에서 한 겹 더 쪼갰다.** 채널 지연만 보면 "벡터가 느리다"까지만 안다. 임베딩 추론과
  ANN 탐색은 고치는 방법이 완전히 다르므로(모델 교체·캐시 vs `ef`·샤딩) `psp_query_stage_latency_seconds`
  (`stage=embed|ann`)로 나눠 잰다. 실제로 이 분해가 **"27ms"가 워밍업 오염이었다**는 걸 드러냈다.
- **지표 정의를 실측으로 고쳤다.** 처음엔 lag을 `now − checkpoint`로 쟀는데, 원천이 하루 안 바뀌자
  **71,908초**가 찍혔다 — 완벽히 최신인데 20시간 뒤처진 것처럼 보였다. 이 지표로 알림을 걸었다면
  매일 밤 오탐이 울린다. `원천 max(updated_at) − checkpoint`로 바꿔 **따라잡았으면 0**이 되게 했다.
- **실측:** 0 → (원천 1건 수정) 72,341 → (증분 색인) 0. 지표가 실제로 반응함을 확인.
- **남은 것:** bulk 실패 카운터, 0건 질의 비율(폴백 부하의 선행 지표), 트레이싱(코루틴 컨텍스트 전파).

### #9 `/admin/reindex`가 무인증이다 → 📝 (완화만)
아무나 전체 재색인 트리거 = DoS 벡터. 로컬 전용이나 운영에선 관리자 인증·레이트리밋 필요.
- **완화:** 질의 전용 노드(`psp.role.indexer=false`)에는 이 경로가 **아예 없다**(404). 공개 트래픽을
  받는 노드에서 색인 API를 물리적으로 제거할 수 있게 됐다. 인증 자체는 여전히 없다.

### #10 자동완성 랭킹이 순진하다 → ✅ 부분 고침 (Step 4) · 원인 진단이 틀렸었다
- **원래 진단:** "term frequency로 정렬 → 임의의 스타*가 상위."
- **실측하니 달랐다.** BM25의 **필드 길이 정규화**가 이미 짧은 이름을 위로 올리고 있었다
  (`스타` 질의 1·2위가 상호명 `스타`). 진짜 문제는 **동점**이었다 — 상위 20건의 점수가 **3종**뿐이고,
  그 안의 순서는 ES 내부 doc id 순, 즉 세그먼트 병합·재색인·레플리카에 따라 **달라진다**.
- **해결:** ① `place_id` 2차 정렬로 동점 순서를 **결정적**으로 고정(실측: 5회 반복 결과 완전 일치).
  ② 접두 일치 가산점(`prefix` on `name.raw`) — 비접두 매칭 `e-스타치과` 57위→122위로 강등.
  ③ `name_length` 역수 — **기대만큼 안 먹혔다.** BM25 길이 정규화와 신호가 겹쳐 상위권은 대부분 불변
  (`강남`만 개선, `김밥`은 무변화). 비용이 필드 하나뿐이라 남겼다.
- **남은 한계:** 진짜 답은 **인기도(클릭·주문) 신호**인데 원천에 없다. `function_score` 구조는
  그대로 두고 함수만 갈아끼우면 되도록 만들어 뒀다. → [ADR 0009](adr/0009-keyword-ranking-and-fallback.md)

## Tier 4 — Step 4에서 새로 드러난 것

### #11 랭킹 가중치에 근거 데이터가 없다 → 🔨 진행 중 (선행 조건 확보)
`name^5 · branch^3 · category^2 · dong^1.5 · 주소^1`은 도메인 직관으로 정한 숫자다. 단위 테스트로
고정해 두었지만 **"이 값이 옳다"는 근거는 없다.**
- **진행:** 질의 로그(`QueryLog` → `logs/query.log`)를 사전 작업의 부산물로 확보했다. 랭킹 튜닝의
  선행 조건 절반이 채워진 셈 — 남은 절반은 **클릭 로그**다.
- **방향:** 질의–클릭 쌍으로 평가셋을 만들고 nDCG로 튜닝. 로그가 없으면 랭킹 튜닝은 취향 논쟁이 된다.

### #12 0건 폴백이 질의를 두 번 보낸다 → 📝
엄격 질의가 0건이면 완화 질의를 한 번 더 던진다. 0건일 때만 드는 비용이라 정상 경로는 안 느리지만,
0건 비율이 높은 서비스에선 그대로 부하다.
- **방향:** 0건 비율을 지표로 뽑고, 임계 초과 시 폴백을 끄거나 캐시. 근본 해결은 오타 교정·동의어.

### #13 형태소 분석 불일치가 검색 누락을 만든다 → ✅ 대부분 고침 · 원인 진단이 또 틀렸었다
- **원래 진단:** "사용자 사전이 없어서 오분석이 난다. 사전을 넣으면 된다."
- **실측하니 원인의 비중이 반대였다.** 상호명 64,239건에서 원문 글자가 색인에서 사라지는 비율을
  재보니, 피해의 대부분은 사전이 아니라 **1단계에서 정한 공격적 `stoptags`** 가 만들고 있었다.
  오분석된 토큰이 조사·의존명사로 태깅되면 필터가 그 글자를 통째로 지워, 그 가게는 **어떤 질의로도
  못 찾게** 된다.

| 구성 | 글자 유실 | 글자 불일치 |
|---|---|---|
| ① 1단계 상태 (사전X · 공격적) | 30.81% | 34.34% |
| ② stoptags 만 완화 | 8.36% | 16.98% |
| ③ ② + 사전 1,379개 | **5.57%** | **14.36%** |
| ④ POS 필터 없음 (하한) | 0.82% | 9.23% |

- **해결:** ① 플러그인에 `user_dictionary`·`fw_dictionary` 로딩 경로 추가. ② 원천에서 사전을
  자동 생성(`scripts/build_komoran_dict.py`, 1,379개). ③ **플러그인 기본 `stoptags` 를 보수적으로
  되돌림** — 색인량 8% 증가로 유실 12,000여 건을 되찾는 거래.
- **사전 설계에서 배운 것:** "원천의 명사를 넣는다"는 순진한 접근은 검색을 **악화**시킨다.
  카테고리는 이미 올바르게 분해되고(`돼지고기/구이/찜`), 상호명 통짜 등록은 부분 검색을 죽인다.
  기준을 **"분석기가 틀리게 아는 문자열"** 로 바꾸고, 어휘 경계 판정(분기 엔트로피 단순화)과
  최소 단위 우선 규칙을 넣어야 쓸 만해졌다.
- **사전을 세 층으로 만들었다:** 자동 추출(1,377) + 사람이 넣는 시드 `manual.dict`(21) +
  검색 로그 채굴(`QueryLog` → `mine_query_log.py`, 후보 제안까지 자동·채택은 사람).
  원천 기반은 *데이터에 있는 말*만 담고 *사용자가 치는 말*은 담지 못해서다(`브런치`가 그 예).
- **0건 질의를 두 종류로 가른다:** 원문 존재 여부를 분석과 무관한 wildcard 로 확인해
  `[분석실패]`(사전으로 해결됨) / `[데이터없음]`(사전 넣어도 그대로)로 표시. 구분하지 않으면
  "사전에 넣었는데 왜 그대로냐"를 반복하게 된다.
- **남은 한계:** 질의와 문서가 *똑같이* 깨지면 검색은 여전히 된다(표본 6,000건 중 519건이
  글자를 잃지만 그 이름으로 찾아진다). 손해는 재현율이 아니라 **정밀도**라, 지금의 유실률 지표로는
  그 부분이 안 보인다. 제대로 재려면 질의–클릭 평가셋이 필요하다(#11과 같은 전제).
  → [ADR 0008](adr/0008-korean-analyzer-komoran-vs-nori.md)

### #14 사전과 인덱스의 버전 불일치를 감지할 장치가 없다 → 📝 (신규)
사전 파일을 바꾸고 재색인을 안 하면, 색인은 옛 사전으로 질의는 새 사전으로 분석된다. 같은 글자가
서로 다르게 쪼개져 **매칭이 조용히 깨진다.** 지금은 규율(사전 바꾸면 재색인)로만 막고 있다.
- **방향:** 사전 파일 해시를 인덱스 메타데이터에 박고, 기동 시 불일치를 경고·차단.

## Tier 5 — Step 5(벡터 검색)에서 새로 드러난 것

### #15 벡터에 모델 버전이 기록되지 않는다 → 📝 (신규, #14와 동형)
임베딩 모델을 바꾸고 재색인을 안 하면, 문서 벡터는 옛 모델·질의 벡터는 새 모델이 된다. 두 벡터가
**다른 공간**에 놓여 유사도가 의미를 잃는데, 에러는 하나도 안 난다. 점수만 조용히 망가진다.
- 사전·인덱스 버전 불일치(#14)와 **정확히 같은 문제의 다른 얼굴**이다. 형태소든 임베딩이든,
  "색인과 질의가 같은 것을 봐야 한다"는 제약은 코드가 아니라 **운영 규율**로만 지켜지고 있다.
- **완화:** 추론을 앱 안에 두어(ADR 0010) 한 프로세스에서 갈라질 수 없게 했다. 하지만
  *색인 시점의 모델*과 *질의 시점의 모델*이 다른 배포일 수 있다는 건 그대로다.
- **방향:** 모델 식별자+버전을 컬렉션 메타(또는 payload)에 박고 기동 시 대조.

### #16 긴 적재의 **마지막 짧은 단계**가 실패하면 전부 잃는다 → 📝 (신규, 실제로 겪음)
벡터 전체 재색인에서 8분 33초를 들여 64,239건을 다 넣고, **alias 조회 URL 오타(404)** 하나로
500이 났다. 적재 자체는 성공했는데 스왑을 못 해서 결과적으로 무용지물.
- 적재분이 컬렉션에 남아 있어 alias만 손으로 붙여 복구했지만, **그 복구 경로가 API에 없다.**
  운영에서 8분(운영 규모면 몇 시간)짜리 작업이 마지막 1초 때문에 통째로 날아가는 구조다.
- **방향:** 적재와 스왑을 **따로 부를 수 있는 단계**로 나누기(`?swap=false` + `POST .../promote`).
  덤으로 "적재해두고 원할 때 승격"이라는 운영 시나리오가 열린다.
- 참고: 실패 시 정리(#3)를 **적재 구간에만** 걸어둔 판단은 결과적으로 옳았다. 스왑 실패까지
  정리 대상에 넣었다면 8분치 작업을 **자동으로** 지웠을 것이다.
- **스왑 자체는 무중단이 확인됐다** — alias 20회 왕복 스왑 중 검색 230회, 실패 0·빈 결과 0.
  즉 이 크리틱은 "스왑이 위험하다"가 아니라 **"스왑에 도달하지 못했을 때 복구할 길이 없다"** 이다.

### #17 벡터 채널은 "없다"고 말할 줄 모른다 → ⚠️ 완화 (6단계 하이브리드 + 문턱)
키워드는 안 맞으면 0건이지만 벡터는 **항상** 가장 가까운 것들을 준다.
- **완화 1 — 코사인 문턱(`min-score` 0.84).** 실측으로 고른 값. `스타벅스`(top-1 0.834)와
  `ㅁㄴㅇㄹ`(0.839)은 막힌다. 하지만 `차 고치는 곳`(0.842)은 못 막는다 — **0.008 차이다.**
- **원리적 한계는 그대로다.** 진짜 질의 top-1 은 0.844~0.883, 엉터리는 0.794~0.870 으로
  **분포가 겹친다.** 어떤 절대 문턱도 둘을 못 가른다.
- **완화 2 — 6단계 하이브리드(ADR 0003).** 실제로 칠 법한 질의 20개에서 0건이 10 → 1 로 줄었다.
- **하지만 RRF 가 #17 을 고치지는 못한다.** 키워드가 0건이면 결합해도 벡터 단독 결과다.
  `차 고치는 곳` → `차병원사거리포차` 는 하이브리드에서도 그대로 나온다. 6단계를 시작할 때
  "RRF 가 해결책"이라고 적었지만, **재보니 되찾기(recall)만 해결하고 걸러내기(precision)는
  해결하지 못했다.**
- **방향:** "맞는 게 있느냐"를 키워드가 **거부권**으로 행사하게 하는 것(키워드 0건이면 벡터
  단독 결과를 신뢰하지 않음)까지 가야 한다. 다만 그러면 `회 먹을 데`(키워드 0건, 벡터 정답)가
  같이 죽는다. **둘을 가르는 신호가 아직 없다** — 정답 데이터(#11) 없이는 튜닝도 불가능하다.

### #18 필터가 **실제로 좁혔는지**를 묻지 않고 문턱을 끈다 → 📝 (신규, 6단계)
벡터 채널은 엔진 필터가 하나라도 있으면 절대 문턱을 끈다(ADR 0010 후속). 문턱을 필터 없는
전체 코퍼스에서 재서 정했기 때문에 옳은 결정이지만, **필터의 선택도(selectivity)를 보지 않는다.**
- 지금 데이터는 전부 강남구라 `sigungu=강남구` 는 아무것도 걸러내지 않는데, 그것만으로
  문턱이 꺼져 `스타벅스` 가 `스타럭스포타커피`(0.834)를 되돌려준다.
- **방향:** 필터 통과 건수(Qdrant `count`)를 보고 코퍼스 대비 비율이 충분히 낮을 때만 끄거나,
  절대 문턱 대신 **필터된 집합 안에서의 상대 기준**(top-1 대비 낙폭)으로 바꾼다.
  둘 다 질의당 호출이 하나 늘어난다 — 근거 없이 먼저 붙이지 않았다.

### #19 하이브리드의 `total` 은 후보 풀 크기다 → 📝 (신규, 6단계)
`/v1/hsearch` 의 `total` 은 채널별 50건씩을 합친 유니크 수(최대 100)라, 코퍼스 매칭 수가 아니다.
페이지를 깊게 넘기면 조용히 결과가 끊긴다.
- 키워드 단독은 진짜 매칭 수(2,552)를 주는데 결합하면 92가 되니, **같은 이름의 필드가 채널마다
  다른 것을 센다.** 클라이언트가 페이지 수를 계산하면 틀린다.
- **방향:** 깊은 페이징을 아예 막거나(`MAX_PAGE` 를 후보 깊이에 맞춰 낮춤), `total` 대신
  `hasMore` 로 계약을 바꾼다. 후자가 검색 API 로선 더 정직하다.

### #20 파생 테이블의 변경을 증분 색인이 못 잡는다 → 📝 (신규, 브랜드 복원)
`place_brand` 는 우리가 만든 파생 테이블이라, 여기만 바뀌면 `place.updated_at` 이 움직이지 않는다.
증분 색인은 `place.updated_at` 워터마크만 보므로 **브랜드 변경이 조용히 반영되지 않는다.**
- 지금은 전체 재색인(17초)으로만 반영된다. 데이터가 커지면 그 비용이 그대로 늘어난다.
- **방향:** 파생 테이블에도 `updated_at` 을 두고 워터마크를 **둘 중 최댓값**으로 잡거나,
  브랜드 갱신 시 대상 `place` 행을 touch 한다. 후자가 단순하지만 원천을 파생이 건드리는 모양이 된다.
- 같은 형태의 문제: 사전·인덱스 버전 정합(#14), 벡터 모델 버전(#15) — **"입력이 바뀌었는데
  그 사실이 워터마크에 안 실린다"** 가 셋의 공통 뼈대다.

### #21 채널이 브랜드를 **서로 다르게 안다** → ⚠️ **부분 고침** (구조는 해결, 짧은 토큰은 남음)
키워드·자동완성은 `brandOf()`(복원 + 시드 사전)를 쓰는데, 벡터는 `r.brand`(복원분만)를 쓴다.
그래서 사전으로만 아는 브랜드를 벡터 채널이 통째로 모른다.

| 질의 | 키워드 | 벡터 | 하이브리드 합의 |
|---|---|---|---|
| `스타벅스`(복원분) | 86 | 26 | 10/10 |
| **`CU`**(사전분) | **187** | **0** | **0/10** |
| **`GS25`**(사전분) | **255** | **1** | **1/10** |
| `파리바게뜨` | 50 | 50 | 10/10 |

`파리바게뜨`가 멀쩡한 건 **상호명 자체에 그 글자가 있어서**다. 정규형이 상호명과 다른
브랜드(`CU`↔`씨유`, `GS25`↔`지에스25`)만 깨진다 — 즉 **사전이 하는 일이 정확히 벡터에서만 안 된다.**

- **같은 실수를 두 번 했다.** 스타벅스 때 "키워드만 고치면 채널이 어긋난다"를 겪고 고쳤는데,
  시드 사전을 붙이면서 벡터를 따라 고치지 않았다.
- **구조적 원인:** 브랜드를 정하는 규칙이 **두 벌**이다. `PlaceDocuments.brandOf()` 는 private 이고,
  `PlaceVectorText`·`PlaceVectors.payload` 는 `r.brand` 를 직접 읽는다.
- **고침:** 브랜드 결정을 `brand/Brands.kt` 한 곳으로 올렸다. 색인 문서·자동완성 label·
  임베딩 문장·Qdrant payload 가 전부 `Brands.resolve()` 를 쓴다. 규칙이 한 벌이면 한쪽만
  고치는 사고가 **날 수 없다.**
- **재발 방지선:** 세 경로를 한 테스트로 묶었다(`BrandsTest.색인 문서와 임베딩 문장과 payload 가
  같은 브랜드를 쓴다`). 어느 하나만 고치면 여기서 걸린다.
- **덤으로 잡은 것:** 표시와 임베딩의 기준이 다르다는 걸 테스트가 드러냈다. 표시는 **어떤 표기든**
  이미 있으면 안 붙이지만(`CU CU` 방지), 임베딩은 **정규형이 없을 때만** 붙여야 한다
  (`씨유역삼점` → `CU 씨유역삼점`, 그러나 `스타벅스` → `스타벅스 스타벅스` 는 안 됨).

### #22 브랜드 두 원천의 **갱신 경로가 완전히 다르다** → 📝 (신규)
같은 `brand` 필드를 채우는 두 원천이 서로 다른 방식으로 배포된다.

| 원천 | 사는 곳 | 갱신하려면 |
|---|---|---|
| 시드 사전 | 앱 리소스 `brands.tsv` | **앱 재배포** |
| 복원분 | DB `place_brand` | **셸 스크립트 실행**(`recover_brands.sh`) |

- 3단계에서 **색인 파이프라인을 앱 안에 두기로** 정했는데(`/admin/reindex`), 브랜드 복원만
  앱 밖 셸+SQL 이다. 앱은 `place_brand` 를 **읽기만 하고 만들지 않는다.**
- 결과: "브랜드를 고쳤다"가 사람마다 다른 뜻이 된다. 앱만 배포하면 한쪽만 갱신된다.
- **방향:** 복원도 `POST /admin/brands/recover` 로 앱 안에 넣어 한 경로로 모은다.
  (증분 색인이 이걸 못 잡는 문제는 #20 과 한 묶음이다.)

### #23 두 번째 원천이 **적재만 되고 아무도 안 쓴다** → 📝 (신규)
`place_localdata` 3,934건이 PostGIS 에 있는데 **앱 코드의 참조가 0건**이다. 브랜드 복원의
재료로만 쓰이고 검색에는 들어가지 않는다.

- 매일 갱신되는 원천인데 **증분 경로가 없다** — `load_localdata.sh` 전체 재적재뿐이다.
- 통합하려면 중복 제거가 필요하다(실측: 이름 완전일치 1,150건, 30m 안 이웃 없음 235건).
- **방향:** ① 통합해서 커버리지를 올리거나 ② **파생 전용 원천임을 이름·문서로 못박거나.**
  지금은 둘 다 아닌 상태라, 다음 사람이 "이건 왜 검색에 안 나오지"를 다시 조사하게 된다.

### #24 복원 결과를 **검토할 길이 없다** → 📝 (신규)
브랜드 86건이 맞는지 보려면 `psql` 을 직접 쳐야 한다. 조회 API 도, 리포트도 없다.

- 매칭 반경 `30m` 와 빈도 `5회` 는 **감도 분석 없이 정한 값**이다. 40m 떨어진 매장은 조용히 누락되고,
  4개짜리 브랜드도 조용히 버려진다. 얼마나 놓치는지 **모른다.**
- 문턱값(0.78→0.84)에서 겪은 것과 같은 종류의 위험이다 — **재보기 전엔 '설정 안 한 것'과 같다.**
- **방향:** `GET /admin/brands` 로 복원 목록·거리 분포를 노출하고, 반경·빈도를 바꿔가며
  건수 변화를 재본다.

### #25 읽기 경로가 색인 패키지에 의존한다 → ✅ 고침 (#21 과 같이)
`query/SearchModels.kt` 가 `index.BrandDictionary` 를 import 한다. 응답 모델이 색인 클래스를
가져다 쓰는 모양이라, 역할 분리(`psp.role.indexer=false`)의 의도와 어긋난다.
- 지금은 스프링 빈이 아니라 실제 고장은 없다. **경계가 흐려진 것**이 문제다.
- **고침:** `brand/` 패키지를 새로 만들어 `Brands` 를 옮겼다. 이제 `index`·`embed`·`vector`·
  `query` 가 **한 방향으로** 이걸 바라본다. #21 의 원인이 곧 이 경계 문제였다 —
  둘 것이 애매하니 각자 자기 자리에서 따로 판단했던 것이다.
