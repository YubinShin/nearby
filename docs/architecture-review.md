# 아키텍처 셀프 크리틱 (Step 3 기준)

색인 파이프라인(Step 0–3)을 스스로 뜯어보고 약점을 정리한다. "동작한다"와 "플랫폼으로 옳다"는
다르다. 각 항목에 **상태**(✅ 고침 / 📝 이월)와 근거를 붙였다. 이 문서 자체가 설계 판단의 기록이다.

## Tier 1 — 정확성 (고쳤음)

### #1 삭제가 반영되지 않는다 → ✅ 고침
증분 색인이 PostGIS에 *존재하는* 행만 읽어 upsert하면, 원천에서 삭제된 장소가 ES에 유령으로 남는다.
- **해결:** `place.deleted_at` 소프트 삭제 컬럼 + `BEFORE UPDATE` 트리거로 `updated_at` 자동 갱신.
  증분은 삭제된 행도 읽어 **ES `_bulk` delete**로 제거(멱등, 없는 문서 삭제 404는 정상 처리).
  전체 재색인은 `deleted_at is null`만 읽어 tombstone을 물리적으로 청소.
- **실측:** 소프트 삭제 1건 → 증분 → 64,239→64,238, 재색인 후에도 유지, `deleted_at=null` 복구 → 64,239.

### #2 watermark 단조성 가정이 깨진다 → ✅ 고침 (#1과 함께)
watermark를 "인덱스의 max(updated_at)"로 뽑으면, 삭제된 문서는 인덱스에서 사라져 max를 못 올린다
→ watermark가 삭제 지점을 못 넘어가 삭제 행을 매번 재처리. 또한 배치 내 색인 순서가 시간순이
아니면 실패한 옛 행을 건너뛸 수 있다.
- **해결:** watermark를 인덱스 내용과 분리해 **별도 체크포인트 문서**(`psp_index_checkpoint`)에 저장.
  전체 재색인이 시드를 심고, 증분이 처리한 델타의 최신 시각으로 전진. 삭제도 정상적으로 전진시킴.
- **실측:** 삭제 후 증분 재실행 → 0건(재처리 없음), 체크포인트가 삭제 지점을 넘어서 있음.
- **남은 한계:** 타임스탬프 기반이라 여전히 밀리초 경계·시계 역행에 이론적 취약. 운영에서는 **단조 증가
  version(bigint) 컬럼**이 가장 견고. 현재는 `date_trunc('milliseconds')`로 PG μs↔ES ms 불일치만 차단.

### #3 재색인 실패 시 고아 인덱스가 쌓인다 → ✅ 고침
`createNextVersion`으로 새 인덱스를 만든 뒤 적재가 실패하면, 스왑도 삭제도 안 된 인덱스가 디스크에 남는다.
- **해결:** `rebuildAndSwap`의 적재 구간을 try/catch로 감싸 실패 시 방금 만든 새 버전을 삭제하고 예외 전파.
  스왑 전 실패라 서빙 중인 인덱스에는 영향 없음.

## Tier 2 — 플랫폼/확장 (이월: 설계로 남기고 단계적 반영)

### #4 본문/자동완성 alias 스왑이 서로 원자적이지 않다 → 📝 이월
두 인덱스를 각각 스왑하는 사이 "search=v2, suggest=v1"인 순간이 존재. 우리 용도엔 무해하나
"두 인덱스 정합"을 주장할 순 없다. 필요 시 단일 `_aliases` 요청에 두 인덱스 액션을 함께 묶으면 원자화 가능.

### #5 색인기와 질의기가 한 앱에 있다 → 📝 이월 (Step 4에서 경계 분리)
`search-api`가 쓰기(색인)와 읽기(질의)를 겸한다. 둘은 스케일 특성·장애 도메인이 다르다(색인은 배치·무거움,
질의는 고빈도·저지연). **플랫폼이라면 indexer / query 서비스 분리.**
- **방향:** Step 4에서 질의 경로를 별도 서비스 경계로 분리. 이것이 멀티클러스터의 전제 —
  질의기가 독립하면 "어느 클러스터를 보나"는 설정 한 줄이 된다.

### #6 환경별 설정이 매핑에 박혀 있다 → 📝 이월
`place_search.json`에 `number_of_replicas: 0`, `number_of_shards: 1`이 하드코딩. 운영은 replica≥1 필요.
- **방향:** 스키마(매핑)와 환경설정(샤드/레플리카)을 분리 — 매핑은 공통, 샤드/레플리카는 환경 오버레이로.
  샤드 수 설계 근거(문서 수·노드 수·검색 동시성)도 함께 문서화 필요.

### #7 위치 정보의 진실 원천이 모호하다 → 📝 이월
`geom`(PostGIS)과 `location`(ES geo_point)이 이중으로 존재. 거리 랭킹의 기준이 어디인가?
- **방향:** PostGIS를 거리 계산의 진실 원천으로, ES `location`은 필터/부스팅 보조로 역할을 ADR에 명시.

### 멀티클러스터 분리 → 📝 설계 문서
JD의 "용도별 멀티클러스터 운영"은 로컬에서 ES 2대 + 용도별 클라이언트 빈으로 시연 가능하나,
메모리 비용 대비 개념적 이득이 적다. **앱 분리(#5)를 먼저** 하고, 멀티클러스터는 토폴로지
다이어그램 + ADR 확장으로 남긴다. 앱이 용도별 클라이언트로 라우팅하면 이미 *cluster-ready*.

## Tier 3 — 운영/품질 (Step 4 읽기 경로와 함께)

### #8 관측성이 없다 → 📝 Step 4
색인 lag, bulk 실패율, 질의 지연 등 지표가 전무. JD가 강조하는 "지표 기반 병목·장애 진단"의 근거가 없다.
- **방향:** Micrometer + **색인 lag 지표**(now − checkpoint), bulk 실패 카운터, 질의 latency 히스토그램.

### #9 `/admin/reindex`가 무인증이다 → 📝
아무나 전체 재색인 트리거 = DoS 벡터. 로컬 전용이나 운영에선 관리자 인증·레이트리밋 필요.

### #10 자동완성 랭킹이 순진하다 → 📝 Step 4
`match`라 term frequency로 정렬 → "스타" 입력 시 스타벅스가 아닌 임의의 스타* 가 상위. 인기도/길이
tie-break가 없다.
- **방향:** 인기도(로그·클릭) 신호를 색인해 function_score, 또는 completion suggester로 정렬 개선.
