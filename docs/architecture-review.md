# 아키텍처 리뷰 (Step 6 + 모듈 분리 기준)

색인 파이프라인과 검색 API(Step 0–6 + 모듈 분리)를 스스로 뜯어보고 약점을 정리합니다. "동작한다"와
"플랫폼으로 옳다"는 다릅니다. 각 항목에 **상태**(Fixed / Deferred)와 근거를 붙였습니다.

## 초기 설계 검토 (Step 0–3) — 정확성

### #1 삭제가 반영되지 않는다 → Fixed
증분 색인이 PostGIS에 *존재하는* 행만 읽어 upsert하면, 원천에서 삭제된 장소가 ES에 유령으로 남습니다.
- **해결:** `place.deleted_at` 소프트 삭제 컬럼 + `BEFORE UPDATE` 트리거로 `updated_at` 자동 갱신.
  증분은 삭제된 행도 읽어 **ES `_bulk` delete**로 제거(멱등, 없는 문서 삭제 404는 정상 처리).
  전체 재색인은 `deleted_at is null`만 읽어 tombstone을 물리적으로 청소.
- **실측:** 소프트 삭제 1건 → 증분 → 64,239→64,238, 재색인 후에도 유지, `deleted_at=null` 복구 → 64,239.

### #2 watermark 단조성 가정이 깨진다 → Fixed (#1과 함께)
watermark를 "인덱스의 max(updated_at)"로 뽑으면, 삭제된 문서는 인덱스에서 사라져 max를 못 올립니다
→ watermark가 삭제 지점을 못 넘어가 삭제 행을 매번 재처리. 또한 배치 내 색인 순서가 시간순이
아니면 실패한 옛 행을 건너뛸 수 있습니다.
- **해결:** watermark를 인덱스 내용과 분리해 **별도 체크포인트 문서**(`psp_index_checkpoint`)에 저장.
  전체 재색인이 시드를 심고, 증분이 처리한 델타의 최신 시각으로 전진. 삭제도 정상적으로 전진시킴.
- **실측:** 삭제 후 증분 재실행 → 0건(재처리 없음), 체크포인트가 삭제 지점을 넘어서 있음.
- **남은 한계:** 타임스탬프 기반이라 여전히 밀리초 경계·시계 역행에 이론적 취약. 운영에서는 **단조 증가
  version(bigint) 컬럼**이 가장 견고.
- **정정 (2026-07-25):** 한때 `date_trunc('milliseconds')`로 PG μs↔ES ms 불일치를 막으려 했는데,
  그 자름이 오히려 **같은 밀리초 안의 뒷행을 영구 누락**시켰습니다. ES 폴백 watermark 는 내림이라 원천보다
  항상 작거나 같고, 굵은 watermark 의 결과는 "몇 행 재처리"뿐(색인은 멱등)이라 자를 이유가 없었습니다.
  지금은 생값끼리 비교합니다 (`PlaceSql.SELECT_SINCE` 주석에 근거).

### #3 재색인 실패 시 고아 인덱스가 쌓인다 → Fixed
`createNextVersion`으로 새 인덱스를 만든 뒤 적재가 실패하면, 스왑도 삭제도 안 된 인덱스가 디스크에 남습니다.
- **해결:** `rebuildAndSwap`의 적재 구간을 try/catch로 감싸 실패 시 방금 만든 새 버전을 삭제하고 예외 전파.
  스왑 전 실패라 서빙 중인 인덱스에는 영향 없음.

## 초기 설계 검토 — 플랫폼/확장

### #4 본문/자동완성 alias 스왑이 서로 원자적이지 않다 → Deferred
두 인덱스를 각각 스왑하는 사이 "search=v2, suggest=v1"인 순간이 존재. 우리 용도엔 무해하나
"두 인덱스 정합"을 주장할 순 없습니다. 필요 시 단일 `_aliases` 요청에 두 인덱스 액션을 함께 묶으면 원자화 가능.

### #5 색인기와 질의기가 한 앱에 있다 → **Fixed — 완전** (Step 4 부분 → 모듈 분리, ADR 0011)
`search-api`가 쓰기(색인)와 읽기(질의)를 겸했습니다. 둘은 스케일 특성·장애 도메인이 다릅니다(색인은
배치·무거움, 질의는 고빈도·저지연).

- **1차 (Step 4, 부분):** 패키지 경계(`index` / `query`)를 가르고 `psp.role.*` 스위치로
  **같은 아티팩트를 두 역할로 나눠 띄우도록** 했습니다. 그때는 "모듈로 쪼개면 설정·DTO가 중복되고
  로컬 데모에서 얻는 게 적다"고 판단해 **배포 단위 분리라는 실익만** 취했습니다.
  실측: `--psp.role.indexer=false` → `/v1/search` 200, `POST /admin/reindex` **404**.
- **그 판단이 틀렸던 지점:** 플래그는 **같은 힙을 공유하는 사실**을 바꾸지 못합니다. 색인 쪽 OOM
  한 번이 곧 검색 장애입니다. 그리고
  **잘못 켜면 열립니다** — `psp.role.indexer=true` 가 실수로 켜지면 질의 노드에 색인 API가 노출됩니다.
- **2차 (ADR 0011, 완결):** `search-core` / `search-api` / `indexer-batch` 로 쪼개고
  `psp.role.*` 를 **전부 제거**했습니다. 모듈이 곧 역할입니다.
  실측: `search-api.jar` 안에 r2dbc/postgresql **0개**, `indexer`·`Admin` 클래스 **0개**.
  질의 앱이 원천 창고를 열 방법 **자체가 없습니다.** "중복될 것"이라던 설정·DTO는 `search-core` 와
  `core.yml` 로 한 벌만 두어 오히려 드리프트를 막는 장치가 됐습니다.
- **대가:** 한 프로세스가 강제하던 보호가 사라졌습니다 → #14·#15 참조(런타임 도장으로 되찾음).

### #6 환경별 설정이 매핑에 박혀 있다 → Deferred
`place_search.json`에 `number_of_replicas: 0`, `number_of_shards: 1`이 하드코딩. 운영은 replica≥1 필요.
- **방향:** 스키마(매핑)와 환경설정(샤드/레플리카)을 분리 — 매핑은 공통, 샤드/레플리카는 환경 오버레이로.
  샤드 수 설계 근거(문서 수·노드 수·검색 동시성)도 함께 문서화 필요.

### #7 위치 정보의 진실 원천이 모호하다 → Deferred
`geom`(PostGIS)과 `location`(ES geo_point)이 이중으로 존재. 거리 랭킹의 기준이 어디인가?
- **방향:** PostGIS를 거리 계산의 진실 원천으로, ES `location`은 필터/부스팅 보조로 역할을 ADR에 명시.

### 멀티클러스터 분리 → Deferred — 설계 문서
JD의 "용도별 멀티클러스터 운영"은 로컬에서 ES 2대 + 용도별 클라이언트 빈으로 시연 가능하나,
메모리 비용 대비 개념적 이득이 적습니다. **앱 분리(#5)를 먼저** 하고, 멀티클러스터는 토폴로지
다이어그램 + ADR 확장으로 남깁니다. 앱이 용도별 클라이언트로 라우팅하면 이미 *cluster-ready*.

## 초기 설계 검토 — 운영/품질

### #8 관측성이 없다 → Fixed (Step 4)
색인 lag, 질의 지연 등 지표가 전무했습니다. JD가 강조하는 "지표 기반 병목·장애 진단"의 근거가 없었습니다.
- **해결:** Micrometer + `/actuator/prometheus`. **채널별** 질의 지연(`psp_query_latency_seconds`,
  태그 `channel=keyword|suggest|vector`, `outcome`)과 **색인 lag**(`psp_index_lag_seconds`).
- **5단계에서 한 겹 더 쪼갰습니다.** 채널 지연만 보면 "벡터가 느리다"까지만 압니다. 임베딩 추론과
  ANN 탐색은 고치는 방법이 완전히 다르므로(모델 교체·캐시 vs `ef`·샤딩) `psp_query_stage_latency_seconds`
  (`stage=embed|ann`)로 나눠 잽니다. 실제로 이 분해가 **"27ms"가 워밍업 오염이었다**는 걸 드러냈습니다.
- **지표 정의를 실측으로 고쳤습니다.** 처음엔 lag을 `now − checkpoint`로 쟀는데, 원천이 하루 안 바뀌자
  **71,908초**가 찍혔습니다 — 완벽히 최신인데 20시간 뒤처진 것처럼 보였습니다. 이 지표로 알림을 걸었다면
  매일 밤 오탐이 울립니다. `원천 max(updated_at) − checkpoint`로 바꿔 **따라잡았으면 0**이 되게 했습니다.
- **실측:** 0 → (원천 1건 수정) 72,341 → (증분 색인) 0. 지표가 실제로 반응함을 확인.
- **반대 방향의 결함도 있었습니다 — 미탐 (2026-08-03 Fixed).** 게이지가 키워드 체크포인트만 읽어서
  (`CheckpointStore.PLACE_PIPELINE`), **벡터 색인이 아무리 밀려도 0** 이었습니다. 위 오탐 수정이
  "따라잡았는데 뒤처진 것처럼 보이는 것" 을 없앴다면, 이건 "뒤처졌는데 따라잡은 것처럼 보이는 것" 입니다.

| 시점 | keyword | vector | 옛 지표(단일) |
|---|---:|---:|---:|
| 원천 1건 touch 전 | 0 | 0 | 0 |
| touch 후 | 86,560 | 86,560 | 86,560 |
| **키워드 증분만 실행 후** | **0** | **86,560** | **0** ← 벡터가 하루치 밀렸는데 안 보임 |
| 벡터 증분 후 | 0 | 0 | 0 |

- **해결:** 게이지를 `pipeline={keyword,vector}` 태그로 나눴습니다. 질의 지연이 이미 `channel` 로
  나뉘어 있으니 같은 어휘를 씁니다. 벡터가 꺼진 노드(`psp.vector.enabled=false`)에서는 vector 게이지를
  **등록하지 않습니다** — 안 도는 파이프라인이 영원히 뒤처진 것처럼 보이는 새 오탐을 만들지 않기 위해서입니다.
- **주의:** 태그 없는 `psp_index_lag_seconds` 시계열은 더 이상 나오지 않습니다. 그걸 보던 알림·대시보드는
  `pipeline` 을 붙여야 합니다.
- **남은 것:** bulk 실패 카운터, 0건 질의 비율(폴백 부하의 선행 지표), 트레이싱(코루틴 컨텍스트 전파).

### #9 `/admin/reindex`가 무인증이다 → Deferred (완화만)
아무나 전체 재색인 트리거 = DoS 벡터. 로컬 전용이나 운영에선 관리자 인증·레이트리밋 필요.
- **완화:** 질의 앱(`search-api`)에는 이 경로가 **아예 없습니다.** 처음엔 `psp.role.indexer=false`
  플래그로 껐는데(404), 플래그는 잘못 켜면 열립니다. ADR 0011 로 별도 아티팩트가 되면서
  **클래스 자체가 jar 에 없습니다**(검증: `search-api.jar` 에 `Admin` 0개). 공개 트래픽을 받는 노드에서
  색인 API 를 물리적으로 제거하는 것이 설정이 아니라 빌드로 보장됩니다. 인증 자체는 여전히 없습니다.

### #10 자동완성 랭킹이 순진하다 → Partial (Step 4) · 원인 진단이 틀렸었다
- **원래 진단:** "term frequency로 정렬 → 임의의 스타*가 상위."
- **실측하니 달랐습니다.** BM25의 **필드 길이 정규화**가 이미 짧은 이름을 위로 올리고 있었습니다
  (`스타` 질의 1·2위가 상호명 `스타`). 진짜 문제는 **동점**이었습니다 — 상위 20건의 점수가 **3종**뿐이고,
  그 안의 순서는 ES 내부 doc id 순, 즉 세그먼트 병합·재색인·레플리카에 따라 **달라집니다**.
- **해결:** ① `place_id` 2차 정렬로 동점 순서를 **결정적**으로 고정(실측: 5회 반복 결과 완전 일치).
  ② 접두 일치 가산점(`prefix` on `name.raw`) — 비접두 매칭 `e-스타치과` 57위→122위로 강등.
  ③ `name_length` 역수 — **기대만큼 안 먹혔습니다.** BM25 길이 정규화와 신호가 겹쳐 상위권은 대부분 불변
  (`강남`만 개선, `김밥`은 무변화). 비용이 필드 하나뿐이라 남겼습니다.
- **남은 한계:** 진짜 답은 **인기도(클릭·주문) 신호**인데 원천에 없습니다. `function_score` 구조는
  그대로 두고 함수만 갈아끼우면 되도록 만들어 뒀습니다. → [ADR 0009](adr/0009-keyword-ranking-and-fallback.md)

## Step 4 (키워드 API)에서 드러난 것

### #11 랭킹 가중치에 근거 데이터가 없다 → In progress (선행 조건 확보)
`name^5 · branch^3 · category^2 · dong^1.5 · 주소^1`은 도메인 직관으로 정한 숫자입니다. 단위 테스트로
고정해 두었지만 **"이 값이 옳다"는 근거는 없습니다.**
- **진행:** 질의 로그(`QueryLog` → `logs/query.log`)를 사전 작업의 부산물로 확보했습니다. 랭킹 튜닝의
  선행 조건 절반이 채워진 셈 — 남은 절반은 **클릭 로그**입니다.
- **방향:** 질의–클릭 쌍으로 평가셋을 만들고 nDCG로 튜닝. 로그가 없으면 랭킹 튜닝은 취향 논쟁이 됩니다.

### #12 0건 폴백이 질의를 두 번 보낸다 → Deferred
엄격 질의가 0건이면 완화 질의를 한 번 더 던집니다. 0건일 때만 드는 비용이라 정상 경로는 안 느리지만,
0건 비율이 높은 서비스에선 그대로 부하입니다.
- **방향:** 0건 비율을 지표로 뽑고, 임계 초과 시 폴백을 끄거나 캐시. 근본 해결은 오타 교정·동의어.

### #13 형태소 분석 불일치가 검색 누락을 만든다 → Fixed (대부분) · 원인 진단이 또 틀렸었다
- **원래 진단:** "사용자 사전이 없어서 오분석이 난다. 사전을 넣으면 된다."
- **실측하니 원인의 비중이 반대였습니다.** 상호명 64,239건에서 원문 글자가 색인에서 사라지는 비율을
  재보니, 피해의 대부분은 사전이 아니라 **1단계에서 정한 공격적 `stoptags`** 가 만들고 있었습니다.
  오분석된 토큰이 조사·의존명사로 태깅되면 필터가 그 글자를 통째로 지워, 그 가게는 **어떤 질의로도
  못 찾게** 됩니다.

| 구성 | 글자 유실 | 글자 불일치 |
|---|---|---|
| ① 1단계 상태 (사전X · 공격적) | 30.81% | 34.34% |
| ② stoptags 만 완화 | 8.36% | 16.98% |
| ③ ② + 사전 1,379개 | **5.57%** | **14.36%** |
| ④ POS 필터 없음 (하한) | 0.82% | 9.23% |

- **해결:** ① 플러그인에 `user_dictionary`·`fw_dictionary` 로딩 경로 추가. ② 원천에서 사전을
  자동 생성(`scripts/build_komoran_dict.py`, 1,379개). ③ **플러그인 기본 `stoptags` 를 보수적으로
  되돌림** — 색인량 8% 증가로 유실 12,000여 건을 되찾는 거래.
- **사전 설계에서 배운 것:** "원천의 명사를 넣는다"는 순진한 접근은 검색을 **악화**시킵니다.
  카테고리는 이미 올바르게 분해되고(`돼지고기/구이/찜`), 상호명 통짜 등록은 부분 검색을 죽입니다.
  기준을 **"분석기가 틀리게 아는 문자열"** 로 바꾸고, 어휘 경계 판정(분기 엔트로피 단순화)과
  최소 단위 우선 규칙을 넣어야 쓸 만해졌습니다.
- **사전을 세 층으로 만들었습니다:** 자동 추출(1,377) + 사람이 넣는 시드 `manual.dict`(21) +
  검색 로그 채굴(`QueryLog` → `mine_query_log.py`, 후보 제안까지 자동·채택은 사람).
  원천 기반은 *데이터에 있는 말*만 담고 *사용자가 치는 말*은 담지 못해서입니다(`브런치`가 그 예).
- **0건 질의를 두 종류로 가릅니다:** 원문 존재 여부를 분석과 무관한 wildcard 로 확인해
  `[분석실패]`(사전으로 해결됨) / `[데이터없음]`(사전 넣어도 그대로)로 표시. 구분하지 않으면
  "사전에 넣었는데 왜 그대로냐"를 반복하게 됩니다.
- **남은 한계:** 질의와 문서가 *똑같이* 깨지면 검색은 여전히 됩니다(표본 6,000건 중 519건이
  글자를 잃지만 그 이름으로 찾아진다). 손해는 재현율이 아니라 **정밀도**라, 지금의 유실률 지표로는
  그 부분이 안 보입니다. 제대로 재려면 질의–클릭 평가셋이 필요합니다(#11과 같은 전제).
  → [ADR 0008](adr/0008-korean-analyzer-komoran-vs-nori.md)

### #14 사전과 인덱스의 버전 불일치를 감지할 장치가 없다 → **Partial** (ADR 0011)
사전 파일을 바꾸고 재색인을 안 하면, 색인은 옛 사전으로 질의는 새 사전으로 분석됩니다. 같은 글자가
서로 다르게 쪼개져 **매칭이 조용히 깨집니다.** 지금은 규율(사전 바꾸면 재색인)로만 막고 있었습니다.
- **고친 부분:** 모듈 분리와 함께 **런타임 버전 도장**(`IndexMeta`)을 도입했습니다. 색인기가 alias
  스왑 성공 후 `psp_index_meta` 에 계약을 남기고, 질의기가 기동 시 대조해 **다르면 뜨지 않습니다.**
  실측: `SCHEMA_VERSION` 을 2로 올리자 질의기가 기동에 실패했습니다(어긋난 항목·조치까지 메시지에 포함).
  ES 매핑·문서 스키마가 바뀌면 이 상수를 올리는 것이 규율이 됐습니다.
- **아직 남은 부분:** **사전 해시는 도장에 없습니다.** 사전이 ES 플러그인 쪽에 있어 앱이 읽기 어렵습니다.
  지금은 **매일 전체 재색인**(ADR 0011 결정 6)이 쓸어내는 것으로 대신합니다 — 어떤 사전 드리프트도
  24시간 이상 살아남지 못합니다. 사전 해시를 도장에 넣는 것이 이 항목의 완전한 해결입니다.

## Step 5·6 (벡터·하이브리드)에서 드러난 것

### #15 벡터에 모델 버전이 기록되지 않는다 → **Fixed** (ADR 0011, #14와 동형)
임베딩 모델을 바꾸고 재색인을 안 하면, 문서 벡터는 옛 모델·질의 벡터는 새 모델이 됩니다. 두 벡터가
**다른 공간**에 놓여 유사도가 의미를 잃는데, 에러는 하나도 안 납니다. 점수만 조용히 망가집니다.
- 사전·인덱스 버전 불일치(#14)와 **정확히 같은 문제의 다른 얼굴**입니다. 형태소든 임베딩이든,
  "색인과 질의가 같은 것을 봐야 한다"는 제약은 코드가 아니라 **운영 규율**로만 지켜지고 있습니다.
- **완화(당시):** 추론을 앱 안에 두어(ADR 0010) 한 프로세스에서 갈라질 수 없게 했습니다. 하지만
  *색인 시점의 모델*과 *질의 시점의 모델*이 다른 배포일 수 있다는 건 그대로였습니다. 그리고 모듈을
  쪼개면서(ADR 0011) 그 완화마저 사라졌습니다 — 이 항목을 **먼저 닫아야** 분리가 안전해졌습니다.
- **해결:** 색인기가 alias 스왑 성공 후 **실제로 로드된 모델**의 식별자·차원을 도장에 남깁니다
  (설정값이 아니라 로드 결과라, 설정만 맞고 파일이 다른 경우까지 잡힌다). 질의기는 기동 시
  대조하고 다르면 뜨지 않습니다. 증분 색인도 도장이 다르면 **거부**합니다 — 한 컬렉션에 두 모델의
  벡터가 섞이는 것을 사후 감지가 아니라 **사전 차단**으로 막습니다.
- **여기서 배운 것:** 위에 적어둔 "컬렉션 메타에 박고" 라는 방향은 **실제로는 불가능했습니다.**
  Qdrant 1.12 는 모르는 필드를 `{"result":true,"status":"ok"}` 로 받아놓고 **조용히 버립니다.**
  하필 이 기능이 막으려는 바로 그 실패 방식이라, 확인 없이 갔다면 "도장을 찍었다"고 믿으면서
  아무것도 안 찍혔을 것입니다. 그래서 도장은 ES 문서(`psp_index_meta`)에 모았습니다.

### #16 긴 적재의 **마지막 짧은 단계**가 실패하면 전부 잃는다 → Deferred (신규, 실제로 겪음)
벡터 전체 재색인에서 8분 33초를 들여 64,239건을 다 넣고, **alias 조회 URL 오타(404)** 하나로
500이 났습니다. 적재 자체는 성공했는데 스왑을 못 해서 결과적으로 무용지물.
- 적재분이 컬렉션에 남아 있어 alias만 손으로 붙여 복구했지만, **그 복구 경로가 API에 없습니다.**
  운영에서 8분(운영 규모면 몇 시간)짜리 작업이 마지막 1초 때문에 통째로 날아가는 구조입니다.
- **방향:** 적재와 스왑을 **따로 부를 수 있는 단계**로 나누기(`?swap=false` + `POST .../promote`).
  덤으로 "적재해두고 원할 때 승격"이라는 운영 시나리오가 열립니다.
- 참고: 실패 시 정리(#3)를 **적재 구간에만** 걸어둔 판단은 결과적으로 옳았습니다. 스왑 실패까지
  정리 대상에 넣었다면 8분치 작업을 **자동으로** 지웠을 것입니다.
- **그 성질이 한때 사라졌다가 되살아났습니다.** Spring Batch 전환(ADR 0013)에서 정리가
  `JobExecutionListener` 가 되면서 job 전체를 덮게 됐고, 스왑이 실패하면 다 채운 인덱스·컬렉션을
  지우는 상태였습니다. 2026-08-03 에 "적재 스텝이 COMPLETED 면 지우지 않는다" 규칙으로 되돌렸습니다(#27).
  다만 **적재와 스왑을 따로 부를 수 있게 나누는 것**은 여전히 안 했습니다 — 이 항목은 그대로 Deferred 입니다.
- **스왑 자체는 무중단이 확인됐습니다** — alias 20회 왕복 스왑 중 검색 230회, 실패 0·빈 결과 0.
  즉 이 항목은 "스왑이 위험하다"가 아니라 **"스왑에 도달하지 못했을 때 복구할 길이 없다"** 입니다.

### #17 벡터 채널은 "없다"고 말할 줄 모른다 → Mitigated (6단계 하이브리드 + 문턱)
키워드는 안 맞으면 0건이지만 벡터는 **항상** 가장 가까운 것들을 줍니다.
- **완화 1 — 코사인 문턱(`min-score` 0.84).** 실측으로 고른 값. `스타벅스`(top-1 0.834)와
  `ㅁㄴㅇㄹ`(0.839)은 막힙니다. 하지만 `차 고치는 곳`(0.842)은 못 막습니다 — **0.008 차이입니다.**
- **원리적 한계는 그대로입니다.** 진짜 질의 top-1 은 0.844~0.883, 엉터리는 0.794~0.870 으로
  **분포가 겹칩니다.** 어떤 절대 문턱도 둘을 못 가릅니다.
- **완화 2 — 6단계 하이브리드(ADR 0003).** 고정 세트 질의 20개(`scripts/queries_regression.txt`)에서
  0건이 키워드 7 → 하이브리드 0 이 됐습니다 (2026-07-29 재측정).
- **하지만 RRF 가 #17 을 고치지는 못합니다.** 키워드가 0건이면 결합해도 벡터 단독 결과입니다.
  `차 고치는 곳` → `차병원사거리포차` 는 하이브리드에서도 그대로 나옵니다. 6단계를 시작할 때
  "RRF 가 해결책"이라고 적었지만, **재보니 되찾기(recall)만 해결하고 걸러내기(precision)는
  해결하지 못했습니다.**
- **방향:** "맞는 게 있느냐"를 키워드가 **거부권**으로 행사하게 하는 것(키워드 0건이면 벡터
  단독 결과를 신뢰하지 않음)까지 가야 합니다. 다만 그러면 `회 먹을 데`(키워드 0건, 벡터 정답)가
  같이 죽습니다. **둘을 가르는 신호가 아직 없습니다** — 정답 데이터(#11) 없이는 튜닝도 불가능합니다.

### #18 필터가 **실제로 좁혔는지**를 묻지 않고 문턱을 끈다 → Fixed
벡터 채널은 엔진 필터가 하나라도 있으면 절대 문턱을 껐습니다(ADR 0010 후속). 문턱을 필터 없는
전체 코퍼스에서 재서 정했기 때문에 옳은 결정이지만, **필터의 선택도(selectivity)를 보지 않았습니다.**
- 지금 데이터는 전부 강남구라 `sigungu=강남구` 는 아무것도 걸러내지 않는데, 그것만으로
  문턱이 꺼져 `스타벅스` 검색어가 `스타럭스포타커피`(0.834)를 반환하였습니다.
- **기각한 대안:** 남은 비율(선택도) 기준. 카테고리 `과학·기술`(0.290)은 진짜 질의 20개 중
  13개를 0건으로 만들고 반경 1000m(0.163)는 0개입니다 — 남긴 양은 점수 하락의 예측 변수가
  아닙니다 (ADR 0010 문턱값 후속 2).
- **해결:** 후보가 **한 건도 빠지지 않은** 필터에만 문턱을 유지합니다. 그때는 후보 집합이 필터
  없을 때와 같은 집합이라 점수 분포가 같다는 것이 재보지 않아도 참입니다.
- **실측:** 개수를 세는 대신 여집합(`must_not`)을 `limit: 1` 로 조회해 빠진 것이 있는지만 봅니다.
  1.2ms — 개수를 다 세면 12ms, 전체와 필터를 각각 세면 25ms 입니다.

### #19 하이브리드의 `total` 은 후보 풀 크기다 → Deferred (신규, 6단계)
`/v1/hsearch` 의 `total` 은 채널별 50건씩을 합친 유니크 수(최대 100)라, 코퍼스 매칭 수가 아닙니다.
페이지를 깊게 넘기면 조용히 결과가 끊깁니다.
- 키워드 단독은 진짜 매칭 수(2,552)를 주는데 결합하면 92가 되니, **같은 이름의 필드가 채널마다
  다른 것을 셉니다.** 클라이언트가 페이지 수를 계산하면 틀립니다.
- **방향:** 깊은 페이징을 아예 막거나(`MAX_PAGE` 를 후보 깊이에 맞춰 낮춤), `total` 대신
  `hasMore` 로 계약을 바꿉니다. 후자가 검색 API 로선 더 정직합니다.

### #20 파생 테이블의 변경을 증분 색인이 못 잡는다 → Deferred (신규, 브랜드 복원)
`place_brand` 는 우리가 만든 파생 테이블이라, 여기만 바뀌면 `place.updated_at` 이 움직이지 않습니다.
증분 색인은 `place.updated_at` 워터마크만 보므로 **브랜드 변경이 조용히 반영되지 않습니다.**
- 지금은 전체 재색인(17초)으로만 반영됩니다. 데이터가 커지면 그 비용이 그대로 늘어납니다.
- **방향:** 파생 테이블에도 `updated_at` 을 두고 워터마크를 **둘 중 최댓값**으로 잡거나,
  브랜드 갱신 시 대상 `place` 행을 touch 합니다. 후자가 단순하지만 원천을 파생이 건드리는 모양이 됩니다.
- 같은 형태의 문제: 사전·인덱스 버전 정합(#14), 벡터 모델 버전(#15) — **"입력이 바뀌었는데
  그 사실이 워터마크에 안 실린다"** 가 셋의 공통 뼈대입니다.

### #21 채널이 브랜드를 **서로 다르게 안다** → **Partial** (구조는 해결, 짧은 토큰은 남음)
키워드·자동완성은 `brandOf()`(복원 + 시드 사전)를 쓰는데, 벡터는 `r.brand`(복원분만)를 씁니다.
그래서 사전으로만 아는 브랜드를 벡터 채널이 통째로 모릅니다.

| 질의 | 키워드 | 벡터 | 하이브리드 합의 |
|---|---|---|---|
| `스타벅스`(복원분) | 86 | 26 | 10/10 |
| **`CU`**(사전분) | **187** | **0** | **0/10** |
| **`GS25`**(사전분) | **255** | **1** | **1/10** |
| `파리바게뜨` | 50 | 50 | 10/10 |

`파리바게뜨`가 멀쩡한 건 **상호명 자체에 그 글자가 있어서**입니다. 정규형이 상호명과 다른
브랜드(`CU`↔`씨유`, `GS25`↔`지에스25`)만 깨집니다 — 즉 **사전이 하는 일이 정확히 벡터에서만 안 됩니다.**

- **같은 실수를 두 번 했습니다.** 스타벅스 때 "키워드만 고치면 채널이 어긋난다"를 겪고 고쳤는데,
  시드 사전을 붙이면서 벡터를 따라 고치지 않았습니다.
- **구조적 원인:** 브랜드를 정하는 규칙이 **두 벌**입니다. `PlaceDocuments.brandOf()` 는 private 이고,
  `PlaceVectorText`·`PlaceVectors.payload` 는 `r.brand` 를 직접 읽습니다.
- **고침:** 브랜드 결정을 `brand/Brands.kt` 한 곳으로 올렸습니다. 색인 문서·자동완성 label·
  임베딩 문장·Qdrant payload 가 전부 `Brands.resolve()` 를 씁니다. 규칙이 한 벌이면 한쪽만
  고치는 사고가 **날 수 없습니다.**
- **재발 방지선:** 세 경로를 한 테스트로 묶었습니다(`BrandsTest.색인 문서와 임베딩 문장과 payload 가
  같은 브랜드를 쓴다`). 어느 하나만 고치면 여기서 걸립니다.
- **덤으로 잡은 것:** 표시와 임베딩의 기준이 다르다는 걸 테스트가 드러냈습니다. 표시는 **어떤 표기든**
  이미 있으면 안 붙이지만(`CU CU` 방지), 임베딩은 **정규형이 없을 때만** 붙여야 합니다
  (`씨유역삼점` → `CU 씨유역삼점`, 그러나 `스타벅스` → `스타벅스 스타벅스` 는 안 됨).

### #22 브랜드 두 원천의 **갱신 경로가 완전히 다르다** → Deferred (신규)
같은 `brand` 필드를 채우는 두 원천이 서로 다른 방식으로 배포됩니다.

| 원천 | 사는 곳 | 갱신하려면 |
|---|---|---|
| 시드 사전 | 앱 리소스 `brands.tsv` | **앱 재배포** |
| 복원분 | DB `place_brand` | **셸 스크립트 실행**(`recover_brands.sh`) |

- 3단계에서 **색인 파이프라인을 앱 안에 두기로** 정했는데(`/admin/reindex`), 브랜드 복원만
  앱 밖 셸+SQL 입니다. 앱은 `place_brand` 를 **읽기만 하고 만들지 않습니다.**
- 결과: "브랜드를 고쳤다"가 사람마다 다른 뜻이 됩니다. 앱만 배포하면 한쪽만 갱신됩니다.
- **방향:** 복원도 `POST /admin/brands/recover` 로 앱 안에 넣어 한 경로로 모읍니다.
  (증분 색인이 이걸 못 잡는 문제는 #20 과 한 묶음입니다.)

### #23 두 번째 원천이 **적재만 되고 아무도 안 쓴다** → Deferred (신규)
`place_localdata` 3,934건이 PostGIS 에 있는데 **앱 코드의 참조가 0건**입니다. 브랜드 복원의

- **방향:** ① 통합해서 커버리지를 올리거나 ② **파생 전용 원천임을 이름·문서로 못박거나.**
  지금은 둘 다 아닌 상태라, 다음 사람이 "이건 왜 검색에 안 나오지"를 다시 조사하게 됩니다.

### #24 복원 결과를 **검토할 길이 없다** → Deferred (신규)

## 모듈 분리(ADR 0011) 실측에서 드러난 것

### #26 Jackson이 **두 개** 올라와 있는데 Kotlin 모듈이 한쪽에만 붙어 있었다 → Fixed
분리 후 회귀 측정을 돌리다가 `/v1/search?q=CU` 가 **187건을 200 OK 로** 돌려주면서 결과의
이름·주소가 **전부 빈 문자열**인 것을 발견했습니다. `total` 도 하이라이트도 정상이었습니다 —
그건 ES 메타데이터라서. `_source` 에서 오는 값만 사라졌고 에러 로그는 없었습니다.

| 누가 | 어떤 Jackson | Kotlin 모듈 |
|---|---|---|
| Spring Boot 4 (웹 직렬화) | Jackson 3 (`tools.jackson`) | 있음 |
| ES 자바 클라이언트 | Jackson 2 (`com.fasterxml.jackson`) | **없음** |

Kotlin 모듈 없는 Jackson 2 는 `val` 뿐인 data class 를 만나면 합성 무인자 생성자로 객체를 만든 뒤
세터가 없어 못 채웁니다. 그래서 **예외 없이 전부 기본값**(`""`·`null`·`0`)이 됩니다.

- **영향이 조회에 그치지 않았습니다.** `CheckpointStore.Checkpoint` 를 항상 못 읽어 증분 색인이
  매번 인덱스 max 로 폴백했습니다 — **#1·#2를 고치려고 만든 체크포인트 장치가 무력화된 상태**였습니다.
  하이브리드에서는 키워드 후보 50건이 전부 같은 빈 문서 하나로 접혀, RRF 가 사실상 벡터 단독으로
  돌고 있었습니다.
- **분리가 만든 버그가 아닙니다.** `main` 에 같은 테스트를 옮겨 돌려 분리 이전에도 실패함을 확인했습니다.
  좌표(`tools.jackson...`)는 초기 스냅샷부터 그대로였습니다.
- **고침:** `search-core` 가 `JsonpMapper` 빈을 제공합니다(Jackson 2 ObjectMapper + KotlinModule).
  ES 를 읽는 코드가 두 앱과 core 에 흩어져 있어 한쪽만 고치면 다른 쪽이 계속 빈 값을 받습니다 —
  **core 를 두는 이유와 정확히 같은 이유입니다.**
- **왜 여태 못 봤나:** 문서에 남은 실측은 대부분 **건수**(ES `total`) 나 **벡터 채널**
  (Qdrant payload 를 손으로 매핑) 기준이었습니다. 키워드 채널의 *내용*을 프로그램으로 검증한 적이
  없었습니다. 그래서 회귀 측정을 스크립트로 고정했습니다(`scripts/measure_search.py`).

## 코드 심문(7/27, 디버거·카오스)에서 드러난 것

### #27 실패 정리 리스너가 **서빙 중인 인덱스**를 삭제 대상에 넣는다 → **Fixed** (2026-08-03)
promote 스텝의 순서는 `swapAlias(search)` → `swapAlias(suggest)` → PROMOTED 도장
(`KeywordIndexJobConfig.kt:142-145`)입니다. **두 스왑 사이에서 죽으면** search alias 는 이미
새 인덱스를 가리키는데 도장은 없습니다. `OrphanIndexCleanupListener` 는 도장 유무만 보고
ctx 에 적힌 새 인덱스 두 개를 고아로 판정해 삭제를 시도합니다 — **한쪽은 서빙 중인데도.**

- **재현:** IntelliJ 디버거로 `:143` 에 브레이크포인트를 걸고 두 스왑 사이에서 잡을 중단.
  리스너가 `정리도 실패 [place_search_..., place_suggest_...]` 를 남겼고 목록에 **서빙 중이던
  인덱스가 들어 있었습니다.** 삭제가 실제로 안 된 건 설계 덕이 아니라 디버거 중단이 남긴 스레드
  인터럽트(`InterruptedIOException`) 때문입니다.
- **운영 리스크:** 로그가 "수동 정리 필요" 와 함께 삭제 대상 목록을 안내하는데, 그 목록에는
  서빙 중인 인덱스가 포함될 수 있습니다 — 목록대로 수동 삭제하면 서빙 인덱스를 지우게 됩니다.
- **자가 치유는 반쪽입니다.** `swapAlias` 가 `mustExist(false)` 라 다음 전체 재색인이 돌면
  스스로 낫습니다(치유 런으로 실측 확인 — sweep 이 고아를 잡고 alias 재정렬). 하지만 스케줄러
  기본값이 `enabled: false` 라 누가 재색인을 누르기 전까지 장애는 지속됩니다.
- **해결 (2026-08-03):** 도장은 **의도의 기록**이고 alias 조회가 **현실의 확인**입니다. 삭제의 근거를
  현실로 바꿨습니다 — 지우기 전에 alias 가 실제로 누구를 가리키는지 묻고, alias 뒤에 있는 인덱스는
  어떤 경우에도 삭제 목록에 넣지 않습니다. 규칙 셋을 키워드·벡터 리스너 양쪽에 넣었습니다.

| 규칙 | 막는 것 |
|---|---|
| 적재 스텝이 COMPLETED 면 지우지 않는다 | 승격에서 실패했을 때 적재분을 버리는 것 (#16 이 잃었던 성질) |
| alias 조회가 실패하면 지우지 않는다 | 현실을 모르는 채 지우는 것 |
| alias 뒤에 있는 것은 제외한다 | 이 항목의 원래 증상 |

- **같이 고친 것:** `IndexAdminService.indicesBehind` 가 모든 예외를 삼켜 빈 집합을 돌려주고 있었습니다.
  그 상태로는 **ES 장애와 "alias 없음"이 구분되지 않아**, 삭제 판단의 근거로 쓸 수 없습니다.
  404 만 빈 집합으로 처리하고 나머지는 던지게 했습니다. 덤으로 증분 prepare 가 ES 장애 때
  "alias 미설정 — 먼저 전체 재색인이 필요합니다" 라는 엉뚱한 안내 대신 실제 오류를 냅니다.
- **검증:** 규칙별 단위 테스트 6건(`OrphanCleanupListenerTest`). 원래 재현에 쓴 디버거 경로로는
  다시 확인하지 않았습니다.

### #28 채널 보호막이 **취소 신호**까지 삼킨다 → Fixed (2026-07-28)
`runChannel` 의 `catch (e: Exception)` (`HybridSearchService.kt:92`)은 부분 실패를 죽음 대신
`degraded: true` 로 승격시키는 좋은 장치입니다 — 문제는 `CancellationException` **까지** 잡는다는
것. 코루틴에서 취소는 실패가 아니라 **예외의 탈을 쓴 제어 신호**라 다시 던져야 합니다.

- **재현:** keyword 채널을 `async<ChannelRun> { delay(50); throw Exception("gd") }` 로 바꿔
  50ms 뒤 폭사시켰습니다. 비행 중이던 vector 채널에 취소가 꽂히자 로그에
  `hybrid channel 'vector' failed, degrading` + `JobCancellationException: Parent job is
  Cancelling` — 5ms 뒤 응답은 500. 로그 기록과 실제가 두 군데서 어긋납니다: vector 는 실패가 아니라
  취소였고, "degrading" 이라 적혔지만 강등 응답은 나간 적이 없습니다.
- **대조 실험:** delay 없이 즉시 던지면 vector 는 디스패치 전에 취소돼 로그 흔적이 0 —
  같은 취소가 타이밍에 따라 "무흔적" 과 "가짜 실패 기록" 으로 갈립니다.
- **실전 발화 경로는 클라이언트 이탈입니다.** 타임아웃·연결 끊김으로 요청 스코프가 취소되면
  두 채널 모두 이걸 삼키고 "failed" 를 찍습니다 — 대시보드에는 엔진 장애처럼 보이는
  **유령 채널 실패**가 쌓이고, `finally` 의 타이머는 취소된 런을 지연 지표에 섞습니다.
- **해결 (2026-07-28):** catch 첫 줄에 `if (e is CancellationException) throw e` — 취소는 다시
  던지고, 진짜 채널 실패만 `degraded` 로 승격합니다. 단위 테스트 36건 통과 확인.
- **후속 (2026-07-29):** 취소 처리를 별도 `catch (e: CancellationException)` 절로 분리하고,
  타이머를 `finally` 에서 `.also` 로 옮겼습니다. 취소된 런은 이제 지연 지표에 섞이지 않습니다.
  단위 테스트 66건 통과 확인.
- 같은 실험의 A/B 로 `runChannel` 의 효과도 확인: 보호막 안에서 던지면 200 + `degraded: true`,
  밖에서 던지면 형제 취소 + 500.
