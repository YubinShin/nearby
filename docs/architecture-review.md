# Architecture Review

색인 파이프라인과 검색 API(Step 0–6, 모듈 분리)를 직접 검토하며 설계상의 약점을 정리했습니다. **동작하는 것**과 **플랫폼으로서 올바른 설계**는 다르므로, 발견한 문제와 해결 여부를 함께 기록합니다.

각 항목에는 **상태**(Fixed / Deferred)와 그 근거를 남겼습니다.

## Initial Review — Correctness (Step 0–3)

### #1 삭제가 검색에 반영되지 않는다 → **Fixed**

증분 색인은 **현재 존재하는 행만** 읽어 Elasticsearch에 upsert합니다. 그래서 원천에서 삭제된 장소가 Elasticsearch에 그대로 남습니다. 결과적으로 검색 결과에 **유령 문서(stale document)** 가 나타날 수 있습니다.

**해결**

- `place.deleted_at` 소프트 삭제 컬럼을 추가했습니다.
- `BEFORE UPDATE` 트리거로 `updated_at`을 자동 갱신합니다.
- 증분 색인은 삭제된 행도 함께 조회하여 Elasticsearch `_bulk` **delete** 작업을 수행합니다. 멱등 처리이므로 존재하지 않는 문서에 대한 `404`는 정상으로 간주합니다.
- 전체 재색인은 `deleted_at IS NULL`만 대상으로 수행하여 tombstone 문서를 물리적으로 제거합니다.

**검증**

- 소프트 삭제 1건 → 증분 색인 → 문서 수 **64,239 → 64,238**
- 전체 재색인 후에도 **64,238** 유지
- `deleted_at = NULL`로 복구 후 증분 색인 → **64,239** 복원

삭제가 증분 색인과 전체 재색인 모두에서 일관되게 반영됨을 확인했습니다.

### #2 Watermark의 단조성 가정이 깨진다 → **Fixed** (#1과 함께)

watermark를 **인덱스에 존재하는 문서의 `max(updated_at)`** 으로 계산하는 방식에는 결함이 있습니다. 삭제된 문서는 인덱스에서 사라지므로 watermark를 전진시키지 못합니다. 그 결과 삭제된 행을 증분 색인이 반복해서 처리하게 됩니다.

또한 배치 내 처리 순서는 시간순이 아닐 수 있습니다. 그 경우 watermark를 너무 이르게 갱신하여, 아직 처리하지 못한 오래된 행을 건너뜁니다.

**해결**

- watermark를 인덱스 상태와 분리하여 별도 체크포인트 문서(`psp_index_checkpoint`)에 저장합니다.
- 전체 재색인은 초기 checkpoint를 생성합니다.
- 증분 색인은 **처리에 성공한 델타의 최신 `updated_at`** 으로 checkpoint를 전진시킵니다.
- 삭제 이벤트도 동일하게 checkpoint를 전진시키므로, 삭제 이후에도 watermark가 정상적으로 증가합니다.

**검증**

- 소프트 삭제 후 증분 색인을 다시 실행해도 **처리 대상 0건**을 확인했습니다.
- checkpoint가 삭제 이벤트 시점을 넘어 정상적으로 전진함을 확인했습니다.

**남은 한계**

현재는 `updated_at` 기반이므로 **동일 밀리초에 여러 변경이 발생하는 경우**나 **시계 역행(clock skew)** 에 이론적인 취약점이 있습니다.

운영 환경에서는 시간 대신 **단조 증가하는 `version (BIGINT)` 컬럼**을 watermark로 사용하는 방식이 가장 견고합니다.

**정정 (2026-07-25)**

PostgreSQL은 마이크로초(μs), Elasticsearch는 밀리초(ms) 정밀도를 사용합니다. 초기에는 이 차이를 맞추기 위해 `date_trunc('milliseconds')`를 적용했습니다.

그러나 이 방식은 **같은 밀리초 안에서 뒤늦게 수정된 행을 영구적으로 누락**시키는 문제를 만들었습니다.

반대로 Elasticsearch의 watermark를 그대로 사용하면 원천보다 작거나 같은 값으로만 계산됩니다. 최악의 경우에도 일부 행이 **재처리**될 뿐입니다. 증분 색인은 멱등하게 설계되어 있으므로 재처리는 허용되지만, 데이터 누락은 허용되지 않습니다.

따라서 현재는 `updated_at`을 자르지 않고 원본 값을 그대로 비교합니다. 관련 근거는 `PlaceSql.SELECT_SINCE` 주석에 남겨두었습니다.

### #3 재색인 실패 시 고아 인덱스가 남는다 → **Fixed**

`createNextVersion()`으로 새 인덱스를 생성한 뒤 문서 적재가 실패하면, alias는 전환되지 않지만 새 인덱스도 삭제되지 않습니다. 이로 인해 **서빙에는 사용되지 않는 고아 인덱스(orphan index)** 가 디스크에 계속 쌓일 수 있습니다.

**해결**

- `rebuildAndSwap()`의 문서 적재 구간을 `try/catch`로 감쌌습니다.
- 적재에 실패하면 방금 생성한 새 버전 인덱스를 즉시 삭제한 뒤 예외를 다시 전파합니다.
- alias 전환 이전에 실패하므로, 서비스 중인 인덱스에는 영향을 주지 않습니다.

**결과**

재색인 실패 시 임시 인덱스가 자동으로 정리되며, 디스크에 고아 인덱스가 누적되지 않습니다. 실패는 호출자에게 그대로 전달되므로 운영자가 원인을 확인하고 재시도합니다.

## Initial Review — Platform & Scale

### #4 본문/자동완성 alias 스왑이 원자적이지 않다 → **Deferred**

본문 인덱스와 자동완성 인덱스는 각각 alias로 교체합니다. 그래서 교체 사이의 짧은 순간에는 **`search = v2`, `suggest = v1`** 처럼 서로 다른 버전을 바라볼 수 있습니다.

현재 서비스에서는 검색과 자동완성이 독립적으로 동작하므로 실질적인 문제는 없습니다. 다만 **두 인덱스가 항상 동일한 버전이라는 보장은 하지 않습니다.**

두 alias 변경을 하나의 Elasticsearch `_aliases` 요청으로 묶으면 원자적으로 처리됩니다.

### #5 색인기와 질의기가 같은 애플리케이션이었다 → **Fixed** (Step 4 → ADR 0011)

초기에는 `search-api`가 **색인(쓰기)** 과 **검색(읽기)** 을 모두 담당했습니다.

그러나 두 역할은 요구 사항이 다릅니다.

- **색인:** 배치 처리, 높은 메모리 사용량, 긴 실행 시간
- **검색:** 고빈도 요청, 낮은 지연 시간, 높은 가용성

**1차 개선 (Step 4, 부분 해결)**

패키지를 `index`와 `query`로 분리하고 `psp.role.*` 플래그로 하나의 애플리케이션을 두 역할로 실행하도록 변경했습니다.

당시에는 **모듈을 분리하면 설정과 DTO가 중복되고, 로컬 데모에서 얻는 이점이 크지 않다**고 판단하여 배포 단위만 분리했습니다.

**검증**

- `--psp.role.indexer=false`
- `/v1/search` → **200 OK**
- `POST /admin/reindex` → **404 Not Found**

**무엇이 잘못된 판단이었는가**

플래그는 실행 경로만 막을 뿐 **프로세스를 분리하지는 못합니다.**

따라서

- 색인 작업의 OOM은 그대로 검색 장애가 됩니다.
- 설정 실수로 `psp.role.indexer=true`가 켜지면 질의 노드에 색인 API가 노출됩니다.

즉, **논리적 분리**였을 뿐 **장애 격리**는 이루어지지 않았습니다.

**2차 개선 (ADR 0011, 완전 해결)**

애플리케이션을

- `search-core`
- `search-api`
- `indexer-batch`

세 모듈로 분리하고 `psp.role.*` 플래그를 모두 제거했습니다.

이제 **모듈 자체가 역할**을 의미합니다.

**검증**

- `search-api.jar`에 `r2dbc-postgresql` 의존성 **0개**
- `search-api.jar`에 `Indexer`, `Admin` 클래스 **0개**

질의 애플리케이션은 원천 데이터베이스에 접근하거나 색인을 수행할 방법 자체가 없습니다.

설정과 DTO의 중복은 처음에는 단점이라고 생각했습니다. 그러나 `search-core`와 `core.yml`로 공통화하면서 오히려 설정 드리프트를 방지하는 장점이 되었습니다.

**대가**

한 프로세스 내부의 역할 플래그가 제공하던 보호 장치는 사라졌습니다.

이 문제는 런타임 검증을 추가하여 해결했으며, 자세한 내용은 **#14, #15**에서 설명합니다.

### #6 환경별 설정이 매핑에 박혀 있다 → **Deferred**

현재 `place_search.json`에 `number_of_shards: 1`, `number_of_replicas: 0`이 함께 정의되어 있습니다.

매핑은 환경과 무관한 **스키마**이지만, 샤드와 레플리카는 클러스터 규모와 운영 정책에 따라 달라지는 **배포 설정**입니다. 예를 들어 운영 환경에서는 일반적으로 `number_of_replicas >= 1`이 필요합니다.

**개선 방향**

- **스키마와 환경 설정을 분리**합니다.
- 매핑(mapping)은 모든 환경에서 공통으로 사용합니다.
- 샤드 수와 레플리카 수는 환경별 오버레이(dev / stage / prod)에서 주입합니다.
- 샤드 개수는 **문서 수, 노드 수, 검색 동시성**을 기준으로 산정하고, 그 근거를 함께 문서화합니다.

**Deferred인 이유**

현재 데이터 규모에서는 `1 shard / 0 replica`로도 기능과 성능에 문제가 없습니다. 운영 환경을 위한 클러스터 튜닝보다 **검색 엔진의 정확성과 구조 개선을 우선**했습니다.

환경별 배포 구성이 필요한 시점에 설정 분리와 샤드 설계 근거를 함께 반영할 예정입니다.

### #7 위치 정보의 진실 원천(Source of Truth)이 모호하다 → **Deferred**

현재 위치 정보는 PostGIS의 `geom`과 Elasticsearch의 `location (geo_point)`에 각각 저장됩니다.

두 값이 모두 존재하면 **거리 계산의 기준이 무엇인지**가 불명확해질 수 있습니다. 데이터가 불일치하는 경우 어느 값을 신뢰해야 하는지도 명시되어 있지 않습니다.

**개선 방향**

- **PostGIS `geom`을 위치 정보의 Source of Truth**로 정의합니다.
- Elasticsearch `location`은 검색 성능을 위한 **필터링과 점수 부스팅** 용도로만 사용합니다.
- 두 저장소의 역할과 책임을 ADR에 명확히 문서화합니다.

**Deferred인 이유**

현재는 Elasticsearch의 위치 검색만으로 요구 사항을 충족합니다. PostGIS와 Elasticsearch를 함께 사용하는 복합 공간 질의는 필요하지 않습니다.

서비스가 복잡해질 경우를 대비해 역할을 명확히 정의하되, 실제 구현은 요구 사항이 생길 때 반영합니다.

### #8 멀티클러스터 분리 → **Deferred** (설계 문서)

용도별 Elasticsearch 클러스터를 분리하는 구조를 로컬에서 시연하려면 **클러스터 2개와 용도별 클라이언트 빈**이 필요합니다.

그러나 현재 프로젝트 규모에서는 메모리 사용량과 운영 복잡도에 비해 얻는 실질적인 이점이 크지 않습니다.

**개선 방향**

- **애플리케이션 분리(#5)를 우선** 완료합니다.
- 멀티클러스터는 ADR과 토폴로지 다이어그램으로 설계를 문서화합니다.
- 애플리케이션이 용도별 Elasticsearch 클라이언트로 라우팅하도록 구성하여 **cluster-ready** 구조를 유지합니다.

**Deferred인 이유**

멀티클러스터는 애플리케이션 구조보다 **운영 토폴로지의 문제**입니다.

애플리케이션은 이미 용도별 클라이언트를 사용하도록 설계되어 있습니다. 실제 클러스터 분리는 운영 환경의 요구가 생길 때 수행해도 구조적인 변경이 거의 필요하지 않습니다.

## Initial Review — Operations & Quality

### #8 관측성이 없다 → **Fixed** (Step 4)

초기에는 색인 지연(index lag)이나 질의 지연(query latency)을 측정하는 지표가 없었습니다. 병목과 장애를 **추측**에 의존해 분석해야 했습니다.

**해결**

Micrometer와 `/actuator/prometheus`를 도입하여 다음 지표를 추가했습니다.

- **채널별 질의 지연**

  - `psp_query_latency_seconds`
  - 태그: `channel=keyword|suggest|vector|hybrid`, `outcome`
- **색인 지연**

  - `psp_index_lag_seconds`

**5단계 개선 — 병목을 단계별로 분해**

채널별 지연만으로는 **"벡터 검색이 느리다"** 까지만 알 수 있습니다.

그러나 임베딩 추론과 ANN 탐색은 원인과 해결 방법이 완전히 다르므로,

- 모델 교체·캐시 최적화
- ANN `ef` 조정·샤드 튜닝

을 구분할 수 있도록 `psp_query_stage_latency_seconds`를 추가하고 `stage=embed|ann`으로 분해했습니다.

이 분해로 **27ms 지연이 ANN이 아니라 임베딩 워밍업 때문**이라는 사실을 확인했습니다.

**지표 정의 수정 — 오탐 (False Positive)**

초기에는 색인 지연을

> `now - checkpoint`

로 계산했습니다.

그러나 원천 데이터가 하루 동안 변경되지 않으면 **최신 상태임에도 약 20시간 뒤처진 것처럼 보이는** 문제가 있었습니다.

실제로 **71,908초**가 기록되었으며, 이 값으로 알림을 구성했다면 매일 불필요한 경보가 발생했을 것입니다.

이를

> `max(updated_at) - checkpoint`

로 변경하여 **원천을 모두 따라잡으면 항상 0**이 되도록 수정했습니다.

**검증**

- 초기 상태 → **0**
- 원천 데이터 1건 수정 → **72,341**
- 증분 색인 완료 → **0**

지표가 실제 상태를 올바르게 반영함을 확인했습니다.

**반대 방향의 결함 — 미탐 (False Negative, 2026-08-03 Fixed)**

오탐을 수정한 이후에도 또 다른 문제가 있었습니다.

게이지가 키워드 체크포인트(`CheckpointStore.PLACE_PIPELINE`)만 읽고 있었기 때문에, **벡터 색인이 아무리 뒤처져도 lag이 0으로 표시**되었습니다.

즉,

- 오탐(False Positive)은 **최신인데 뒤처진 것처럼 보이는 문제**였고,
- 미탐(False Negative)은 **뒤처졌는데 최신인 것처럼 보이는 문제**였습니다.

체크포인트 선택을 수정하여 두 경우 모두 실제 상태를 반영하도록 개선했습니다.

| 시점                      | keyword | vector     | 옛 지표(단일)                              |
| ------------------------- | ------- | ---------- | ------------------------------------------ |
| 원천 1건 수정 전          | 0       | 0          | 0                                          |
| 원천 1건 수정 후          | 86,560  | 86,560     | 86,560                                     |
| **키워드 증분만 실행 후** | **0**   | **86,560** | **0** ← 벡터는 하루치 밀렸지만 보이지 않음 |
| 벡터 증분 후              | 0       | 0          | 0                                          |

**해결**

`psp_index_lag_seconds`를 **`pipeline={keyword,vector}`** 태그를 갖는 지표로 분리했습니다.

질의 지연이 이미 `channel` 태그를 사용하고 있으므로, 색인 지표도 동일한 방식으로 표현하여 대시보드와 알림의 일관성을 유지했습니다.

또한 `psp.vector.enabled=false`인 노드에서는 **vector lag 게이지를 등록하지 않습니다.**

벡터 파이프라인이 존재하지 않는 노드에서 lag을 0이 아닌 값으로 노출하면 새로운 오탐(False Positive)이 생깁니다. **실제로는 비활성화된 기능이 영원히 뒤처진 것처럼 보이기 때문입니다.**

**운영 영향**

태그가 없던 기존 `psp_index_lag_seconds` 시계열은 제거되었습니다.

기존 알림과 Grafana 대시보드는 `pipeline` 태그를 기준으로 갱신해야 합니다.

**남은 과제**

- Bulk 색인 실패 카운터
- 0건 검색 결과 비율(폴백 부하의 선행 지표)
- 분산 트레이싱 및 코루틴 컨텍스트 전파

### #9 `/admin/reindex`가 무인증이다 → **Deferred** (완화만)

`/admin/reindex`는 전체 재색인을 수행하는 관리 API입니다.

인증 없이 외부에 노출될 경우, 누구나 반복적으로 재색인을 실행하여 서비스에 부하를 줄 수 있으므로 **DoS 공격 벡터**가 됩니다.

**완화**

현재 공개 트래픽을 처리하는 `search-api`에는 `/admin/reindex`가 **존재하지 않습니다.**

초기에는 `psp.role.indexer=false` 플래그로 비활성화하여 `404 Not Found`를 반환했지만, 설정이 잘못되면 다시 노출될 수 있었습니다.

ADR 0011 이후에는 관리 기능을 `indexer-batch`로 완전히 분리하여, `search-api.jar`에는 `Admin` 관련 클래스가 포함되지 않습니다.

**검증**

- `search-api.jar`에 `Admin` 클래스 **0개**
- 공개 서비스 애플리케이션에는 `/admin/reindex` 엔드포인트 자체가 존재하지 않음

즉, 공개 노드에서는 설정이 아니라 **빌드 결과물 자체**가 관리 API의 부재를 보장합니다.

**남은 과제**

`indexer-batch`에는 여전히 인증이 없습니다.

운영 환경에서는 관리자 인증과 레이트 리밋을 추가하여, 권한이 있는 사용자만 재색인을 수행할 수 있도록 해야 합니다.

### #10 자동완성 랭킹이 순진하다 → **Partial** (Step 4)

초기에는 자동완성 랭킹의 문제를 **"term frequency만으로 정렬하기 때문"**이라고 판단했습니다.

그러나 실측 결과, 원인은 달랐습니다.

**잘못된 진단**

BM25는 이미 **필드 길이 정규화(field-length normalization)**를 적용하고 있었습니다.

실제로 `스타`를 검색하면 1·2위는 모두 상호명이 `스타`인 문서였으며, 짧은 이름이 자연스럽게 상위에 노출되었습니다.

진짜 문제는 **동점(tie)** 이었습니다.

상위 20개의 문서가 단 **3개의 점수**로만 구성되어 있었습니다. 같은 점수 안에서는 Elasticsearch 내부 `doc_id` 순으로 정렬되었습니다.

이 순서는 세그먼트 병합, 재색인, 레플리카 상태에 따라 달라질 수 있으므로 결과가 결정적이지 않았습니다.

**개선**

1. **결정적 정렬(Deterministic Ordering)**

  - `place_id`를 2차 정렬 키로 추가했습니다.
  - **검증:** 동일 질의를 5회 반복해도 결과 순서가 완전히 동일했습니다.

2. **접두어 우선**

  - `name.raw`에 대한 `prefix` 가산점을 추가했습니다.
  - 비접두 매칭인 `e-스타치과`는 **57위 → 122위**로 내려가며 기대한 방향으로 랭킹이 조정되었습니다.

3. **이름 길이 보정**

  - `name_length`의 역수를 점수에 반영했습니다.
  - 그러나 BM25의 길이 정규화와 신호가 대부분 겹쳐 효과는 제한적이었습니다.
  - `강남` 질의에서는 일부 개선이 있었지만 `김밥`에서는 변화가 없었습니다.
  - 구현 비용이 필드 하나뿐이므로 유지했습니다.

**남은 한계**

궁극적으로 자동완성 랭킹은 **인기도(클릭 수, 주문 수 등)** 와 같은 사용자 행동 신호가 있어야 품질이 크게 향상됩니다.

현재 원천 데이터에는 이러한 신호가 없으므로, `function_score` 구조만 마련해 두고 실제 랭킹 함수는 교체 가능한 형태로 설계했습니다.

자세한 내용은 **ADR 0009**를 참고합니다.

### #12 0건 폴백이 질의를 두 번 보낸다 → **Deferred**

엄격 질의(strict query)의 결과가 0건이면 완화 질의(relaxed query)를 한 번 더 실행합니다.

정상 경로에서는 추가 비용이 없습니다. 0건 비율이 높은 서비스에서는 동일한 사용자 요청이 두 번의 검색 요청으로 확장되어 Elasticsearch 부하가 증가합니다.

**개선 방향**

- 0건 검색 비율을 별도 지표로 수집합니다.
- 임계치를 초과하면 폴백 정책을 조정합니다.

  - 폴백 비활성화
  - 결과 캐시 적용
  - 완화 전략 변경

**남은 과제**

근본적인 해결은 검색 실패 자체를 줄이는 것입니다.

- 오타 교정(spell correction)
- 동의어 사전
- 질의 정규화

등을 도입하여 폴백 의존도를 낮추는 방향이 필요합니다.

### #13 형태소 분석 불일치로 인한 검색 누락 → Analyzer Pipeline Fixed

초기에는 형태소 분석기의 품질 문제로 검색 누락이 발생한다고 판단했습니다.
그러나 실측 결과, 문제의 대부분은 분석기가 생성한 결과를 후처리 단계에서 제거하는 필터 정책에 있었습니다.

**잘못된 진단**

초기 가설:

> 사용자 사전이 부족하여 형태소 분석이 잘못되고 있으며, 사전을 추가하면 해결된다.

실제 원인은 형태소 분석 자체보다 **분석 결과를 제거하는 필터 정책**에 있었습니다.

**원인 분석**

상호명 64,239건을 대상으로 원문 토큰이 색인 과정에서 사라지는 비율을 측정했습니다.

피해의 대부분은 사용자 사전 부족이 아니라, 1단계에서 설정한 공격적인 `stoptags` 때문이었습니다.

특정 상호명이 잘못 분석되어 조사·의존명사 등 제거 대상 품사로 태깅되면, `stoptags` 필터가 해당 토큰을 색인 대상에서 제외합니다.

결과적으로 해당 장소는 특정 질의에서만 낮게 노출되는 수준이 아니라, **어떤 질의로도 검색할 수 없는 상태**가 됩니다.

| 구성                          | 글자 유실 | 글자 불일치 |
| ----------------------------- | --------- | ----------- |
| ① 1단계 상태 (사전X · 공격적) | 30.81%    | 34.34%      |
| ② stoptags 만 완화            | 8.36%     | 16.98%      |
| ③ ② + 사전 1,379개            | **5.57%** | **14.36%**  |
| ④ POS 필터 없음 (하한)        | 0.82%     | 9.23%       |

> 글자 유실: 원문 상호명에 포함된 문자가 분석 결과 토큰에서 사라진 비율
> 글자 불일치: 원문과 분석 결과 토큰 집합이 다른 비율

**해결**

1. 플러그인에 `user_dictionary`, `fw_dictionary` 로딩 경로 추가
2. 원천 데이터 기반 사전 자동 생성 (`scripts/build_komoran_dict.py`, 1,379개)
3. 기본 `stoptags` 정책을 보수적으로 변경

마지막 변경으로 색인량은 약 8% 증가했지만, 약 12,000건의 상호가 검색 가능한 상태로 회복됐습니다.

**사전 설계에서 배운 것**

"원천의 명사를 넣는다"는 순진한 접근은 검색을 **악화**시킵니다.
카테고리는 이미 올바르게 분해되고(`돼지고기/구이/찜`), 상호명 통짜 등록은 부분 검색을 죽입니다.
기준을 **"분석기가 틀리게 아는 문자열"** 로 바꿨습니다. 문자열이 항상 하나의 고유명사인지 일반 단어 조합인지 판단하기 위해, 문자 주변 결합 패턴을 활용한 어휘 경계 점수를 도입했습니다.

**세 층으로 나눈 사전**

자동 추출(1,377) + 사람이 넣는 시드 `manual.dict`(21) +
검색 로그 채굴(`QueryLog` → `mine_query_log.py`, 후보 제안까지 자동·채택은 사람).
원천 기반은 *데이터에 있는 말*만 담고 *사용자가 치는 말*은 담지 못해서입니다(`브런치`가 그 예).

**0건 질의의 두 종류**

원문 존재 여부를 분석과 무관한 wildcard 로 확인해
`[분석실패]`(사전으로 해결됨) / `[데이터없음]`(사전 넣어도 그대로)로 표시합니다. 구분하지 않으면
"사전에 넣었는데 왜 그대로냐"를 반복하게 됩니다.

**남은 한계**

현재 지표는 문서 분석 결과와 원문 간 차이를 측정하기 때문에 recall 저하만 직접 측정합니다.

그러나 query analyzer와 document analyzer가 동일하게 실패하는 경우 검색 결과는 유지될 수 있습니다.
표본 **6,000건 중 519건**이 글자를 잃고도 그 이름으로 검색됩니다.
이 경우 문제는 recall이 아니라 precision 저하로 나타납니다.

이를 검증하려면 실제 사용자 질의와 클릭 로그 기반 평가셋이 필요합니다.
→ [ADR 0008](adr/0008-korean-analyzer-komoran-vs-nori.md)

### #14 사전과 인덱스의 버전 불일치를 감지할 장치가 없다 → **Fixed** (ADR 0011)

사전 파일을 변경한 뒤 재색인하지 않으면, 색인은 이전 사전으로 질의는 새 사전으로 분석됩니다. 같은 문자열이 서로 다르게 분해되어 **매칭이 실패합니다.** 초기에는 "사전을 변경하면 재색인한다"는 운영 규율로만 방지하고 있었습니다.

**1차 해결 — 스키마 도장 (ADR 0011)**

모듈 분리와 함께 **런타임 버전 도장**(`IndexMeta`)을 도입했습니다. 색인기가 alias 스왑에 성공한 뒤 `psp_index_meta`에 계약을 기록하고, 질의기는 기동 시 이 값을 대조하여 다르면 기동에 실패합니다. Elasticsearch 매핑이나 문서 스키마를 변경하면 `SCHEMA_VERSION`을 올리는 것이 규율이 되었습니다.

**검증**

- `SCHEMA_VERSION`을 2로 변경 → 질의기 기동 **실패**
- 실패 메시지에 어긋난 항목과 조치 방법이 포함됨을 확인했습니다.

**2차 해결 — 분석기 지문 (2026-08-03)**

사전 파일은 Elasticsearch 파드에만 마운트되므로, 별도 JVM으로 실행되는 색인기와 질의기는 파일 해시를 계산할 수 없습니다. 따라서 파일 대신 **분석 결과를 지문**으로 사용합니다. 고정된 문장 세 개를 `_analyze`에 전달하고, 반환된 `term:startOffset:endOffset` 목록을 SHA-256으로 해시한 앞 6바이트를 `analyzer_fingerprint`로 도장에 기록합니다.

측정 대상은 "파일이 동일한가"가 아니라 "같은 문자열이 동일하게 분해되는가"입니다. 그래서 사전뿐 아니라 애널라이저 설정과 플러그인 버전 변경도 감지합니다. 검색 인덱스와 자동완성 인덱스는 애널라이저가 다르므로 지문도 각각 기록합니다.

**검증**

| 인덱스 / 애널라이저                         | 지문           |
| ------------------------------------------- | -------------- |
| `place_search` / `komoran`                  | `6985af8f19f6` |
| `place_suggest` / `autocomplete_search`     | `98bd512b40b3` |
| `komoran_probe` / `komoran_raw` (사전 없음) | `263b8fe32946` |

사전 유무에 따라 지문이 달라짐을 확인했습니다.

**남은 한계**

지문은 고정된 세 문장의 분석 결과만 측정하므로, 이 문장들에 영향을 주지 않는 사전 변경은 감지하지 못합니다.

`analyzer_fingerprint` 필드가 없는 기존 도장은 차이로 판정하지 않으므로, 보호는 다음 전체 재색인부터 적용됩니다. 감지 범위 밖의 드리프트는 **매일 전체 재색인**(ADR 0011 결정 6)이 24시간 안에 정리합니다.

## Findings — Step 5·6 (Vector & Hybrid)

### #15 벡터에 모델 버전이 기록되지 않는다 → **Fixed** (ADR 0011, #14와 동형)

임베딩 모델을 변경한 뒤 재색인하지 않으면, 문서 벡터는 이전 모델로 질의 벡터는 새 모델로 생성됩니다. 두 벡터가 **서로 다른 공간**에 놓여 유사도가 의미를 잃지만, 예외는 발생하지 않고 점수만 잘못됩니다.

사전과 인덱스의 버전 불일치(#14)와 **같은 구조의 문제**입니다. 형태소 분석이든 임베딩이든, "색인과 질의가 같은 것을 사용해야 한다"는 제약을 코드가 아니라 운영 규율로만 보장하고 있었습니다.

**1차 완화 (ADR 0010)**

추론을 애플리케이션 안에 두어 한 프로세스에서 두 모델이 갈라질 수 없도록 했습니다. 다만 *색인 시점의 모델*과 *질의 시점의 모델*이 서로 다른 배포일 가능성은 그대로 남았습니다. 그리고 모듈을 분리하면서(ADR 0011) 이 완화마저 사라졌습니다. 따라서 이 항목을 먼저 해결해야 모듈 분리가 안전해집니다.

**해결 (ADR 0011)**

색인기가 alias 스왑에 성공한 뒤 **실제로 로드된 모델**의 식별자와 차원을 도장에 기록합니다(`VectorIndexJobConfig`). 값은 설정이 아니라 로드 결과에서 읽습니다(`EmbeddingModel.modelId`는 해석된 모델 디렉터리 이름). 그래서 설정만 일치하고 파일이 다른 경우도 감지합니다.

질의기는 기동 시 이 값을 대조하여 다르면 기동에 실패합니다(`IndexContractGuard`). 증분 색인도 prepare 단계에서 도장을 대조하여 다르면 **거부합니다.** 증분은 새 컬렉션을 만들지 않고 살아 있는 컬렉션에 덮어쓰므로, 모델이 바뀐 채 증분이 실행되면 한 컬렉션에 두 모델의 벡터가 섞입니다. 사후 감지 대신 **사전 차단**을 선택했습니다.

**검증**

- `IndexMetaTest` 10건 — 모델 식별자 불일치, 차원 불일치, 필드별 차이 수집, 벡터 비활성 노드 예외를 각각 고정
- `IndexMetaStampDeserializationTest` 3건 — 분석기 지문 도입 이전에 기록된 도장과의 호환

**기각한 대안 — Qdrant 컬렉션 메타**

당초 방향은 도장을 Qdrant 컬렉션 메타에 기록하는 것이었습니다. 확인 결과 Qdrant 1.12는 모르는 필드를 `{"result":true,"status":"ok"}`로 응답한 뒤 저장하지 않습니다. 이 기능이 막으려는 실패 방식과 정확히 동일합니다. 확인 없이 진행했다면 도장을 기록했다고 판단하면서, 실제로는 아무것도 기록되지 않았을 것입니다. 따라서 도장은 Elasticsearch 문서(`psp_index_meta`) 한 곳에 모았습니다.

### #16 긴 적재의 마지막 짧은 단계가 실패하면 전부 잃는다 → **Deferred** (Step 5 신규)

벡터 전체 재색인에서 8분 33초를 들여 64,239건을 모두 적재했습니다. 그 뒤 alias 조회 URL 오타로 발생한 `404` 하나 때문에 `500`으로 실패했습니다. 적재는 성공했지만 스왑에 도달하지 못해 결과적으로 사용할 수 없는 상태가 되었습니다.

적재분이 컬렉션에 남아 있어 alias를 수동으로 연결하여 복구했으나, 이 복구 경로는 API에 없습니다. 운영 규모에서는 수 시간짜리 적재가 마지막 1초 때문에 전부 무효가 되는 구조입니다.

실패 시 정리(#3)를 적재 구간에만 적용한 판단은 결과적으로 옳았습니다. 스왑 실패까지 정리 대상에 포함했다면 8분치 적재를 자동으로 삭제했을 것입니다.

**검증 — alias 스왑 무중단**

alias를 20회 왕복 스왑하는 동안 검색 230회를 실행하여 실패 0회, 빈 결과 0회를 확인했습니다(ADR 0010).

즉 이 항목은 "스왑이 위험하다"가 아니라 "스왑에 도달하지 못했을 때 복구할 방법이 없다"입니다.

**개선 방향**

적재와 스왑을 따로 호출할 수 있는 단계로 분리합니다(`?swap=false` + `POST .../promote`). "적재해 두고 필요한 시점에 승격"이라는 운영 시나리오도 함께 확보합니다.

**적재분 보존 규칙의 회귀와 복원**

Spring Batch 전환(ADR 0013)에서 정리가 `JobExecutionListener`로 바뀌면서 job 전체를 대상으로 하게 되었습니다. 그 결과 스왑이 실패하면 적재를 마친 인덱스와 컬렉션을 삭제하는 상태가 되었습니다. 2026-08-03에 "적재 스텝이 COMPLETED면 삭제하지 않는다" 규칙으로 되돌렸습니다(#27).

**Deferred인 이유**

적재분을 잃지 않는 성질은 복원했지만, 적재와 스왑을 따로 호출할 수 있게 분리하는 작업은 하지 않았습니다. `indexer-batch`의 관리 API에는 `?swap=false`도 `POST .../promote`도 없습니다.

### #17 벡터 채널이 결과 없음을 판별하지 못한다 → **Mitigated** (문턱 + 하이브리드)

키워드는 일치하지 않으면 0건을 반환하지만, 벡터는 **항상** 가장 가까운 후보를 반환합니다.

**완화 1 — 코사인 문턱**

실측으로 `min-score` 0.84를 선택했습니다. `스타벅스`(top-1 0.834)와 `ㅁㄴㅇㄹ`(0.839)은 차단되지만, `차 고치는 곳`(0.842)은 차단하지 못합니다. 0.008 차이입니다.

**원리적 한계**

완화를 두 겹으로 적용해도 남습니다. 뜻이 통하는 질의의 top-1은 0.844~0.883, 엉터리 질의는 0.794~0.870으로 **분포가 겹칩니다**(ADR 0010). 어떤 절대 문턱도 두 집단을 나누지 못합니다.

**완화 2 — 하이브리드 결합 (ADR 0003)**

고정 세트 질의 20개(`scripts/eval/queries_regression.txt`)에서 0건이 키워드 7 → 하이브리드 0으로 줄었습니다(2026-07-29 재측정).

**RRF가 해결하지 못하는 부분**

키워드가 0건이면 결합해도 벡터 단독 결과입니다. `차 고치는 곳` → `차병원사거리포차`는 하이브리드에서도 동일하게 반환됩니다. 6단계 착수 시점에는 RRF를 해결책으로 기록했지만, 재측정 결과 recall만 해결하고 precision은 해결하지 못했습니다.

**개선 방향**

"일치하는 결과가 있는가"를 키워드가 거부권으로 행사하는 방식(키워드가 0건이면 벡터 단독 결과를 신뢰하지 않음)까지 가야 합니다. 다만 그렇게 하면 `회 먹을 데`(키워드 0건, 벡터 정답)도 함께 차단됩니다.

**남은 한계**

두 경우를 가르는 신호가 아직 없습니다. 정답 데이터는 2026-08-05에 확보했습니다(`scripts/eval/golden_set.yaml`, 질의 25개·정답 1,088건). 다만 `expect_empty`가 전부 `false`라 "0건이 정답인 질의"를 구분하는 라벨은 없습니다. 트랩 질의 4개도 0건이 아니라 속성을 제외한 나머지가 정답입니다.

### #18 필터의 선택도를 확인하지 않고 문턱을 해제한다 → **Fixed**

벡터 채널은 엔진 필터가 하나라도 있으면 절대 문턱을 해제했습니다(ADR 0010 후속). 문턱은 필터 없는 전체 코퍼스에서 측정해 정했으므로 방향 자체는 옳습니다. 다만 **필터의 선택도(selectivity)를 확인하지 않았습니다.**

현재 데이터는 전부 강남구이므로 `sigungu=강남구`는 아무것도 걸러내지 않습니다. 그런데도 필터가 있다는 이유만으로 문턱이 해제되어, `스타벅스` 질의가 `스타럭스포타커피`(0.834)를 반환했습니다.

**기각한 대안 — 선택도 기준**

남은 비율을 기준으로 삼는 방식입니다. 카테고리 `과학·기술`(0.290)은 REAL 질의 20개 중 13개를 0건으로 만들지만, 반경 1000m(0.163)는 0개입니다. 남긴 양은 점수 하락의 예측 변수가 아닙니다(ADR 0010 Threshold follow-up 2).

**해결**

후보가 한 건도 빠지지 않은 필터에만 문턱을 유지합니다. 이 경우 후보 집합이 필터가 없을 때와 동일하므로, 점수 분포가 같다는 것이 측정 없이 성립합니다.

개수를 세는 대신 필터의 여집합(`must_not`)을 `limit: 1`로 조회하여 한 건이라도 빠졌는지만 확인합니다(`QdrantSearchStore.narrows`).

**실측 — 판별 비용**

| 방법                             | 실측          |
| -------------------------------- | ------------- |
| 전체 개수 + 필터 개수 (2회 조회) | 10.7 + 14.5ms |
| 여집합 개수 조회 (1회)           | 12.0ms        |
| **여집합 1건 조회 (채택)**       | **1.2ms**     |

**남은 한계**

후보를 전혀 줄이지 않는 필터만 걸러냅니다. 의미 축을 잘라내는 필터에서는 문턱이 해제된 채로 나가므로, `교육` 카테고리에 엉터리 질의를 넣으면 여전히 결과가 반환됩니다. 문턱으로 풀 수 있는 문제가 아니라는 #17의 결론은 그대로입니다.

### #19 하이브리드의 `total`이 후보 풀 크기다 → **Deferred** (Step 6 신규)

`/v1/hsearch`의 `total`은 채널별 후보 50건씩을 결합한 유니크 문서 수입니다(최대 100, `psp.hybrid.candidates: 50`). 코퍼스 전체의 매칭 수가 아닙니다. 페이지를 깊게 요청하면 결과가 조용히 끊깁니다.

키워드 단독 채널은 실제 매칭 수 2,552를 반환하지만 결합하면 92가 됩니다. **같은 이름의 필드가 채널마다 다른 것을 셉니다.** 클라이언트가 이 값으로 페이지 수를 계산하면 틀립니다.

**완화**

api-spec에 두 `total`의 의미가 다르다는 점과 상한 100을 명시했습니다. 계약 문서로는 구분되지만, 응답만 보고는 두 값을 구분할 수 없습니다.

**개선 방향**

깊은 페이징을 차단하거나(`MAX_PAGE`를 후보 깊이에 맞춰 낮춤), `total` 대신 `hasMore`로 계약을 변경합니다. 검색 API에서는 후자가 계약을 과장하지 않습니다.

**Deferred인 이유**

`MAX_PAGE`는 여전히 99이고(`SearchModels.kt`), `hasMore` 필드도 없습니다. `page=99`를 요청하면 `total`은 100 이하인데 `hits`는 빈 배열로 반환됩니다.

### #20 파생 테이블의 변경을 증분 색인이 잡지 못한다 → **Deferred** (브랜드 복원 신규)

`place_brand`는 원천이 준 값이 아니라 인허가 데이터와 대조해 복원한 파생 테이블입니다. 여기만 바뀌면 `place.updated_at`이 움직이지 않습니다. 증분 색인은 `PlaceSql.SELECT_SINCE`의 `p.updated_at > ?`만 보므로, **브랜드 변경이 색인에 반영되지 않습니다.**

`place_brand`에는 `created_at`만 있고 `updated_at`이 없습니다. `recover_brands.sh`도 `place_brand`에 INSERT만 수행하고 `place`를 갱신하지 않습니다.

현재는 전체 재색인으로만 반영됩니다(키워드 17초, 벡터 8분 12초 — ADR 0011). 데이터가 커지면 그 비용이 그대로 늘어납니다.

**같은 구조의 두 번째 테이블**

`place_duplicate`도 동일합니다. `SELECT_BASE`가 `place_brand`와 `place_duplicate`를 모두 left join하므로, 중복 판정이 바뀌어도 `place.updated_at`은 움직이지 않습니다.

이쪽은 `IndexMeta.SCHEMA_VERSION`을 2로 올려 우회했습니다. 색인 대상이 달라졌다는 사실을 도장에 실어, 전체 재색인 전까지 질의기가 기동하지 못하게 막습니다. 다만 증분으로는 이미 색인된 중복 문서를 걷어내지 못한다는 한계 자체는 남아 있습니다.

**개선 방향**

파생 테이블에도 `updated_at`을 두고 워터마크를 **둘 중 최댓값**으로 계산합니다. 또는 브랜드 갱신 시 대상 `place` 행을 touch 합니다. 후자가 단순하지만 파생 테이블이 원천을 갱신하는 구조가 됩니다.

**같은 형태의 문제**

"입력이 바뀌었는데 그 사실이 워터마크에 실리지 않는다"는 뼈대는 사전·인덱스 버전 정합(#14), 벡터 모델 버전(#15)과 같습니다. 두 항목은 런타임 도장으로 닫았습니다. #20에는 대응하는 장치가 없습니다.

### #21 채널이 브랜드를 서로 다르게 인식한다 → **Partial** (구조는 해결, 짧은 토큰은 남음)

키워드와 자동완성은 `brandOf()`(복원분 + 시드 사전)를 사용하지만, 벡터는 `r.brand`(복원분만)를 사용했습니다. 그래서 사전으로만 아는 브랜드를 벡터 채널이 전혀 인식하지 못합니다.

| 질의               | 키워드  | 벡터  | 하이브리드 합의 |
| ------------------ | ------- | ----- | --------------- |
| `스타벅스`(복원분) | 86      | 26    | 10/10           |
| **`CU`**(사전분)   | **187** | **0** | **0/10**        |
| **`GS25`**(사전분) | **255** | **1** | **1/10**        |
| `파리바게뜨`       | 50      | 50    | 10/10           |

`파리바게뜨`가 정상인 이유는 **상호명 자체에 그 글자가 있기 때문**입니다. 정규형이 상호명과 다른 브랜드(`CU`↔`씨유`, `GS25`↔`지에스25`)만 깨집니다.

**같은 실수의 반복**

스타벅스 때 "키워드만 고치면 채널이 어긋난다"를 확인하고 고쳤습니다. 그러나 시드 사전을 추가하면서 벡터를 함께 고치지 않았습니다.

**구조적 원인**

브랜드를 정하는 규칙이 **두 벌**이었습니다. `PlaceDocuments.brandOf()`는 private 이고, 임베딩 문장과 Qdrant payload 는 `r.brand`를 직접 읽었습니다.

**해결**

브랜드 결정을 `brand/Brands.kt` 한 곳으로 올렸습니다. 네 경로가 전부 `Brands.resolve()`를 사용합니다.

| 경로           | 위치                        |
| -------------- | --------------------------- |
| 색인 문서      | `PlaceDocuments.searchDoc`  |
| 자동완성 label | `PlaceDocuments.suggestDoc` |
| 임베딩 문장    | `PlaceVectorText`           |
| Qdrant payload | `PlaceVectorPayload`        |

규칙이 한 벌이면 한쪽만 고치는 사고가 발생하지 않습니다.

**검증**

`BrandsTest` 14건으로 고정했습니다. 그중 `the search doc, the embedding text and the payload use the same brand`가 세 경로를 한 테스트로 묶으므로, 어느 하나만 고치면 여기서 실패합니다.

### #27 실패 정리 리스너가 **서빙 중인 인덱스**를 삭제 대상에 넣는다 → **Fixed** (2026-08-03)

promote 스텝의 순서는 `swapAlias(search)` → `swapAlias(suggest)` → PROMOTED 도장입니다(`KeywordIndexJobConfig`). **두 스왑 사이에서 중단되면** search alias 는 이미 새 인덱스를 가리키는데 도장은 없습니다. `OrphanIndexCleanupListener`는 도장 유무만 보고 ctx 에 적힌 새 인덱스 두 개를 고아로 판정해 삭제를 시도합니다. **한쪽은 서빙 중입니다.**

**재현**

IntelliJ 디버거로 두 스왑 사이에 브레이크포인트를 걸고 job 을 중단했습니다. 리스너가 `정리도 실패 [place_search_..., place_suggest_...]`를 남겼고, 목록에 **서빙 중이던 인덱스가 들어 있었습니다.**

삭제가 실제로 실행되지 않은 것은 설계 덕이 아니라 디버거 중단이 남긴 스레드 인터럽트(`InterruptedIOException`) 때문입니다.

**운영 리스크**

로그가 "수동 정리 필요" 와 함께 삭제 대상 목록을 안내하는데, 그 목록에 서빙 중인 인덱스가 포함될 수 있습니다. 목록대로 수동 삭제하면 서빙 인덱스를 지우게 됩니다.

**부분적 자가 치유**

`swapAlias`가 `mustExist(false)` 라 다음 전체 재색인이 실행되면 스스로 복구됩니다(치유 런으로 실측 확인 — sweep 이 고아를 정리하고 alias 를 재정렬). 다만 스케줄러 기본값이 `enabled: false` 라, 누군가 재색인을 실행하기 전까지 장애가 지속됩니다.

**해결 (2026-08-03)**

도장은 **의도의 기록**이고 alias 조회는 **현실의 확인**입니다. 삭제의 근거를 현실로 바꿨습니다. 삭제 전에 alias 가 실제로 어느 인덱스를 가리키는지 조회하고, alias 뒤에 있는 인덱스는 어떤 경우에도 삭제 목록에 넣지 않습니다. 규칙 셋을 키워드와 벡터 리스너 양쪽에 넣었습니다.

| 규칙                                     | 막는 것                                             |
| ---------------------------------------- | --------------------------------------------------- |
| 적재 스텝이 COMPLETED 면 삭제하지 않는다 | 승격 실패 시 적재분을 버리는 것 (#16이 잃었던 성질) |
| alias 조회가 실패하면 삭제하지 않는다    | 현실을 모르는 채 삭제하는 것                        |
| alias 뒤에 있는 인덱스는 제외한다        | 이 항목의 원래 증상                                 |

**함께 고친 것**

`IndexAdminService.indicesBehind`가 모든 예외를 삼켜 빈 집합을 반환하고 있었습니다. 그 상태로는 **Elasticsearch 장애와 "alias 없음"이 구분되지 않아** 삭제 판단의 근거로 쓸 수 없습니다. `404`만 빈 집합으로 처리하고 나머지는 던지도록 바꿨습니다.

증분 prepare 도 Elasticsearch 장애 때 "alias not set — run a full reindex first" 라는 엉뚱한 안내 대신 실제 오류를 반환합니다.

**검증**

규칙별 단위 테스트 6건(`OrphanCleanupListenerTest`). 재현에 사용한 디버거 경로로는 다시 확인하지 않았습니다.

### #28 채널 보호막이 취소 신호까지 삼킨다 → **Fixed** (2026-07-28)

`runChannel`의 `catch (e: Exception)`은 부분 실패를 전체 실패 대신 `degraded: true`로 승격시키는 장치입니다. 문제는 `CancellationException` **까지** 잡는다는 점입니다. 코루틴에서 취소는 실패가 아니라 **예외의 형태를 띤 제어 신호**이므로 다시 던져야 합니다.

**재현**

keyword 채널을 `async<ChannelRun> { delay(50); throw Exception("gd") }`로 바꿔 50ms 뒤 실패시켰습니다. 실행 중이던 vector 채널에 취소가 전파되자 로그에 `hybrid channel 'vector' failed, degrading`과 `JobCancellationException: Parent job is Cancelling`이 남았고, 5ms 뒤 응답은 `500` 이었습니다.

로그와 실제가 두 군데서 어긋납니다. vector 는 실패가 아니라 취소였고, "degrading" 이라고 기록됐지만 강등 응답은 나간 적이 없습니다.

**대조 실험**

delay 없이 즉시 던지면 vector 는 디스패치 전에 취소되어 로그 흔적이 0입니다. 같은 취소가 타이밍에 따라 "무흔적" 과 "가짜 실패 기록" 으로 갈립니다.

`runChannel` 자체의 효과도 같은 실험의 A/B 로 확인했습니다. 보호막 안에서 던지면 `200` + `degraded: true`, 밖에서 던지면 형제 취소와 함께 `500` 입니다.

**실제 발생 경로 — 클라이언트 이탈**

타임아웃이나 연결 끊김으로 요청 스코프가 취소되면 두 채널 모두 이를 삼키고 "failed" 를 기록합니다. 대시보드에는 엔진 장애처럼 보이는 **유령 채널 실패**가 쌓이고, `finally`의 타이머는 취소된 런을 지연 지표에 섞습니다.

**해결 (2026-07-28)**

catch 첫 줄에 `if (e is CancellationException) throw e`를 넣었습니다. 취소는 다시 던지고 실제 채널 실패만 `degraded`로 승격합니다. 단위 테스트 36건 통과를 확인했습니다.

**후속 (2026-07-29)**

취소 처리를 별도 `catch (e: CancellationException)` 절로 분리하고, 타이머를 `finally`에서 `.also`로 옮겼습니다. 취소된 런은 지연 지표에 섞이지 않습니다. 단위 테스트 66건 통과를 확인했습니다.

## Findings — Load Test (2026-08-03, 1,000 concurrent)

### #29 취소 삼킴이 hydrate 경로에 남아 있었다 → **Fixed** (2026-08-03)

#28 은 `runChannel`만 고쳤습니다. 같은 파일 `present()`의 hydrate 는 `runCatching { keyword.byIds(...) }` 라 `Throwable`을 잡아 `CancellationException` 까지 삼키고 있었습니다.

**발견 계기**

부하 측정 중 콘솔이 읽을 수 없는 속도로 출력됐습니다. 내용은 `hybrid hydrate failed for N ids`와 `JobCancellationException: MonoCoroutine was cancelled` 였습니다. 클라이언트가 연결을 끊을 때마다 경고와 스택트레이스를 기록하고, 취소를 무시한 채 진행하고 있었습니다.

**해결**

`runChannel`과 같은 형태로 `catch (e: CancellationException) { throw e }`를 앞에 두고 나머지만 삼키도록 교체했습니다. 단위 테스트 70건 통과를 확인했습니다.

**같은 패턴의 잔존**

결함을 한 자리에서 고칠 때 **같은 패턴이 파일 안에 몇 군데 더 있는지** 세지 않으면 남습니다. `runCatching`은 코루틴에서 취소를 삼키는 기본 함정입니다.

### #30 WebClient 기본 커넥션 풀이 코어 수에서 유도된다 → **Fixed** (2026-08-03)

`QdrantSearchStore`는 `WebClient.builder().baseUrl(...).build()`로 끝나 커넥션 풀을 지정하지 않았습니다. Reactor Netty 기본값은 `maxConnections = max(코어, 8) × 2`이고 대기 큐는 그 2배입니다. 10코어 머신에서 **동시 20개 처리, 40개 대기**가 상한이었습니다.

**발견 계기**

벡터 채널이 부하에서 조용히 빠졌습니다. HTTP 는 전부 `200`이고 본문의 `degraded: true` 로만 드러납니다.

**두 단계로 드러난 한계**

처음에는 `PrematureCloseException` 이었습니다. 서버가 끊은 idle 커넥션을 풀이 그대로 재사용한 것입니다. 커넥션 수명을 설정해 이를 막자 다음 한계인 `PoolAcquirePendingLimitException`(`Pending acquire queue has reached its maximum size of 40`)이 드러났습니다.

**실측 (서울 531,528건, 요청 5,000 고정)**

| 동시성 | degraded 전   | degraded 후 | 로그 줄 수 전 → 후 |
| ------ | ------------- | ----------- | ------------------ |
| 100    | 14건 (0.3%)   | **0**       | 5,650 → 0          |
| 500    | 288건 (5.8%)  | **0**       | 115,774 → 0        |
| 1000   | 845건 (16.9%) | **0**       | 320,670 → 0        |

**해결**

`ConnectionProvider`에 `maxConnections(100)`, `pendingAcquireMaxCount(1000)`, `pendingAcquireTimeout(5초)`, `maxIdleTime(20초)`, `maxLifeTime(5분)`, `evictInBackground(30초)`를 명시했습니다. 풀을 직접 만들었으므로 `@PreDestroy`로 정리합니다.

**측정 도구의 한계**

`ab`는 반쪽 응답을 성공으로 세므로 같은 구간에서 "실패 0" 이 나옵니다. 응답 본문의 `degraded`와 `channels[].failed`를 세는 측정기로 바꾼 뒤에야 드러났습니다.

**남은 한계**

로그 축약(경고 1건당 385줄 → 1줄, 상세는 DEBUG)은 코드에 넣었지만, 이번 측정에서는 실패가 0이라 효과를 재지 못했습니다.

**처리량 천장**

동시성을 10배 올려도 하이브리드는 350~420 RPS 로 유지되고 지연만 선형으로 늘었습니다. 한 대(MacBook Air M4)에 Elasticsearch·Qdrant·PostGIS·애플리케이션이 함께 올라간 배치의 몫입니다. 하드웨어와 배치를 가르는 실험은 ADR 0011 의 EKS 노드 분리입니다.
